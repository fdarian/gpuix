# Motion

Everything that moves on its own: spring transitions for `motion` (patch 3), and the rest of area E: CSS transitions, keyframes and `animation`, motion values, layout animations, Web Animations objects, `matchMedia`, reduced motion, `motion.span` and `display: contents` inheritance. Rust resolves motion per frame inside the GPUI render, in `packages/native/src/motion/`; the API stays Framer-shaped (`initial` / `animate` / `transition`).

How a running animation is drawn cheaply (patch frames, dormant animations) is in [patch-frames.md](patch-frames.md). Where this doc differs from Chrome or Motion is in [deviations.md](deviations.md#motion).

## Spring transitions (patch 3)

`motion` had `duration` plus a named ease or `cubicBezier`, and a retarget (`MotionState::sync`) restarted from the visible value at zero velocity. That cannot express a Framer-style spring. The second gap matters more: velocity carried through an interruption is what makes a spring feel fluid, for example a hover highlight gliding between rows as the pointer moves. The motivation is porting the components on fluidfunctionalism.com, whose springs are `fast` (0.08 s, critically damped), `moderate` (0.16 s) and `slow` (0.24 s, bounce 0.12).

`transition: { type: "spring", ... }` has two forms, both Framer-shaped: `stiffness` / `damping` / `mass` (defaults 100 / 10 / 1), or `duration` + `bounce`. The second is converted with a port of motion-dom's `findSpring` and `bounceToDampingRatio` (`animation/generators/spring.mjs`, the engine behind Framer Motion), checked in a Rust test against values taken from that module's `spring()`. `restDelta` / `restSpeed` use Framer's defaults, tighter for moves under 5 units. Tween transitions (no `type`, or `"tween"`) are untouched. A spring runs on any `motion` key, the transform keys (`x`, `scale`, `rotate`, ...) included ([transforms](paint-and-transforms.md#css-transforms-92)).

`MotionState` keeps a position and a velocity for the segment start. A spring is the closed-form damped oscillator (under-, critically and over-damped) evaluated from that start, so it is exact, does not depend on frame rate, and there is no numeric integration. On `sync` the new segment starts at the sampled position and sampled velocity. A tween interrupted by a spring hands over its instantaneous slope (a central difference of the easing curve); a spring interrupted by a tween drops the velocity. `frame().active` / `just_settled` / `motionComplete` work as for tweens.

- Springs overshoot, so the applied value is clamped (`opacity` to 0..1, sizes and `borderRadius` to zero or more) while the unclamped value keeps driving the physics.
- **When a spring ends is Motion's rule** (`spring.mjs` and `calcGeneratorDuration`; a `motion` element and a motion value alike). A spring given as `duration` and `bounce` is done when `duration` has passed, and the thresholds are not read. A spring of physics is done at the first multiple of 50 ms at which the generator is within its thresholds, `restDelta` (0.5, or 0.005 for a move under 5 units) and `restSpeed` (2, or 0.01), and that multiple is its duration. Before then it reads the target at every instant it is within its thresholds, and the spring where it is not. From its end it is the target, whatever the spring would read: a spring that is within its thresholds for only a while (an underdamped one passes through them with some speed) used to rest where its first reader found it, 1.0017 for a motion value from 0.4 to 1.
- A spring given as `duration` and `bounce` that is retargeted at speed carries the speed (see [deviations](deviations.md#motion)), and so is done when `duration` has passed and it is within its thresholds, at a multiple of 50 ms: it may not have settled by `duration`.
- `duration` is where the spring has decayed to 0.1% of the move, as in motion-dom, and where it ends.
- A spring with a very large `sqrt(stiffness / mass)` or `damping / (2 * mass)` (over 1e6) is rejected, because the closed form would overflow.
- `AnimatePresence` needed no change. The React `motionKey` hashes the whole transition, so changing only a spring option starts a new generation.

**Why native, and not Framer Motion.** Framer runs its physics in JavaScript every frame and writes the DOM. In gpuix that would be a JS-to-native style mutation per frame per animated element, with no `requestAnimationFrame` to pace it (only `setTimeout`, which is not synced with the display link), and most of Framer has nothing to attach to: DOM measurement, layout animations, gestures and MotionValues bound to CSS. Native motion needs no React render or N-API call per frame.

**Rejected: numeric integration per frame** (what Framer's generators do). It needs a stable step, so it depends on frame timing. The closed form is exact and stateless, which also keeps frozen-clock frame capture deterministic.

## The default transition

A key whose transition describes no curve runs Motion's default for it (`motion/default_transition.rs`, motion-dom's `getDefaultTransition` and the `isTransitionDefined` test of `animateMotionValue`, the same in motion-dom 12 to 14): a spring (stiffness 500, damping 25, rest speed 10) for a transform key, a critically damped one (stiffness 550, damping 30, or `2 * sqrt(550)` towards 0) for `scale`, `scaleX` and `scaleY`, `easeOut` over 0.8 s for more than two keyframes, and `cubic-bezier(0.25, 0.1, 0.35, 1)` over 0.3 s for the rest. The transform keys are Motion's `transformProps`; `scaleZ` and `originZ` are not among them.

- **A transition describes the curve** by any field but `delay`, `repeat`, `repeatType` and `repeatDelay` (`Transition::defaulted` is false). `{ delay: 0.3 }` keeps the key's default and delays it; `{ type: "tween" }` or `{ duration: 1 }` on `x` is a tween of 0.3 s or 1 s with `easeOut`.
- **The level for a key** is `transition[key]`, else `transition.default`, else the whole transition. When it is the whole transition, an entry for another key in it counts as describing the curve, so `{ width: { duration: 1 } }` leaves `x` a 0.3 s `easeOut` tween and not a spring (Motion does the same).
- **`delay` is not inherited** from the top of the transition by a `default` or an entry. A `delay` beside them is ignored, as in Motion.
- **The transition of a target** (a variant, `whileHover`, ...) replaces the component's as a whole.
- **`animate(value, target)` on a motion value** is Motion's `animateMotionValue("", ...)`: no key, so never a spring, and three or more keyframes run for 0.8 s.
- **`for_prop` resolves** the default when the track begins, from the number of keyframes and whether `keyframes[1]` is 0. A gesture target's own transition is resolved the same way for the properties it moves.
- The oracle replay (`motion-default-oracle.json`, `motion-default.test.tsx` in React and Solid) compares the path of every key it can read (not `opacity`, whose default curve `motion-waapi.test.tsx` replays) to within 0.6 px. `rotate`, `skew` and the other angle and depth keys are checked by the table in `default_transition.rs` alone.

## A target's own transition

`animate`, `exit`, a variant and `whileHover` / `whileTap` / `whileFocus` / `whileInView` take a `transition` beside their keys, resolved as Motion's `animateTarget` does (`visual-element-target.mjs`): the target's own `transition` replaces the component's wholesale (Motion merges only for `inherit: true`, not built), a target without one plays with the component's, and the key level and the per-key default then run on whichever it is (previous section). So `exit={{ scale: .6, transition: { duration: .1 } }}` over a component spring plays a 0.1 s `easeOut` tween with no `scale` spring default, while `{ delay: .2 }` alone keeps each key's default.

- **One place splits it.** `resolveTarget` (`motion-variants.ts`) takes `transition` out of an object target as it does out of a variant, for `animate`, `exit`, `initial` and the gestures, in React, Solid, `motion.span` and the SVG shapes. The description's `transition` is the resting target's own, else the component's; Rust is unchanged.
- **`initial` is never animated**: its `transition` is accepted and ignored.
- **The way out of a gesture** plays with `animate`'s own transition, else the component's, not the gesture's, as in Motion (a test pins it).
- **Solid's `AnimatePresence`** played an exit with the description's transition; it now plays `exitTransition` (exit's own, else the component's), for an object and for a named variant, in every mode.
- **The layout glide** uses the component's `transition` (or `MotionConfig`'s) and not a variant's or target's, as Motion's projection does (`getDefaultTransition()` is `props.transition`). React fed it the variant's before.
- **The oracle**: `motion-default-oracle` has 17 more rows for a target's transition against the component's (a duration against a spring on `scale` to 0, a delay alone, entries and `default` on either side, `{}`); `motion-default.test.tsx` in React and Solid replays every `target` row through a variant, an object `animate`, an object `exit` through `AnimatePresence` and `whileHover`. `motion-target-transition.test.tsx` covers the way back, `initial`, a changed target transition restarting the animation and the exit modes.

## What animates

- **Lengths are a px part and a percentage part.** A motion length is `AnimValue::Number`, `Percent` or `Calc { px, percent }` (`motion/value.rs`), whatever unit it is written in, so `px`, `%`, `calc()` and `em` / `rem` / `vw` / `vh` / `vmin` / `vmax` mix and blend part by part, as Chrome blends a `calc()` pair. Relative units are px when a track holds them and the percentage stays a share of its basis, which lowers to a taffy calc node every frame: a parent that resizes mid-animation is followed exactly with no measurement, and a spring carries its speed on each part. Measurement still serves `auto` and unset starts only. Number-kind fields (`fontSize`, gaps, border widths, outline width and offset, corner radii) take length strings too, and refuse a percentage where CSS gives none. CSS transitions and animations start from a calc value instead of treating it as unset.
- **Multi-value shorthands split before they parse.** `animate`, `initial`, `exit`, keyframes and CSS `@keyframes` split `padding`, `margin`, `inset`, `borderWidth`, `borderColor`, `gap` and `borderRadius` (the `/` form included) into one value per longhand (`split_shorthand`), frame by frame for keyframes, so each side, axis or corner has its own track. An elliptical corner is one `AnimValue::Ellipse` of four channels, so both radii animate.
- **Filters.** `filter` animates in CSS transitions, `@keyframes`, Web Animations and Motion keys (tweens and springs, `motion/filter_value.rs`, `AnimValue::Filters`), by the Filter Effects rules and checked against Chrome (`filter-interp-oracle`, 97 cases, 408 computed strings): lists with the same functions blend function by function, a shorter list is padded with each missing function's identity (`blur(0)`, `brightness(1)`, `grayscale(0)`, `drop-shadow(0 0 0 transparent)`), `none` is the empty list, and lists that differ at a position of the common prefix flip at the middle of the eased progress. The `drop-shadow()` colour blends in sRGB when both ends are legacy syntax and in Oklab otherwise. Blur, brightness, contrast and saturate are held at zero or above, and grayscale, invert, sepia and opacity to 0..1, under a spring's overshoot. A CSS keyframes track decides each interval alone (`PropPlan::Segments`). A spring carries its velocity across a retarget over the functions the two lists share. `Filter` is in `AnimProp::paints_only`, so a tick patches (20 of 20 ticks over a 400-cell page, one element built); the element is an effect group, as it is with a static filter. Motion hands `filter` tweens to Web Animations, so `getAnimations()` lists them for a `motion.div`.
- **Colours** animate in Oklab (premultiplied) with springs per channel and velocity carry-over: `color`, `backgroundColor`, `borderColor`, `outlineColor`, `boxShadow`, SVG `fill` and `stroke`. `borderColor` is the shorthand of four side colours, so a `border-color` transition fires one event per side. Motion colours go through the paint `ColorContext` and animated `<svg>` colours repaint through `SvgPaint::image` (see [paint-and-transforms.md](paint-and-transforms.md#colours)).
- **CSS transitions**: `transition`, `transitionProperty`, `transitionDuration`, `transitionTimingFunction` and `transitionDelay` (all timing functions, including `steps()` and `linear()`), with transition events. They apply to plain style changes and state-style changes. Transition and animation events dispatch through the pointer-event path and bubble, not cancelable ([events-and-input.md](events-and-input.md#pointer-events)). The events of one time come in Chrome's order: a transition's `transitionstart` follows its own `transitionrun` (the next transition's run comes after both), and ends by their time. The transitions of one change are made in the order of their CSS names, which sets that order.
- **Per-property transitions** (`transition: { default, opacity: {...} }`) for every numeric `StyleDesc` property, including margin, padding, gap and per-corner radii. `height: "auto"` and px to `%` targets work through a zed commit that exposes a layout node's content size.
- **Keyframes** with `times`, `repeat`, `repeatType` and `repeatDelay`; CSS `animation` with `defineKeyframes`. A keyframe may write `none` or `auto` against a value (a paint, a dash list, a path, a size, a radius): that interval swaps at 50%, and each interval of a property decides on its own (`PropPlan::Segments`), so a blend followed by a swap blends first.
- **Transforms.** Motion's transform keys (the depth keys `z`, `translateZ`, `scaleZ`, `rotateX`, `rotateY`, `transformPerspective` and `originZ` among them), `transform` as a key, and CSS `transform`, `translate`, `rotate`, `scale`, `transformOrigin`, `perspective` and `perspectiveOrigin` animate, and their ticks patch. How lists pair and blend in 3D, and what steps instead of blending, is in [paint-and-transforms.md](paint-and-transforms.md#animations).
- **Text underline.** `textUnderlineOffset` and `textDecorationThickness` animate, from the offset an element inherits when it leaves it unset (an unset thickness is `auto`, which is not inherited), and through a negative thickness, which is valid and paints one device pixel as zero does, all against Chrome.

### SVG

`<svg>` takes DOM-style shape children (`<path>` and friends); `pathLength`, `strokeDasharray` and `strokeDashoffset` draw, and `d` morphs (see [paint-and-transforms.md](paint-and-transforms.md#svg-and-img)). CSS keyframes drive the SVG properties Chrome animates (`strokeDashoffset`, the other stroke and paint properties, geometry, `d`), on the shapes in an `<svg>` and on the `<svg>`:

- Keyframes carry `PropKey::{Style, Svg}` (`motion/keyframes.rs`) and a name resolves per target (`PropTarget` in `css_animation.rs`: shape, host, element). On a shape it resolves to the SVG property first (`opacity`, `width`, `height` and `fontSize` included); elsewhere to the style, where an SVG-only property is ignored because Chrome computes it and never paints it.
- A shape is never built as an element, so `svg_tree.rs` advances its CSS animations while the `<svg>` writes its markup. Their values overlay the shape's props and its `motion`, and a shape with animation state joins `Sources.motion` while it moves or its keyframes changed, so the host is built again. The `<svg>`'s own values go on the root node, which is how inherited properties reach the shapes.
- A missing endpoint is the shape's own attribute, else the nearest ancestor's for an inherited property, else CSS's initial value (`SvgAttr::initial_css`).
- Keyframe properties are limited to the animatable set. `defineKeyframes` refuses the attributes that are not CSS properties (`pathLength`, `x1`, `stdDeviation`, `dx`, `refX`).
- **Transitions.** A change of an SVG attribute or of the same property in `style` on a shape or the `<svg>` starts a CSS transition when that element declares one, as Chrome does for the properties its keyframes animate. `css_transition.rs` is keyed by `PropKey` (`Style` or `Svg`) and an element has a `PropTarget`; the restyle that starts a box transition starts an SVG one from the computed SVG values of the frame (`SvgValues`: own attribute, else inherited, else CSS's initial value). `svg_tree::animate` steps a shape's transitions beside its animations, between its own attributes and its `motion`, and the `<svg>` steps both in `resolve_declared_style`. They are listed as `CSSTransition` with the CSS property name.
- **A transition declared in the same update as the first change** runs. CSS judges a change by the transition properties of the style after it, and a shape has no style before it to seed from, so an element an `<svg>` writes keeps, per update, the first value each custom prop replaced (`ElementExtras::props_before`, cleared when the `<svg>` writes it again). A shape that declares a transition and is not tracked yet seeds its state from those props and the ones its ancestors had; the `<svg>` does the same. A shape without a transition pays one map insert per changed prop and nothing per frame.
- **`motion` on a shape** owns the attributes it animates: a transition of such an attribute stays off it, as on a box, while the attributes `motion` does not drive still transition.
- A motion value binds style properties and no SVG attribute. To move the stroke of an `<svg>` with one, bind its `color` and use `currentColor` strokes.

## Motion values

`useMotionValue`, `useTransform`, `useSpring`, `useVelocity` and the imperative `animate()` exist in React and Solid and are native-driven, so linked layers cannot drift. Grabbing a value mid-flight continues from where it is.

`animate()` returns Motion's playback controls (`time`, `speed`, `duration`, `iterationDuration`, `startTime`, `state`, `pause()`, `play()`, `stop()`, `cancel()`, `complete()`, `attachTimeline()`, `finished`, `then`), run natively and read against Motion 14.1.0 itself (the `motion-controls` oracle):

- A source keeps its animation as a track on a `Playback` clock (`motion/web_animation.rs`, shared with CSS animations).
- `Sample.moving` separates a held animation (in effect, no frame asked for, no velocity) from one that moves.
- The renderer has `pauseMotionValue`, `playMotionValue`, `seekMotionValue`, `setMotionValueSpeed`, `completeMotionValue`, `detachMotionValueClock` and `getMotionValuePlayback`.
- **`time` counts the delay**: 0 is the start of the delay, and it is not held at the end, so a seek past the end reads back as set.
- **`speed` 0 is a hold** that lasts until `play()`, whatever the speed is set to after, and the state stays `"running"`. It is kept in `Run` (`values.rs`), not in `Playback::SetPlaybackRate`, whose rate semantics are the Web Animations ones.
- **`isAnimating()` is Motion's `!!value.animation`.** It stays true after the controls' `stop()` and `cancel()` and is cleared by a finish, the value's own `stop()` or `jump()`, or a replacing `animate()`.
- **`startTime`** is in the time base of the Web Animations timeline (below): ms on the renderer's clock, set where Motion sets it (`play()`, the `time` setter while running) and `null` before the animation starts, after a finish and after `stop()` or `cancel()`.
- **`duration` and `iterationDuration` before the value is bound** come from `measureMotionAnimation`, which takes the transition and keyframes the native run would use and needs no renderer. The browser entry (wasm) does not register it.
- **`attachTimeline(timeline)`** is Motion's `JSAnimation`: the clock stops driving the run (the state stays `"running"`), `timeline.observe(controls)` is called and its cleanup kept for `stop()`, and `play()` gives the frames back. Called before the value is bound, the last timeline attached is observed when the animation starts. gpuix has no scroll timelines (`scroll()`, `useScroll`, `ScrollTimeline`, `animation-timeline`), so only a timeline an app writes drives it.

## Layout animations and presence

`layout` (FLIP), `layoutId` shared-element morph, `LayoutGroup`, and a `Reorder` drag-reorder primitive. `AnimatePresence` gets `mode="wait"`, `"popLayout"` and `custom`. `Reorder` calls `setPointerCapture` on `pointerdown`. See [Layout glides](#layout-glides) for what the glide animates and how.

### Layout glides

`motion/layout_flip.rs` holds the state of every `layout` box, `motion/layout_projection.rs` the geometry (Motion's `calcBoxDelta` and `mixTargetDelta`).

- **A projection**, not an offset: the translation of the centre of the box and a scale of its size about it, from the box that was shown to the box layout gives, easing to nothing (four channels of one track). `layout` is `Axes::Both`; `"position"` cuts the shown box to the new size (translation of the corner only); `"size"` cuts it to the new corner (`create-projection-node` `notifyLayoutUpdate`). A glide is a transform: `FlipOffset` enters `Window::with_element_space` in prepaint and in paint, so bounds, hitboxes and every primitive are drawn and measured through it, and layout is never touched.
- **When a glide starts.** Only on a frame where the tree changed since the box was last stepped (`tree.revision()`, handed to `LayoutFlips::retain`). Motion measures around one render, and animation ticks never set `isLayoutDirty`, so a box that layout moves because an animation above it ticked (a height spring), or because scroll anchoring adjusted, follows at once with the offset it had. The box is stepped on every frame it is prepainted, so nothing is missed; a box not prepainted for a while (skipped content) glides what moved on the first commit it sees.
- **Where it measures.** At the first *drawn* frame after the commit. A layout-only pass (a forced read, or the one `scrollTo` runs before it writes) reads the glides in flight and starts none (`Flip::peek`, `LayoutFlips::step(.., painted)`), so a scroll a layout effect, a passive effect or a Solid `createEffect` writes after such a read is in the measure, as it is in Motion (which measures in a microtask after the layout effects; React runs the passive effects of a sync render before it, those of a default-lane render after). The glide starts where the box was *seen on the screen*, which is Motion's viewport measure of a scroller without `layoutScroll`: the flip keeps the layout box in the frame of layout and the offset of the scrolling around it (`Flip::offset`, `Held::offset`), and the move between the offset of the frame it was drawn in and the offset of the frame that measures is part of the start. A `layoutId` newcomer in another scroller (or outside one) starts at the holder's place on the screen the same way. A scroll written after the measuring frame (a default-lane passive effect, a wheel) moves the glide with the content, as in Motion. Moves are still judged in the frame of layout: a scroll alone, with the box unmoved in its content, glides nothing (Motion glides a box that re-rendered in a commit that scrolls; gpuix cannot tell which boxes re-rendered).
- **The commit apart from the frame's ticks.** A commit that lands while something animates (`LayoutFlips::note_ticking`) is laid out once before the frame that draws it, in a layout-only pass that samples time at the last draw (`Window::set_commit_survey`, asked at the start of every draw, skipped when a read already made that pass). A flip records the box the pass saw (`Flip::surveyed`, kept for that revision) and glides from where it was shown to *that* box, so what the frame's own ticks move (a height spring above a `layout="position"` footer) is followed and not glided, as Motion measures a render apart from the animation frame after it.
- **Corrections.** `Window::with_projection_scale` hands the scale to the first element prepainted or painted inside it; `Interactivity::compute_style_internal` divides that element's px radii (per axis; a zero `y` means the `x`) and its shadows' offsets (per axis), blur and spread (by the mean) by it, as Motion's `correctBorderRadius` and `correctBoxShadow`. Children are not corrected, and are stretched along.
- **A tick beside an idle box is patched** ([patch-frames.md](patch-frames.md#an-idle-layout-box-117)). A `layout` box is built by every frame (it is `Exclusion::LayoutAnimation`), which is what starts a glide at the commit that moved it. Whether a glide is in flight is asked of the live boxes at each tick (`LayoutFlips::needs_frames`) and not recorded with the frame: while one is, or while its start or complete event waits for a render, or for a box with `dragOffset`, the tick is whole (`Gliding`).
- **Nested boxes.** A `layout` box inside another is shown at its own projection, not the enclosing one's: `Store::enclosing` carries the net projection and the ambient transform inside the box, and `layout_projection::inside` is the matrix that takes the enclosing projection back out (Motion's `treeScale`/`applyTreeDeltas`). Nothing is subtracted from a nested move any more, because the box compares its own shown box with its own new layout box.
- **A drag** (`dragOffset`) is a translation of the same projection; the lifted box is deferred inside the same space.

## Web Animations objects

`element.getAnimations()` returns `CSSTransition` then `CSSAnimation` objects (`js/web-animations.ts`), one per native run id per renderer, then the plain `Animation`s of a `motion` component (below). They are the DOM's `Animation`, an `EventTarget`, and are compared with Chrome in the `web-animations` and `motion-waapi` oracles.

- Native carries the clock (`motion/web_animation.rs`: id, rate, the API's pause and play override, seek, end time, start time, the pending play or pause and the notes `Ready`, `Finish` and `Cancel` the spec makes promises and events of). A run that ended stays readable until JS releases it (`releaseAnimation`).
- `RendererState.dispatch` consumes `webanimationready`, `webanimationfinish` and `webanimationcancel` before any app dispatch, and the mutation queue cancels the animations of destroyed elements.
- A command names its element to the next frame (`Sources::commanded` in `retain.rs`): a transition that had finished runs again after `play()`, a seek or a rate change, and nothing in its last build said it could. Retention reads that as one of the reasons an element is built again ([retention.md](retention.md#invalidation-rules)).
- Relevance follows Chrome by phase and rate: a paused animation at its end without a fill is not listed.
- `getAnimations()` and the commands of an element that is dormant read the clock, not the instant of the last frame, since no frame or tick need have come for it for any time (`GpuixView::api_instant`; dormancy is in [patch-frames.md](patch-frames.md)).

**Playback.** `cancel()`, `finish()`, `reverse()`, `updatePlaybackRate()`, `ready`, `pending`, `startTime` (settable), `timeline`, `onfinish` and `oncancel` work as in Chrome, with the `finish` and `cancel` events and the promises in Chrome's order. A `play()` or `pause()` waits for a frame that is drawn: a layout pass a read forced (`Window::is_layout_pass`, told to the engines by `note_pass`) creates runs pending and tells the DOM nothing, and the draw after it resolves them (`Ready` first for a play and after the events for a pause). `emit_css_events` merges the DOM events and the Web Animations events by `seq`, and the events of a play that just ran or a transition a frame made go after them (`late`), which is Chrome's order. `cancel()` leaves the run idle: a CSS animation stays in `runs`, a transition goes to `ElementState::cancelled`, and `play()` brings it back.

**Time base.** A renderer is gpuix's document, so its timeline time is ms on its `AutomationClock` since its origin (the base the test renderer's `clock*` calls return). `startTime`, `animation.timeline.currentTime`, the `timelineTime` of an event and a motion value's `startTime` are on it. `document.timeline` does not exist, since `document` spans every window; `animation.timeline` is the renderer's `DocumentTimeline` (`currentTime` only). Only differences between two times are comparable with Chrome or Motion, whose bases are the page's and `performance.now()` ([deviations](deviations.md#motion)).

**Effect.** `animation.effect` is a `KeyframeEffect` (`motion/effect.rs`), the same object every time: `target`, `getKeyframes()`, `getTiming()`, `getComputedTiming()` and `updateTiming()`. `getKeyframes()` has the implicit 0% and 100% keyframes Chrome adds (`composite: "replace"`, at the value the element has without the animation), the per-keyframe easing, or the start and the end of a transition, with every value written as Chrome does: transforms with the functions they were written with, colours in the space they were written in, shadows, easings as written, SVG lengths, dash lists and paths, `border-spacing` as its two properties. A transition holds a colour of another space in Oklab, and a `transform-origin` of a transition is the lengths of the box it started in. `updateTiming()` serves both engines and what it sets stays against a later style; a transition plays `endDelay`, `iterationStart`, `iterations`, `direction` and `fill` from the same timing animations use. The effect cannot be made or replaced (no `setKeyframes()`, `composite` or `pseudoElement`).

**Lists.** `getAnimations({ subtree: true })` and `document.getAnimations()` list the animations of the elements below, or of every window, in Chrome's order: every transition then every animation, each in document order of the elements (`getSubtreeAnimations` and `getDocumentAnimations`; `document` takes each renderer's list in the order the roots were installed).

**Animations of Motion.** An animation of a `motion` component that Motion 14.1.0 hands to the browser is listed as a plain `Animation` (`motion/script.rs`; kind `"script"`): `opacity`, `backgroundColor`, and a colour (`color`, `outlineColor`, SVG `fill` and `stroke`) with a keyframe in a syntax only the browser reads (`oklch()`, `color-mix()`), unless the transition has `repeatDelay`, `repeatType: "mirror"` or `damping: 0`. The track keeps the clock it always had for the value it shows, and the script adds the clock and the effect the Animation would have: Motion's delay, iterations (`direction: "alternate"` for `repeatType: "reverse"`), `fill: "both"`, the easing of the effect or per keyframe where `ease` is a list, and a spring as the `linear()` easing Motion samples every 10 ms over the time it takes to rest. It is listed once a frame is drawn and delisted when it finishes, is replaced or its element goes. Standalone motion values, and the keys Motion runs in JS (`x`, `width`, ...), are not listed. Every command works as on the Animation Motion makes: the value follows the animation, `finish()` completes the motion, `cancel()` shows the value it started from and Motion never hears of it (`onMotionComplete` does not fire), a pause asks for no frames, and a finish tells its `cancel` a frame later.

**Revival.** A run the style lets go of (a CSS animation whose name leaves `animation`, a transition whose property is no longer transitioned or has a new target) or a script animation that was cancelled or finished is idle and unlisted, and Chrome plays it again when a script plays, seeks or finishes it, without the style owning it. Native keeps it while JS holds the `Animation`: `css_animation.rs` and `css_transition.rs` move it to the element's disowned runs (listed after the ones the style owns once played, driving its property whatever a later style says, telling the DOM nothing for an animation and everything for a transition) and `track.rs` keeps the idle script of a motion track. JS holds such an animation weakly, and native drops the run on `forgetAnimation`, called from a `FinalizationRegistry` or for an event nobody holds. A revived script animation lasts only while its track is unchanged.

**Never-built content.** `getAnimations()` of an element inside `content-visibility` skipped content styles the skipped hosts around it like a read of its geometry ([forced-reads.md](forced-reads.md#animations-in-forced-content)); the lists of a subtree and of the document do not force.

## `matchMedia` and reduced motion

`matchMedia` has change events for `prefers-reduced-motion` (from the OS), `prefers-color-scheme` (from the appearance, see [window.md](window.md#appearance)), `hover`, `pointer` and size queries. `MotionConfig reducedMotion="user"` follows the OS setting.

## `motion.span`

`motion.span` (React and Solid) animates what an inline box shows (`Scope::InlineBox`): colours, `opacity`, the font of its text, padding, margin, border, radii, outline and the decoration lengths. It takes `animate`, `initial`, `exit`, `variants`, `whileHover`, `whileTap`, `whileFocus` and `whileInView`.

- The paragraph reads the style `motion/inline.rs` sampled for the frame (`InlineStyles`, which also lays the motion values bound in its `style` over it) in `paragraph::styles`, `inline_decoration::of` and `InsetSpec::of_moving`, so a width-affecting key lays the paragraph out again every frame.
- The gestures are states of the span's `PointerStates` sources, read whether or not the span declares a `hover` entry (`MotionState::set_gestures`, called from `sync_motion_states`). `whileInView` is a gesture JS turns on (`inView`) from an `IntersectionObserver`.
- A key that is not an inline box's (`width`, `display`, ...) throws. A transform key, `layout*` and `drag*` are accepted and do nothing, as a transform does nothing to a non-atomic inline box in Chrome.
- The gestures, `variants` and the variant names a controlling component hands down are those of every `motion.*` (`motion-variants.ts`).
- A span's CSS transitions and keyframe animations move the same properties; its other properties apply at once. Letter and word spacing and `textShadow` do not exist on an inline box, so they do not animate.

The inline-box model itself is in [text.md](text.md#inline-text-and-spans).

## An animated inherited value on `display: contents` (#49)

A motion, transition or keyframes animation of `color` or `fontSize` on a `display: contents` element reaches its children, with retention on or off. The element is never built and its children are spliced into its parent, so they used to get only the inheritable part of its declared style.

`splice_overlay` steps the wrapper with `animate_style`, the function `build_element` also steps an element's style with (transitions, `motion`, motion values, keyframes), once a frame for each (`contents_styles`), and hands the children the inheritable part of what it shows. The overlay key is a hash of those values and of what runs, not the wrapper's `style_serial`, so a child is built again exactly when a value it inherits changes. A child under a running element notes the motion in its own record, which keeps it and the way up to the wrapper on the spine while the wrapper runs. A property that needs a box (`opacity`, a background, a size) still does nothing, because there is no box, as in the DOM.

## A style native rejects does not freeze React

An invalid animation, transition or grid track used to make `applyBatch` fail inside `resetAfterCommit`. That left react-reconciler's `isFlushingWork` set, so no root in the process committed a sync update again. The batch is now resent without the offending `setStyle`, and the error goes to the root's `onUncaughtError`. Don't let a native style error propagate out of `resetAfterCommit`: every root stops committing.

## Breaking changes

- **A `motion` key with no transition runs Motion's default for it**, not a 0.3 s `easeOut` tween: a transform key springs (`x`, `y`, `rotate`, `scale`, ...), more than two keyframes take 0.8 s, and the rest use `cubic-bezier(0.25, 0.1, 0.35, 1)`. So does `animate(value, target)` on a motion value, and a transition that holds only a `delay` or a repeat field.
- An unknown or non-animatable key in `motion` `animate`, `initial`, `exit` or `transition` throws (it was ignored). Invalid `transition*` and `animation*` values throw when the batch flushes.
- A `motion` or keyframe target written with `calc()`, `em`, `rem`, a viewport unit or a mixed length no longer throws, and a CSS transition from or to one no longer jumps. `borderRadius` and the corner longhands are not circular-only: a percentage or elliptical corner animates.
- A `width`, `height` or `px`-to-`%` animation that waits for a measurement starts its clock at the change, not at the frame that measured, so its first moving sample is one frame earlier than it was.
- A cubic-bezier `ease` can overshoot (it was clamped to 0..1). Applied values still clamp per property.
- A property dropped from `animate` keeps animating to its old target, as in Framer. Unchanged properties keep their timeline on re-render instead of restarting.
- An `<svg>` with shape children ignores `source`/`src`, and its `width`/`height` props size the svg box.
- `strokeDasharray: ["4","2"]` in `motion` is now two keyframes.
- `layout` is a universal prop on host elements, and `animate` is optional on motion components.
- Solid's host keeps an element alive when Solid moves its node (a removed node's element is destroyed at flush, and inserting a node before itself is a no-op). This fixed Solid `Reorder` and `AnimatePresence` exits.
- Solid `AnimatePresence` keeps exiting nodes in place.
- A motion, transition or keyframes animation of an inherited property on a `display: contents` element reaches its children.
- The controls of `animate()` follow Motion: `time` counts the delay and is not held at the end, a `speed` of 0 holds until `play()` (a later speed no longer runs it), `isAnimating()` stays true after the controls' `stop()` and `cancel()`, `duration` and `iterationDuration` no longer throw before the value is bound, and `startTime` and `attachTimeline` exist.
- Transition events of one time come in Chrome's order (a start follows its run, ends by their time), where every run of a change came before any start.
- A script animation of `backgroundColor` that Motion hands to the browser (a motion component's, listed by `getAnimations()`) blends two legacy colours in sRGB as CSS does; the colours Motion keeps to itself blend in Oklab as before.
- A forced read (a geometry read inside skipped content) creates the CSS animations and transitions of the elements it builds, where it used to step none ([forced-reads.md](forced-reads.md#animations-in-forced-content)).
- `getAnimations()` lists the animations of `motion` components that Motion hands to the browser, and a CSS animation or transition the style cancelled is revived by a command instead of throwing.

## A motion starts at the frame that shows it (#104)

A layout pass a read forced samples the instant of the last draw, which is long past in a window that sat idle. A motion that a commit starts or retargets starts its tracks at the later of that instant and the clock (`ScriptFrame::started`), not at the stale one: a `getBoundingClientRect` in the handler of the pointer event, after a second of nothing, otherwise started the glide a second ago, and the frame that shows it was already at the target. Sampling still uses the instant of the pass, so a read of a motion that moves answers as the last frame showed it.
