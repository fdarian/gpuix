# Forced reads

`getElementBounds`, `getBoundingClientRect` and `getScrollMetrics` never return a stale answer: a read in the same turn as a mutation lays the window out first, as a browser forces layout. Here that costs a layout-only pass that draws nothing, the pass does only the work the change needs, and the reads after it share it. This file covers that read path, including reads inside skipped `content-visibility` content.

## A read lays out and does not draw (#39)

A browser forces layout on a read and paints once at the frame. The first version here drew the window synchronously on a read, and that draw was not a frame the display showed: a pointer handler that wrote and read on every move paid 3 draws per frame. `Window::draw_if_dirty` is now `Window::layout_pass(paint = false)`: it builds the next frame with the same `draw_roots` as a draw, up to and including prepaint, so scroll handle metrics and element states are current, and then throws the frame away. Element states go back to `rendered_frame`, and the hit test, pointer capture and tooltip bounds are restored.

A pass:

- skips paint, focus listeners, the input handler, entity observation, text-layout frame rotation, the accessibility tree and `needs_present`;
- renders every view in full instead of reusing its cached prepaint and paint;
- leaves the window dirty, so the frame that follows is the only draw and the display link presents once however many reads came before it;
- runs again only when something was invalidated since the previous pass. A clean window runs no pass.

`Window::paint_if_dirty` is the variant for a caller that needs painted output: `getPaintedText`, `getPaintedHighlights` and the synthetic input that `automation.rs` injects (it is hit tested against a drawn frame). It draws, and it is the same pass with paint inside it.

### Inside input dispatch

A read never swaps frames, in or out of dispatch. A draw inside dispatch would swap the frame the dispatch is reading: a key's dispatch path indexes a different dispatch tree, and mouse listeners the dispatch holds out of the frame are written back over the new one, so scrollers stop scrolling and bubble handlers see `is_hovered` false. A pass is safe there because the dispatch reads the rendered frame and a pass swaps nothing. Don't make a read draw: `paint_if_dirty` inside dispatch builds every subtree. See [patch 1](frames-and-wakes.md#no-inline-draws-in-real-windows-patch-1) for the rule on inline draws.

The accessibility tree and the input handler (IME caret bounds) are not covered by a pass: they describe the previous frame until the next draw. Making them current would mean swapping frames.

### Publication

What paint used to publish is published from prepaint. `Window::publish_layout(f)` queues `f` and runs it once the whole tree is prepainted, because an element's own prepaint does not yet have the bounds of what comes after it. Published this way: element bounds, borders, inline span bounds and scroll metrics. A `List` that prepaints a row range and rolls it back takes the entries its rolled-back rows queued with it.

Anything new that a read can observe must be published from prepaint when `window.is_layout_pass()`, or a read after a change sees it stale. The `on_painted` and `on_painted_layout` listeners already are; a custom paint-time publisher queues itself with `publish_layout`.

A publication runs under the layout engine that was current when it was queued, and so does a deferred draw (`Window::defer_draw`). An atomic inline lays its boxes out in an engine of its own, swapped in only while it works, and a layout id from it means nothing in the window's engine. Running a publication in the wrong engine made a box inside an `inline-block` read its insets from an unrelated node, or panic with "invalid SlotMap key used", on a layout-only read.

### A pass does not advance time (#70)

A browser's animation clock stands still within a frame and a forced layout runs no animation. `GpuixView::pass_instant` reads the clock in a draw and `frame_instant` in a pass that only lays out: the instant of the last draw, stamped once before the first. Scrollbar fades, scroll animations, motion states, motion values and virtual rows all sample it. The reference pass of a verified frame already took the draw's instant.

When a pass read the clock, it moved a spring, which fired its `change` event, whose handler wrote `scrollTop` and read layout again. FF's command menu did this: one arrow key ran 40 to 60 layout passes (about 90 ms) before a frame drew. Chrome runs none of this: its animation clock is fixed within a frame and a scroll offset is a paint property, so N writes with nothing dirty are zero layouts. How a scroll write keeps the metrics current without a pass is in [scroll writes](scroll.md#scroll-writes-70).

### What the pass reuses

The pass uses the retained subtrees the last presented frame recorded (`RetainedPhase::Layout`, and `LayoutPaint` for a hole). It skips them, publishes their bounds from the tape with `tape::write_in_layout`, builds the spine and what moved, records no frame and takes nothing from the rendered frame, so the draw after it still replays. What it builds it leaves a layout record of (below). A write followed by a read costs the layout and prepaint of the page and the build of the spine, not a build of the page: `write-then-read` is 1.6 ms against 6.7 ms on the 1000-element page of `draws-vs-presents.perf.test.tsx`, one move per frame.

The pass counts as a frame for the deltas (`Retain::unbuilt`), or a hover that a read consumed would stay stuck.

A read on a dirty window still builds the spine and lays out and prepaints the page. Only `paint_if_dirty` inside dispatch builds every subtree. After a write that drives only paint-only properties a read does nothing at all (next section).

The test renderer draws a dirty window inline whenever effects flush, which hides every pass. `setInlineDraws(false)` stops that and `drawFrame()` ends a frame the way the display link does. `getLayoutPassCount()` counts the passes and `getPaintedFrameCount()` the real paints.

## Writes that do not make the next read run a pass (#47)

A script that read a rect on every frame after a motion value moved something paid about 6 ms of layout pass at 3000 nodes for a change that cannot move a box. Chrome runs no layout for it.

A write is classified when the retained tree takes it. `RetainedTree::take_dirty` says `Clean`, `Paint` or `Layout`:

- `Paint` is a batch whose only changes are style changes by keys of `AnimProp::paints_only`, the one list of what cannot move a box: `opacity`, `boxShadow`, `color`, `backgroundColor`, the four `border*Color`, `outlineColor`, `textDecorationColor`, `scrollbarColor` and `selectionColor`; plus the `borderColor` shorthand (four colours and nothing else). `StyleDesc::differs_only_in_paint` copies those fields over a clone of the old style and compares the whole. A field that is not listed, a state style (`hover`), a `@container` block and a custom property make the batch `Layout`. A universal layer that only changes these is `Paint` too.
- Left out of the list on purpose: `border`, `outline`, `outlineWidth` and `outlineOffset` (widths), `filter` (a JS change of it; its animation is paint only), `mask*`, `clipPath` and `transition` (a stacking context, a clip, a motion), and the `*Color` of anything inside `hover` and the like.
- A motion value write is paint-only when nothing a layout reads is driven by the value (`MotionValueStore::writes_paint_only`). A value that a transform or a follower computes a width from, a drag offset and an inset are layout, as is every JS commit, hover, scroll and resize.

A paint-only write notifies with zed's `App::notify_paint_only` (`invalidate_after_mutation`, and the test renderer's `UNFLUSHED_MUTATIONS`, which holds the strongest kind). It invalidates as `notify` does and keeps the window's layout current when it was current before, so a bounds read or a scroll write before the frame lays out nothing: the invalidator records the `update_count` at which a draw or layout pass began, and `draw_if_dirty` returns false while the count has not moved past it. Any other notify, `set_dirty` or refresh moves the count, and the next read runs the pass. The frame after the write still draws and builds the changed element. `opacity` crossing 1 makes or drops an effect group, which only paints and stacks, so it is still `Paint`. `boxShadow` and the outline reach the culling outset (`layout/cull.rs`), but that is worked out in the build from the style and gpui's painted extent is made of boxes, so a stale extent is never read.

Scroll writes have their own notification, `App::notify_scroll_only`, and a write that moves nothing does nothing: see [scroll writes](scroll.md#scroll-writes-70). A bounds read after a scroll write still lays out, because the children moved with the offset.

## What a forced read costs (#83)

A scroll write or a bounds read after any mutation, a colour included, used to run a layout-only pass over the whole retained tree: 0.46 ms at 1k elements and 3.5 ms at 8k. Chrome lays out nothing for a paint-only change and the dirty chain for a layout one. The read now costs what changed.

**Layout counters.** `getLayoutCounters().nodesLaidOut` and `nodesSized` are the cache misses of taffy's `compute_cached_layout` by run mode (`TaffyTree::layout_runs`, `size_runs`). They are two counters because a parent sizes a child before it places it, and `measures` already names the calls of a measure function. A hidden node (`display: none`) is in neither. Changing the height of one leaf at depth d lays out d + 1 nodes and sizes d, whatever the fan-out. The same read in a list of 8000 elements lays out 7, as in a list of 100. Relayout boundaries, which keep the dirty chain short, are in [layout](layout.md#relayout-boundaries).

**Link resolution starts from the relations.** `accessibility::links::compute` used to walk every entry of `tree.elements` (`display: none` subtrees included) on every layout pass after any mutation: 8 to 11% of a warm forced pass at 8 to 10k elements, whatever the accessibility state. It now starts from `RelationRegistry` (labels, elements with an `aria-*` id reference, elements by DOM `id`) and is worked out again only when something it reads changed: a relation or `htmlFor` prop, an `id` or `role` that is named or on a label, text under a label or a named element, structure while a source exists. A tree with neither label nor reference reads none, whatever it holds. `getLayoutCounters().relationVisits` (test renderer) counts the elements it read since the tree was made.

### A layout-only pass leaves a layout record

A layout-only pass could skip a retained subtree only with the painted recording of a presented frame. On a tree that had not been presented since it changed (a page that mounts with a `scrollTop` write or a bounds read after each step and no frame between; FF mounts 11 lists that way) every pass built every element from the JS tree and threw it away: about 28 ms a pass at 5000 elements, 5 us per element against 0.3 warm.

- **The record.** zed's `LayoutRecord` on `RetainedState` sits next to the painted `Recorded` and never touches it. It holds the gpuix token, the engine and root of the build, the entities it read, the `ReplayKey` and the layout generation of the root after prepaint, `rendered_serial` when it was made, and a flag the last publication of the build sets. The next layout-only pass skips with it (`RetainedLayout::SkippedLaidOut`) under the conditions of a recording (same token, no notified entity, node alive, same engine, `shapes_layout_like`). When the generation or the place differs it puts the build on the nodes it has (`SkipBasis::LaidOut`), and it republishes with `RetainedPhase::LayoutRecorded`. A pass that is abandoned, or whose prepaint a `List` rolls back, never runs the last publication, so its records are not skipped with.
- **A draw ignores layout records.** It ends the records it visits (`rendered_serial` moves; a draw that hits drops the record, a draw that builds makes the state anew), builds what it has no painted recording of and records that. The exception is content a read forced inside a skipped `content-visibility` host (below).
- **Not recorded:** a prepaint that did anything a skip cannot repeat (`Effects::reasons`, as for a painted recording, but not lifts: a pass that only lays out paints nothing, so where a subtree's `position: relative` boxes went in the stacking context around it is not repeated, and the publications of the lifted content are in the subtree's own tape; `finish_layout_recording` leaves `NonReusable::Lift` out), a subtree that published without an `on_replay` listener, and one that holds a subtree skipped from a presented frame (`window.retained.layout_painted_skips`: its tape is a painted one, which cannot nest into a layout tape without corrupting `tape::PARENTS`).
- **The tape.** `Tape::laid_out` is a tape of two lists: the prepaint writes, and the writes of the publications the prepaint queued (`Taped` queues one publication before and one after its child prepaints, which run in order and bracket the `Recorder` of the paint list). It is kept in `TapeStore::laid_out`, not `tapes`, and its lists carry `tape::LAID_OUT` in the serial, so `automation::Stored::laid_out` holds the boxes it wrote beside `recorded`. A pass that lays out can neither forget the box of the recording a draw replays nor be forgotten by one. Nested subtrees nest into it as into a painted tape.
- **A refresh and a reference pass end records.** `Window::refresh` leaves `refreshing` set until a frame is drawn, which stops a painted recording from being skipped; a layout record made after the last refresh is skipped with (`refresh_epoch`), one made before it is not. A verified pass is followed by a pass that builds every subtree inline, whose writes go to the lists of the roots around them. A layout record made before such a pass (`reference_passes`) is not skipped with after it, since the box a root's tape holds is no longer the last one written.
- **An `<svg>` no frame has painted does not exclude its subtree.** Its box is its style and its document, both in the key. The raster state (`retain_state` is `None` until a paint shows it) only matters to a pass that paints, which still excludes it. FF's command menu has 130 icons, 315 of the 460 elements a steady mount pass built.

### A layout-only pass wraps what it builds

The planner used to wrap a node only in a pass that paints (`Node::records` had `!layout_only`). The first build of a cold or changed subtree in a layout-only pass ran inline, outside any gpui `Retained`, and left no layout record: the second pass wrapped it and built it again, and only the third skipped. A node built in a layout-only pass is now wrapped with the token `finish_session` records for it, gpui leaves the layout record under that key, and the next layout-only pass skips it. `Plan::recorded` (the patch preview) and `begin_unit` still ignore a layout-only pass. A cold tree is built once, in its first pass: a page of 5500 elements that mounts its list and writes `scrollTop` 11 times with no frame builds 5502, 14, then 13 elements a round (the changed entry and the spine from the second pass on), where it was 5500, 5500, then 13.

Four things refused the second pass at first. Don't undo any of them:

- **The overscan.** The pass that wraps the entries of a list laid out empty finds no scroller (`Scroller::of`), so it records them to stay where they are. The pass after finds the scroller and gives the skip an overscan, which gpui refused (`ReplayKey`: content mask and culling differ). A skip in a layout-only pass therefore uses the overscan its record was wrapped with (`Node::wrapped`, `Record::wrapped`; 124 elements built before).
- **`<svg>` icons.** The icons a pass created were new ids to the delta of the next (`seen.customs` is committed before the build), so the 500 icons of the page made the entries they are in the spine (2582 of 6002 elements). The build tells the planner the state it saw (`Retain::custom_built`), and a paint that moves it is a change as before.
- **A scroll handle seen for the first time** was taken as scrolled, which gave the content under it no layout record, so a scroller that appears in the same pass as its content had the content built whole twice more (152, 152, 152, then 12 for a scroller of 15 entries). A handle that a frame first finds at its origin, in a pass that only lays out or a frame that paints, is not scrolled: the content is built once (167, then 13) and recorded to be moved by the scroller, so its first scroll puts it elsewhere (`Scroller::of`). A scroller first found away from its origin is scrolled, and its content is built again where it is.
- **A record wrapped to be moved by a scroller** that no longer moves it is built again, in a painted frame (`Kept::Unmoved`, for example an `overflow: scroll` box whose content does not overflow). gpui keeps the overscan and relocation handles of such a recording, which a build there has none of (a verified frame showed text bounds the build lacked).

### Consecutive reads share one pass

Every read of an element inside a skipped `content-visibility` subtree used to run a layout pass of its own (and one before it, for a dirty window): ten reads of the children of one skipped entry were ten forced passes with nothing changed between them. Chrome keeps the forced layout of a locked subtree clean until something dirties it, so later reads cost nothing.

`read_after_layout` leaves in `Relevance` (`ForcedRead`) the set of skipped ancestors it forced, the window's `gpui::LayoutStamp` (read after its trailing invalidation so that invalidation is not a change), where each forced host stood (`HostPlace`), and three clocks: the instant it sampled (`timed`), the layout animations running (`LayoutRuns`) and the transform writes (`TransformWrites`). The stamp is `LayoutStamp { layout_invalidations, animation_frames, boxes, nested_boxes }`:

- `layout_invalidations` is the invalidator's count of the invalidations not declared paint-only (`notify`, scroll-only ones included, a resize, a mutation that can move a box), from `Window::layout_stamp`. The frame of a running animation is not in it.
- `animation_frames` counts those frames. A running animation requests a frame, which stales the layout as an invalidation does, so it has a counter of its own: a stamp read after an animated frame can tell the boxes that moved from an invalidation.
- `boxes` is the window engine's count of the boxes laid out to another place or size. It is taffy's `TaffyTree::box_generation`, bumped by `set_unrounded_layout` when the stored layout of a node differs in location, size, border, padding or scrollbar size. Content size and order do not count: the content size of a host flips each time its children are parked and given back. `layout_generation` keeps leaving location out for gpui's `ExtentStamp`. It is one counter for the tree and is never reset.
- `nested_boxes` counts the same for the nested engine of an atomic inline (`Window::with_layout_engine` notes a box that moved while it ran), so a box that moves only there is seen.

A read below skipped content shares the pass when the invalidations are equal and the outermost skipped ancestor of the element is where it was: its `HostPlace` keeps `Window::box_stamp` of the host's layout node, the greatest `box_changed_at` over the node and its ancestors in the window's engine, and the transform it was reported through. A box that moves elsewhere (a sibling subtree that grows in a layout animation) and the frames that move none do not end the share. Only the outermost host is asked: a skipped host inside another is parked while the frames skip the outer one, and the outer is where all the content below is placed from. A host the window engine does not hold (an atomic inline's) or that no pass prepainted has no stamp, and the share asks the window-wide `boxes` and `nested_boxes`. A read of an element outside any skipped content has no host to ask and needs the whole stamp to be the same.

A read while those hold skips the layout it would run first and the forced pass when every skipped ancestor of its element is in the set (an element outside any skipped subtree has none), and reads the boxes as they stand. One that needs an ancestor outside the set forces the union with the set in one pass, so the boxes read before are those of the same pass. `getScrollMetrics` shares the same way.

Frames that come between do not write the forced content, so the read that shares the pass takes its boxes and scroll state as the pass left them. `WindowBounds::keep` notes the frame the pass wrote and the replays it put back (`live`); `get_kept` falls back to them for an element no later frame wrote (`automation::reading_kept`, only for an element with skipped ancestors); the purge keeps what they need; and `renderer::keep_scroll_state` keeps `SCROLL_HANDLES` and `VIRTUAL_LIST_STATES`, which every build rebuilds without the scrollers in skipped content. A read of a built element is of what the frame published, as it always was.

What ends the share:

- a mutation or any other invalidation that can move a box: a style write, a scroll write, a resize. A paint-only one, a colour or an opacity, does not, as Chrome's layout stays clean for it, unless it writes a transform (below);
- a frame in which the box of the outermost skipped ancestor, or of one above it, moved or changed size. A box that moved elsewhere, in a layout animation that has nothing to do with the host, does not, and neither does a painted frame that moved none;
- a frame in which an element on the chain of the read (the target and what is above it) started or stopped running an animation that can change its layout (`LayoutRuns`, an inherited property such as `fontSize`): it reflows the skipped content without moving a box, which no stamp sees;
- a transform written on the chain of the read (below), or a frame that changed the transform a host is reported through;
- a pass that built something running (below), once the instant it sampled is not the instant a new pass would sample;
- a layout pass of anything else that moves a box. `getBuiltElementBounds`, which runs a pass for a dirty window, does not end it by itself.

What a frame or a pass can change without an invalidation or a box, read through for the share: element offsets (a scroll write, a wheel or a drag, a smooth scroll's frame request and a clamp all invalidate or move a box; anchoring moves an offset only for a box that moved), layout-record translations and relocations (the delta is the move of a box or of an offset), virtual-list rows (`layout_as_root_unsnapped` lays them out in the window's engine, so a row that changes size is a box change), text re-measure and `restore_placed_measures` (they put the measure's state back for the size already placed), the window's size and scale (a refresh, and every box changes) and motion values written paint-only (nothing a bound reads). The content a read forced is not built by a frame, so nothing moves inside it.

### A read after a write to a transform

A CSS transform moves a box without a layout pass, and `getBoundingClientRect` adds the transforms around the box on top of the layout box ([geometry](paint-and-transforms.md#geometry)). The stamp counts layout boxes, which a transform does not change, and a paint-only write to a transform leaves the layout current, so the boxes a pass captured (each with the matrix that carries it to the window, `to_window`) predate the write. Chrome answers every such read with the transform written, in skipped content and out of it, in the same task or after frames, and so does the fork:

- `StyleDesc::touches_transform` says a style change reaches `transform`, `translate`, `rotate`, `scale`, the origin, one of Motion's transform keys (its depth keys and its `transform` target included), `perspective`, `perspectiveOrigin`, `transformStyle` or a custom property (the transform properties read `var()`, and a descendant inherits it); `assign_style`, on a change that is otherwise paint-only, notes it for the element (`Relevance::note_transform_write`), and so does a paint-only write of a motion value that a transform key may be bound to (for any element: `note_transform_write_anywhere`). `TransformWrites` keeps a clock that moves with each write, the clock at the last write to each element, and the clock when the window last built its elements, which captures their boxes.
- A read whose element or an ancestor was written after the last capture runs `Window::draw_for_transforms`: it lays out and prepaints once more although the layout is current, and the boxes are captured again. It is a pass for a visible element too, so a read right after a transform write costs one pass and the next reads share it.
- A write to the element read or above it ends the share of a forced pass, since the boxes inside skipped content are not built by the frames. A write to an element that is not on that chain does not. A frame that moves a transform the host is reported through (a transform animation on the host or above it) ends it as well, by the `to_window` of its `HostPlace`.

A transition on a transform starts a frame after the write, where Chrome starts it at the style recalculation (see [deviations](deviations.md#motion)).

## Reads inside skipped content (#88)

A forced read inside `content-visibility` skipped content cost two layout passes after a change, built the content from scratch every time a draw had come between two reads, and told the observers the content was gone. What a read does there, and why each part is as it is:

### Forcing the skipped ancestors

A read of geometry forces the skipped ancestors: `getBoundingClientRect`, `getElementBounds` and `getScrollMetrics`, in both renderers (`renderer::read_after_layout`; Chrome's `DisplayLockUtilities::ScopedForcedUpdate`). The skipped strict ancestors of the element (`content_visibility::skipped_ancestors`: those skipped as the last build did or as the next would, `hidden` or `auto`, outermost first; the element's own box needs no forcing) are put in `Relevance::force` before the layout the read always does. The window is invalidated and a layout-only pass runs, which is the one pass the read costs:

- `skips` answers no for a forced element, so its content is built and laid out in the box it keeps (`contains_size`: the size containment and the intrinsic size stay, as in Chrome, where the locked element keeps its size while its subtree is laid out), and its boxes are published;
- the read takes them, the set is cleared and the window invalidated again, so the next painted frame skips the content as before. The reads that follow share the pass (above);
- forced elements are a source of the frame (`Relevance::pending`) and part of the key of the element, so the roots above them are built and the ones beside them are replayed;
- a layout-only pass records no frame, which is why the frame after finds the painted records of the skipped build. It leaves layout records of what it builds, and they outlast the draws that skip the content (below).

The pass leaves no trace. `built` and `remember` ignore a forced element: its state, its notified state and its remembered size are not touched. `answer` is not asked. What runs below it is sampled and put back ([next section](#animations-in-forced-content)), so no `animationstart` fires for a loop that is never shown (a run the pass makes is told after the reveal, below). A read of an element outside any skipped subtree costs the walk up its ancestors and nothing else.

The test renderer's `getBuiltElementBounds` is the old read: the box of the last layout, null for what is not built, which is how tests tell that the content of an element is skipped.

Observers on an element below a skipped one do not gather it: see [observers below skipped content](observers-and-content-visibility.md#observers-below-skipped-content).

### Animations in forced content

Chrome's read styles the element, so a CSS animation, a native `motion` or an animated motion value below a skipped host is in the boxes it answers, at its current time, `hidden` or `auto`. `animate_style` resolves an element that an ancestor forces for its values, with the clocks off: it takes a rewind point of the element's CSS animation and transition state first (`rewind_point` and `rewind` in `css_animation.rs` and `css_transition.rs`: the runs and their clocks, the queued events and API events, the wake flags, the transition state) and puts it back after the build. What the element already ran does not move on, so a read ticks nothing and queues no event for it, and the frames after the reads tick as many dormant times as frames without them.

- A native `motion` and a motion value bound below the host are sampled at the instant of the pass in the same way.
- **What the pass makes stays and runs.** A CSS animation the element had no run of, and a transition the style change in skipped content starts, is made at the clock of the read, as Chrome creates it when the element is styled. It is pending, starts at the next frame, goes on with the clock while the content skips and is the same object (`getAnimations()`, `getKeyframes()`) for every later read and after the reveal. `CssAnimations::hold` and `CssTransitions::hold` keep such an element on time through the dormant tick without a build (`Beat::Held`: a play starts, the DOM is told nothing) until a build that is not forced releases it (`release`). The DOM hears of an animation's starts, iterations and ends after the reveal; a transition tells `transitionrun` and `transitionstart` at the read and `transitionend` at the reveal.
- **What a read styles.** A read of an element in content gpuix never built (skipped from load, or given an animation while skipped) styles every never-rendered skipped host around it, not only the element: its siblings and ancestors up to the host get their runs too, whatever the property read (`getAnimations()` of the element, its rect, an unanimated style). `getAnimations()` of an element inside skipped content forces its hosts like a geometry read; `getAnimations({ subtree })` and `document.getAnimations()` do not, and list only what a direct read made. Content nobody reads gets its runs at the reveal.
- `Retain::skip_content` drops the records of a forced element that runs a CSS animation, and of the elements above it up to the host, since they were sampled at the instant of the read.
- The build is not dynamic and not an effect group for the frames that skip the content, and its measurement is not kept.

**A pass that built something running is the answer of one instant.** When the pass built an element with an animation, a transition, a motion or a bound motion value, its boxes are those of the instant it sampled, and the frames since skipped the content: a read at another instant is not answered by them. `ForcedRead::timed` is that instant (`Option<Instant>`, not a flag), and a read shares the pass only while it equals the `frame_instant` a new pass would sample, which `read_after_layout` takes from the view. Ten reads in one task beside a running loop are one pass; a frame between reads makes the next read another pass, with the moved value, which the reads after it share.

### The first read after a change is one pass

Which ancestors skip is read from the value each element was last built with, which is stale for the pass that lays the change out: an ancestor the change turned `hidden`, or inserted. It cost two passes, because the pass that laid the change out had to come first. Now the ancestors that `skipped_ancestors` finds are forced before the pass, and every strict ancestor of the element is registered with it (`Relevance::force_for_read`, `ancestors_of`). One whose style says it skips and whose build, in that pass, resolves it to a skipping one (`contains_size`: `hidden`, or an `auto` that is not near) is forced as it is built (`Relevance::join_read`, from `build_host_container`, before `skips`) and joins the forced set, exactly as if it had been forced before the pass.

Its key is the forced one (`Some(8)`) from the planner on (`joins_read`), or the pass would leave a layout record, made with the content built, under the key of a frame's. An ancestor that does not contain size keeps its key. After the pass the chain is dropped and the ancestors that still skip (`skipped_ancestors` with the fresh values) are looked up in the forced set; a pass is run again only if one is missing. The registration leaves no case of that except a `contentVisibility` that a state style sets (`hover`), which the declared value does not show.

### The layout of forced content is kept across draws

A forced read inside `content-visibility: hidden` content builds it in a layout-only pass, and the next draw threw all of it away: the host was built with no children, `release_unused_element_states` dropped the states, `collect_garbage` freed the detached layout nodes, a draw moved `rendered_serial` so no layout record was current, and `skip_content` dropped every Retain record below the host. The next read after any draw built it again from scratch. A read of a line in a hidden element of 300 cards of 3 lines (1203 elements) after a paint-only write and a draw built 1203 elements in 6 to 27 ms each time, and Chrome keeps a locked subtree's layout.

`build_host_container` now calls `InteractiveElement::locked_content(skipped)` on the host of every element that `contains_size` (`skipped` is whether this build skips; a forced host is built with its children and `skipped: false`). This is zed's half: the lock keeps the element states, the layout nodes (parked under the host while it skips) and the layout records the content left. A layout record made under a lock with no entity read is current in the next pass that forces the content, however many draws came between.

The planner's half:

- `Retain::forced_host` marks the node of a forced host. A node built inside one (or in a late build whose `FrameEnv::forced` says it is) is `Node::under_forced` and its record `Record::forced`.
- `skip_content` keeps the forced records, still dropping `dynamic`, `dormant`, `unbuilt` and `woken` ones so no clock runs and no spine is held, and drops the others, and any record in `deltas.spine`.
- `commit_deltas` drops the record of every spine id that has a skipping host above it (`forget_changed_under_skipped`; the spine is closed under parent, so the path up to the host goes). Don't remove this: a pointer, a focus, a motion value or a measurement that changed under the host while it skips would be replayed stale by the pass that forces it.
- A host that shows builds the content whole: a forced host's key is `Some(8)` and a node's shape includes its parent's, so the forced records fail with `Kept::Shape`.
- The tapes behind `LayoutRecorded` are kept by `TapeStore::laid_out`, which a draw does not touch. The boxes a layout record holds survive `WindowBounds::reset`'s purge until the sweep of destroyed elements removes them (`automation::retain_bounds`); a page of more than 4096 boxes had a read after a draw return null for an element in skipped content before that.

A read inside a hidden element after a draw that changed something is one layout pass that builds the host and the spine: 4 elements and 8 layout skips for the hidden element of 8 cards of the scene `firstReadKept` (36 to build it from scratch). The 300-card probe builds 3 elements in 0.5 to 0.8 ms (1203 in 6 to 27 ms). A read after a draw that moved no box is not a pass at all, as the shared pass above.

### A read after a painted frame shares the forced pass (#98)

A read of an element in skipped content after a paint-only write and a drawn frame was one layout pass (3.2 ms median for a line in a hidden element of 300 cards of 3 lines, with a title and a tint beside it), where Chrome needs none. With the `boxes` count in the stamp it is none: 0 passes and under 0.01 ms. The mechanism is in "Consecutive reads share one pass" above.

### A layout record is skipped at a translated place

A retained subtree that a change elsewhere only moves (a box before it grows, a card above it gets a line) was refused by `prepaint_skipped_laid_out` and built again where it is, where Chrome lays out nothing for it. The read after a line grew in `firstReadKeptInside` built 28 elements: the card, the five after it, the host and the page. A record is now skipped where the change moved it, not only where it was made.

The record keeps the key of its build, and each skip works out its delta from that, not from the skip before, so a subtree that is moved back is at its own place with no drift. The place is a translation when:

- the box, the origin the layout engine gave it and the content mask around it moved by one whole number of device pixels (the engine's origin to within the 1/256 of a device pixel the phase is compared to);
- the size, the phase of the origin, the scroll offset around it and everything else the subtree reads are equal;
- the scale factor is a power of two and there is no exact clip.

Otherwise the place is not one, and the subtree is built again where it is. The check is zed's `ReplayKey::translation`.

**A mask that did not move with the subtree** (the cards of a scroller viewport, moved by a box above that grows) leaves what is culled inside the same only when culling cannot decide differently, because it depends on where the subtree is in the mask. `Window::lies_outside_the_mask` notes the rects it compares with the mask (the inflated box, and the inflated painted extent when it gets that far, also while an element holds the capture) into the layout recording open around it. A subtree skipped inside the build adds its own, moved by its delta. The union (`LayoutOutcome::cull_reach`) is kept in `LayoutReplay` with the key, and a culled box is told so (`LaidOut::culled`, read for dormancy). A key whose mask did not move with the subtree is accepted when nothing was tested, or when the union lies strictly inside the mask before and after the move (by the 1/256 device pixel; strictly, as the mask of a clip inside that misses the one around is empty at a corner of it). One that crosses an edge, or was culled, is built again where it is, and a culled subtree root keeps its rule (it is under the empty mask). The corner radii are not asked of the union: culling compares the bounds only, and equal radii are still required. No decision is recomputed per candidate. What culling compares includes the outset of the candidate, 15 px beyond a text, so a card has to be that far inside the viewport: a card flush with it is built.

**Blockers.** The positioned frame around is not asked, as for a scroll relocation: a box placed by a frame outside the subtree is a blocker. What stays in the way is kept when the record is made (`LayoutOutcome::blockers`): sticky, positioned capture such as a canvas or a scroll anchor, a scroller that is scrolled, an input handler, a box that escapes to a frame outside the subtree, a scale that is not a power of two, and a publication whose owner does not take the translation. A subtree skipped inside the build of another hands its blockers to it.

**What the build holds outside the frame** (`Window::note_relocated`: text bounds, scroll handle bounds and the bounds of its children) is a `HandleList` per record, held by the list of the build around it as the tapes are. A skip puts it where the delta says (it knows where it was last put). The hook of the owner is given the delta (`RetainedPhase::LayoutRecorded`), and `TapeStore::replay_laid_out` replays the tape with it, which moves what is nested too.

What it buys, counted with zed's `layout_translations` (`RetainedCounters`) and the element counts below:

- `firstReadKept` step 2 (the hidden element is moved by a box above it) reads in 4 elements with 8 skips where it built 36.
- `firstReadKeptInside` after a line grew builds 8 with 7 skips where it built 28.
- A page of cards with text and a scroller (`overflow: hidden`) moved by a box above builds the page and the host (3 elements, 6 skips) where it built 33, and the boxes and scroll metrics are those of a page built where it is.
- Cards of a scroller viewport that clips (the mask they are under does not move), moved by a box above it: 8 cards of a box and a text, the box above 30 to 50 grew. 7 are put where they are (the five inside the viewport, and the two outside it that are culled both times), the sixth reaches the edge and is built: 6 elements built and 7 translations where it was 21 built and 2 translations (the culled two). The boxes are those of a page built where it is.
- A card with a scroller that was drawn since the scroller appeared is skipped like any other: a draw that finds a new handle at its origin does not take it as a change, so the record of what is around it stays. The first move of the page of cards of the `content-visibility-auto` test builds 3 elements and skips the 6 cards, where it built 21. A frame that replays a record skips nothing new, so `clip-cull.test.tsx` counts what the frames since the mount skipped, not the one frame after.

## Limits

- **A scroller the user scrolls (`overflow: scroll`) is never retained, nor the card around it.** A card with such a scroller is built, not skipped at a translated place. See the exclusions in [retention](retention.md#eligibility-and-exclusions).
- **A subtree under a content mask that did not move with it is built when it is moved and something culled inside it is near the mask's edge.** A layout record is skipped at a translated place under such a mask only when every rect culling tested inside it lies strictly inside the mask before and after. A card across the edge of its scroller's viewport, or one whose child is within its cull outset and a pixel of it, is laid out again. The union is of what was tested when the record was made, not recomputed per candidate, so a subtree with one child near the edge is built whole.
- **A read right after a write to a transform costs a pass**, also for an element that is not in skipped content, where the boxes used to be the stale ones; the reads after it share the pass.
- **A `contentVisibility` set by a state style** (`hover`) is not shown by the declared value, so the one-pass registration cannot see it. The read runs a second pass if an ancestor that still skips is missing from the forced set.

Where a retained frame differs from a full build is in [retention](retention.md#where-a-frame-differs-from-a-full-build).
