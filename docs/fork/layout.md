# Layout

How boxes are placed: positioning and stacking, grid, tables, container queries, shorthands and lengths, intrinsic widths, the layout engine that persists across frames (and the vendored taffy it runs on), relayout boundaries, layout containment and the 1/64 px unit that boxes are measured and read back in. Text layout is in [text.md](text.md), scrolling in [scroll.md](scroll.md).

## Positioning

`position` defaults to `static`. `absolute` resolves against the nearest positioned ancestor (zed `taffy/containing_block.rs`) and `fixed` against the window. `sticky` stays inside its nearest scroll container's scrollport less that container's padding on every side (Chrome's constraining rectangle, zed `sticky.rs`; percentage insets are of it), inset by its own insets and never out of its parent's content box.

Also supported: `aspectRatio` (an `<img>` is sized like a replaced element), `order`, `row-reverse` / `column-reverse`, `margin: "auto"`, full CSS grid syntax (tracks, placement, areas, auto flow; zed `grid_template.rs`), `display: none` and `display: contents`. An empty or whitespace text node produces no box and no `gap` slot (the inline builder in [text.md](text.md) owns this rule). `inline-block`, `inline-flex`, `inline-grid` and `inline-table` are atomic inlines, described in [text.md](text.md).

Animatable properties take the dimension margins and insets of this area and its aspect ratio type.

**Anchored popups** (a gpuix component, not DOM) place like floating-ui, and a deferred one is sized as a portal into `body` (`width: fit-content(<window width>)`, since taffy would size an absolute child in the box of its parent, the trigger's wrapper): `align="center"` is offset once, flip clears the trigger and re-flips live, `onPlacement` reports the available size and the anchor size, and `anchor-size()` is supported.

### Clip and scroll follow the containing block (C2)

An absolute box is clipped and scrolled only by its containing block and what is outside it, a fixed one by the window alone. A static `overflow` ancestor does not clip it.

Content masks and element offsets are inherited down the paint tree, so a positioned `Div` (also `<anchored>` and a layout root such as a list row) records the mask and offset its children see on a `Window` stack. `Element::escapes_to` makes `Drawable` prepaint and paint an absolute (`AbsoluteInAncestor`) box under the nearest recorded frame (`Window::with_replaced_content_mask`, which replaces the mask instead of intersecting) and a fixed one under the viewport with no offset. Hitboxes take the mask at insert time, so hit testing follows; deferred draws carry the frame. gpuix's `IntersectionObserver`, `scrollIntoView`, key scrolling and `getElementsAt` use `layout::containing_block` instead of `parent`. Zed's parent-relative `Position::Absolute` is unchanged.

A `position` that only a hover or focus style sets escapes the clips too. `build_element` leaves a `Resolved` record per element in `RetainedTree::resolved` (`resolved_style.rs`), made from the style it was built with, and every walk over the retained tree (`getElementsAt`, `IntersectionObserver`, `scrollIntoView`, key scrolling) reads it. A `position`, `overflow`, `zIndex`, `opacity`, `visibility` or `pointerEvents` set by a state, an `@container` block, a transition, an animation or a motion value therefore counts. An effect group widens its composite mask to an escaped box (`Scene::widen_groups`).

`build_element` resolves a style in a fixed order, and each stage reads the one before: the base style with the `@container` blocks that the containers above select folded in (`layout/container.rs`); the pointer, focus and form-control state layers ([Layer order](events-and-input.md#layer-order), `resolve_pointer_states`; `RetainedElement::control_disabled` holds the disabled state, and `formControl` marks a `div` that stands in for a control); CSS transitions; `motion` `animate`; motion values; CSS animations, which skip a property a transition is running on and advance first, inside `resolve_declared_style`, so a property one drives starts no transition; then the `display: contents` overlay and `anchor-size()`. A stage that changes a style copies it first, because `RetainedElement.style` is a shared `Arc<StyleDesc>`. A walk over the retained tree reads the `Resolved` record through `RetainedTree::resolved_of`, `position_of`, `overflow_of` or `display_of`, never `element.style`, which is only the declared style and the answer for an element that was never built.

The `Resolved` record is written on each build and kept by a replay, which is right because nothing it is made from changed. A destroyed element forgets its record, and so does a `display: none` build. It is made from the focus-folded style, and the focus variants are on the spine (`:focus-within`, `:focus-visible`, the keyboard flag). The gpui element must say the same lift as the record: `apply_focus_variants` decides it again from the folded style (`stacking::apply_folded_lift`), because a variant applied on its own could not see the base `position` or the item flag. `Retain::digest` of a host includes the `Resolved` record, so a verified build sees a stale one (see [retention.md](retention.md)).

### Stacking contexts and `zIndex` (C3)

Positioned elements paint and hit-test above in-flow ones, and `zIndex` orders them across stacking contexts as CSS 2 Appendix E: a descendant can reach over its parent's later sibling. `getElementsAt` lists elements in paint order.

gpuix flags the `Div`s that create a context: the window root, a positioned element with a `zIndex`, `fixed`, `sticky`, every effect group (`opacity` < 1, `filter`, `backdropFilter`, `maskImage`, `clipPath`), a `transform`, a `perspective` or a declared `transform-style: preserve-3d` (as an effect group; see [paint-and-transforms.md](paint-and-transforms.md)), `<anchored>` content and each virtual-list row. An element whose `opacity` is animated is a context for the whole run, even at 1, as in Chrome (see [patch-frames.md](patch-frames.md)). A flex or grid item takes its `zIndex` without a `position`, and a non-positioned element with `opacity` < 1, a filter, a backdrop filter, a mask or a clip path paints in the `z-index: 0` layer in tree order and forms a context (`Styled::lifted`, `layout/stacking.rs`).

zed (`Div::stacking_context`, `Element::lift_z`, `Window::lift_lists`) takes every positioned descendant out of its parent at prepaint (its hitboxes and its `AnyElement`, leaving an `Empty` placeholder) into the nearest context's list. The context paints them by (z, tree order): negative z after its own background and before its in-flow children, the rest after them, then its scrollbar overlay. Because prepaint runs in place, the dispatch tree, the a11y tree and element state stay in tree order. What changes with lifting:

- Hitboxes are re-inserted in paint order, so a parent hitbox can follow its child. `dom_hit_test` and `ClipIndex` no longer assume otherwise.
- Tab stops are rewritten into document order: `TabStopMap::restore_lifted_order` for lifted elements, `restore_children_order` for children a parent paints in another order (`paint_rank`s, and `Div::document_order` for flex and grid `order`).
- `RetainedTree::elements_at` models the same contexts with the same predicates (`layout/stacking.rs`, also used by `build_element`), so it agrees with paint where it used to list tree order.

Barriers where nothing lifts and the old per-parent `paint_rank` applies: layout roots (`prepaint_at`, `prepaint_as_root`), deferred layers and `visibility: hidden` subtrees. An element that is not a `Div`, `Img`, `Svg`, `List`, `UniformList`, `Canvas` or `Surface` is never lifted, and gpuix elements positioned only for layout (the text wrapper, anchored placement boxes) are `.unlifted()`.

### Tab order is document order whatever `order` does

The builder sorts the children of a flex or grid container by `order` (`plan_children_at`), so the sorted position is not the document position. It hands gpui each child's document index (`Placement`, `build_content`), and `Div::document_order` makes the tab stops they register follow it, with a positive `tabIndex` still first and Shift+Tab walking the same order back. Nested containers, `display: contents` items, anonymous cells and a change of `order` follow the document.

## Box shorthands keep their parts

`padding`, `margin`, `inset` and `borderWidth` take one to four values (`Sides<T>`), `gap` one or two (`Gap`), `paddingBlock` / `paddingInline`, `marginBlock` / `marginInline` and `insetBlock` / `insetInline` one or two (`Pair<T>`: block is top and bottom, inline left and right). `borderBlock` / `borderInline` are `border` strings, and `flex`, `flexFlow`, `placeItems`, `placeContent` and `placeSelf` take the full CSS grammar.

Each is its own `StyleDesc` field holding the parts it expanded to (`css/shorthand.rs`, `logical.rs`, `flex.rs`, `place.rs`), parsed when the style is deserialized. Flattening a shorthand into its longhands there would lose which ones the author wrote, and the state overlay needs that: a state's shorthand resets the base longhands it covers (`drop_shadowed_longhands`), a state's longhand changes only its own. Don't flatten them: a hover state that sets `padding` would stop resetting a base `paddingLeft`.

Consumers read a side through `*_below_longhands()` or `effective_*`, which put the explicit longhand over the shorthand. The later key wins, as in Chrome: the deserializer notes the order of the keys it reads, and a shorthand drops the longhands it covers that were written before it, so the rank (shorthand, logical pair, longhand) gives Chrome's answer for what is left. One table (`css/covers.rs`) says what a shorthand covers, for that and for `drop_shadowed_longhands`. Tests assert Chrome's boxes at rest, in a hover state and along an inline span.

## CSS lengths are linear expressions

Every length field (sizes, margins, insets, padding, gap, `flexBasis`, border and outline widths, `fontSize`, `lineHeight`, shadows, the lengths inside filters, gradients, masks, clip paths and grid tracks) takes a number or a string with `px`, the absolute units, `%`, `em`, `rem`, `vw`, `vh`, `vmin`, `vmax` or `calc()` (`+` and `-` between any of them, `*` and `/` by numbers).

It is parsed once into `LinearLength` (`css/length.rs`) and resolved at apply time with a `LengthContext` carried in `Inherited` next to `ColorContext`. The font size is cascaded during the build (`em` of `fontSize` is the parent's, `rem` the root element's, initial 16px) and the viewport is the window size. A length plus a percentage reaches layout as a taffy calc value (vendored taffy, `DefiniteLength::Calc`) or, for backgrounds and gradient stops, as `LengthPercentage::Calc` / `StopPosition::Calc`. `motion` animates every length, `calc()` and the relative units included, as a px and a percentage part (see [motion.md](motion.md)).

The limits of this grammar are listed in [deviations.md](deviations.md#layout).

## Intrinsic widths are a pre-pass, not taffy

`width`, `minWidth`, `maxWidth` and `flexBasis` take `min-content`, `max-content`, `fit-content` and `fit-content(<length-percentage>)`. taffy 0.13 has no such keywords, so gpui keeps them in a `Style::intrinsic_widths` field (the real width slots stay `auto`). `TaffyLayoutEngine::compute_layout` measures each keyword node, deepest first, as a sub-root with `MinContent` / `MaxContent` available width, then rewrites its taffy style to definite values:

- `fit-content` becomes `auto` with `min-width` and `max-width` set to the content sizes kept between the author's own limits. That is the same as clamping to the content sizes and then to the limits, `min-width` winning.
- A limit in `%` or `calc()` makes those a taffy `Calc` that holds a value between a floor and a ceiling, which layout resolves against the containing block. A cyclic `%` is none while that width is unknown.
- Height keywords are `auto`, as CSS Sizing 3 says of the block axis. As `minWidth` / `maxWidth`, `fit-content` is `min-content` / `max-content`.
- `flexBasis` is measured like a width only along a row or row-reverse flex container's main axis (the parent is looked up where the pre-pass runs, since children are created first) and is `auto` in a column, block or grid. It wins over `width`. Its `fit-content` is `max-content`, because the container's size is not known there, and `fit-content(<limit>)` is the limit clamped between min and max-content for a length.
- In a flex column, the width `fit-content` fits into is the container's content width less the item's own margins, whether it is aligned to a side or stretched. The vendored taffy clamped the space an item gets with the container's margin (`flexbox.rs`), so a column with a negative margin laid its `fit-content` item out as one without, and a margin on the item itself did not narrow it. `leaf.rs` also took a leaf's margin off a second time.

Cost: a keyword node costs one or two extra subtree layouts when it is measured, and nesting multiplies it. The node is measured again only when something changed (its cache is empty, its dirty generation moved since it was resolved, or its keywords came out differently), because the two rewrites and the probe layouts it makes bump the layout generation of what holds it, and a retained root is replayed only while its generation is the one it was recorded under. Without that check a root under a keyword node was built again every idle frame. A measured leaf is always resolved again.

## `display: flow-root`

`display: flow-root` maps to gpui's `Display::FlowRoot`, which taffy lays out as a block that starts a new block formatting context: the margins of its children stay inside it and make it tall, and an empty one does not let its margins through to its neighbours. The style mapping used to drop the value, so the element stayed a plain block and a child's `margin-top: -30px` moved the box.

## A flex row of unknown width is sized by its items

A row whose width is not known (an absolutely positioned box, an `inline-flex`, a `fit-content` width, a column item aligned at the start, a `max-content` grid column) is shrink-to-fit. Blink takes its width from the contributions of its items (`ComputeMinMaxSizeOfRowContainer`, `flex_layout_algorithm.cc`), not from their flex bases, so `flex: 1 1 0` around a 100px box is 100px wide and not 0. taffy's `row_intrinsic_main_size` (`compute/flexbox.rs`) sums them for the `Definite` arm of `determine_container_main_size` and for the row min-content and max-content, in place of the spec's flex-fraction loop, which sized `flex: 1 0 150px` around 100px of content 0 wide.

- **Contribution.** The `width` of an item or its min- or max-content width, kept between its `min-width` and `max-width` (`length_utils.cc`). An item that cannot move (`contribution > base` with no grow, or `contribution < base` with no shrink, with a basis that is a length) contributes its hypothetical main size. A wrapping row counts its items side by side and is at least its largest item wide.
- **Width.** `min(max-content, max(min-content, available))` of those sums when the available space is definite.
- **Lines.** A wrapping row fitted to its items collects its lines again at the width it got, as Blink breaks them at the final width: three `1 1 100px` items around 10px boxes are 30 x 60.
- **Measures are reused.** A row of unknown width in a definite space is also what a column measures its item with for the cross size, so the sums read the content sizes the flex base size and the automatic minimum size already measured (`FlexItem::measured_content_size`) and measure only an item they did not. Measuring every item again laid the list of `forced-layout-incremental` out with 39 nodes where 28 are needed.
- **Percentage basis.** A percentage `flex-basis` of a width that is not known is the content of the item (`FlexItem::is_basis_indefinite`), as it is for a height in a column; it resolves against the fitted width once the row is laid out at it, so `flex: 1 0 50%` with `width: 50px` around 100px of content is 50 wide.

A column is unchanged: its height is the sum of the hypothetical main sizes of its items (see [Layout containment](#layout-containment-of-content-visibility)).

## Tables

**Tables are a table algorithm in taffy, not a grid mapping.** Mapping a table onto grid (`repeat(N, auto)` columns, row groups `display: contents`) would have been a few days of work and would have left out `table-layout: fixed`, `%` column distribution and `border-collapse`. The fork already carries taffy, so `third_party/taffy/src/compute/table/` implements CSS Tables 3 as Chrome lays it out: structure, column widths, row heights, `colSpan` / `rowSpan` distribution, captions, header and footer groups, and cell `vertical-align` on the row baseline. Its tests compare against headless Chrome. gpui carries `Display::Table`, a `TableRole` per node and the table styles; `css/table.rs` parses them. A `display: table` or `table-*` value lays out as a table.

taffy makes a child that is no table part a cell of its own. gpuix does the CSS wrapping instead (anonymous cells and anonymous tables, `layout/table.rs`), so the tree gpui lays out is always well formed. Copied text has a tab between the cells of a row (see the selection order in [text.md](text.md)).

**Heights are shared as Blink shares them**, in `LayoutUnit`s (1/64 device px in taffy), where floats left the row that takes the rest a 64th short. `taffy/compute/table/heights.rs` has the steps by name:

- `distribute_excess_block_size_to_rows` (`DistributeExcessBlockSizeToRows`): percent rows by deficit, the rows a spanning cell starts in, auto rows in proportion, empty rows equally, the rest in proportion; `MulDiv` in raw units, with what the cuts leave to the last row of the step. It serves a cell that spans rows (`Caller::RowSpan`, in Blink's `RowspanCell::operator<` order, no percentage resolves) and a row group with a length (`Caller::Section`).
- `distribute_table_height` (`DistributeTableBlockSizeToSections`): the percent phase by distance from the percentage, then the tbody-auto, tbody-fixed or tbody-percent groups, the remainder to the last; every group that grew shares again over its rows.

Percentages of groups are taken against the groups' height without the spacing around them, a group's rows against that group, the rows' clamped to 100% and the groups' not. What is short is shared out in proportion to it, the rest goes to the rows without a height. `SectionHeight::min_extra` is gone: a group with a length grows its rows when they are measured. A `div` cell has no baseline in Chrome, so tests of these rows use `vertical-align: top` cells.

**`border-collapse` is split three ways.** gpuix resolves which border an edge has at build (CSS 2.1 17.6.2.1, `layout/collapse.rs`, over the slot grid `layout/table_grid.rs` re-derives from taffy's placement). Layout gets Chrome's exact half widths. The table paints each edge once, centred on the grid lines layout recorded and above the cell backgrounds (zed `collapsed_borders.rs`); cells paint no borders. Painting by the recorded lines means that when the two grids disagree nothing is drawn, not a wrong border.

A part of a collapsed table is built after the table, so the table reads its borders from the last pass's record (`ResolvedStyles::borders`) and builds again before the frame is presented when a part was painted with another width or style since (`rebuild_if_borders_moved`). The first pass of a changed width therefore costs a second build. A colour is not read from the record: the table paints the colours its parts are built with in the same frame (`settle_collapsed_borders`, #68), so a `border-color` transition costs no second pass.

In retention (see [retention.md](retention.md)), every part of a collapsed table is `Exclusion::CollapsedTable` (the parts are under `Inherited::table.collapse`), so neither the parts nor the table around them are ever replayed, whatever transitions or animates in a cell. The table itself is the one unit such a page has:

- Paint-only motion on any part makes the table the unit (`Retain::collapsed_table`, `Retain::unit_facts`: the motion of the table and of what is in it, and no exclusion below it but the parts), since it is the table that paints their borders. A tick builds the table alone.
- The parts are never units. A part excluded for another reason (`Retain::exclude` replaces `CollapsedTable` by it), or one that lays out, keeps the table from being one.
- An anonymous table has no element, so `build_plan` marks the element that builds it as holding the table, and that element is the unit. A container over the cap stays whole and is counted `TooLarge`.
- A patched tick still lays the unit out onto its own nodes (one pass, no node made).

**Table styles in motion.** `borderSpacing` blends, and is cut to whole device pixels where it is laid out (gpui `snap_border_spacing_to_device_pixel`: 2.5 is 2px at scale 1 and 2.5px at scale 2, 0.99 counts as 1), as Chrome's `short` does it. An unset `borderSpacing` and the other inherited table styles start a transition from the value they inherit (`motion::Inheritable`, as do an unset `pointerEvents`, `visibility`, `textUnderlineOffset` and a unitless `lineHeight`; a `lineHeight` that is `normal` or a length is no number, so it starts at its target, as in Chrome). `motion` and keyframes take none of the discrete table styles.

## Direction

`Inherited::apply` takes `&mut E` on purpose: it runs on every build level, and a by-value `Div` made the deepest debug test overflow its stack.

`direction` is inherited in `Inherited::direction` and reaches taffy as `Style.direction`, which flex, grid and block already honoured. Tables mirror their columns about the grid (`DetailedTableInfo::column_lines` stay in order from the left), and `layout/collapse.rs` walks the grid in table order and mirrors only what it hands out. `start` and `end` of `textAlign` resolve per element (`css::direction::Inherited`), and the text a paragraph lays out is positioned and hit by its alignment (`TextLayout::position_for_index`, `index_for_position`, `align_offset_at`), so the bounds of a centred or right-aligned span, selection washes and hit tests follow it.

## Container queries

**Container queries are same-frame.** A container's size is known only after layout, and the tree is built from the style that size picks. A lag of one frame (query against the last measured size) was the cheap option and was not taken: a mount or resize that flips a query would show the old style for a frame.

- The build reads the content box the last layout recorded (`ContainerStore`, `layout/container.rs`). Each container's prepaint listener (`Div::on_prepainted_layout`) compares its new box with what the build assumed for the axes something read, and a mismatch calls `Window::request_redraw_before_present`.
- zed's `Window::draw` then drops the pass before paint, as a layout pass is dropped, and builds again, up to `set_max_draw_passes` (4, one per level of containers that flip each other). At the cap the last pass is presented and the window draws once more, so a loop costs a frame per step and never hangs. The classic scrollbar gutter of an `overflow: auto` scroller asks for a pass the same way and shares the cap ([scroll.md](scroll.md#scrollbars)).
- Only the presented pass paints, so bounds, observers, `onLayout`, registries and a11y never see a dropped one. What a build publishes outside the frame therefore has to be idempotent.
- A window that allows more than one pass does not use GPUI's view cache. gpuix never builds cached views, so that costs nothing.

Cost: a steady frame pays one comparison per read container. A flip of 500 containers (4.5k elements, `examples/container-queries.perf.test.tsx`, `bun run test:perf:cq` in `examples/`) takes 1.9 to 2.0 times a steady frame.

**Containment.** `containerType` is size containment in taffy (`contain_inline_size`, `contain_block_size`: the content-based size ignores the content on those axes) plus a formatting context of its own. It is no containing block and no stacking context, as in Chrome. With no `width` in a flex row or an absolute box, a query container is as wide as its padding and border, whatever it holds. `cq` units ride in `LengthContext`. The grammar is `css/container_query.rs`, three-valued, and unknown is false.

**Which element is a container** follows CSS and was checked against Chrome 156 (`container-hosts-oracle.html`):

- One container answers a whole query: the nearest that contains every axis its size features read. `style()` alone asks the parent.
- An element that cannot be size contained (a span that is not atomic, `display: contents`, a table or internal table box) is still the container a query finds, with its size unknown, and a `cq` unit skips it.
- `<img>` and `<svg>` only get the containment (zed `Img` drops the natural size and ratio on the contained axes). `<input>` is untouched, as in Chrome.
- A `<virtual-list>` is a container for its rows. zed `List` runs `on_prepainted_layout` listeners after its rows are built, since they are built in prepaint.
- `--name` keys are custom properties (`css/custom_properties.rs`, collected by the parser in `css/covers.rs`, inherited through `Inherited::custom`), read by `style()` and by the `var()` of the transform properties ([paint-and-transforms.md](paint-and-transforms.md#custom-properties-and-calc)), and nothing else. A value that holds `var()` is computed where it is declared. A change of a custom property alone lays out only while some `@container` rule is in the tree, since a `style()` query may read it; otherwise it is paint.

**Ordering inside a build.** A block is evaluated where the element is built, while hit testing, stacking and observers read the painted style. The `display` a block gives is settled before the paragraph planner and the table role read it (`settle_children`). `order` is settled the same way (`RetainedElement::container_order`, set by `container::settle` and read through `order()`), so a flex or grid parent sorts by the folded order in the frame that lays it out, both when a container shrinks past a query and when it grows back. `display: contents` is the exception for `display`, since the parent splices a child in before it is built.

`display: contents` wrappers hand a container declaration and custom properties to the children spliced out of them (`contents_levels`). The wrapper's style serial is in the child's `contents_key`, so a change in the wrapper is a change in the key of each spliced child. A wrapper that toggles `display: contents` re-tracks the focusable elements below it (`track_focusable_subtree`).

## Baselines

**Text has a first baseline.** A measured leaf reports the first baseline of its first row to taffy (`MeasuredLeaf`), so a `baseline`-aligned table cell, an `inline-table` and flex and grid items with `alignItems: baseline` line up by their text, as in Chrome. Two grid bugs showed up against Chrome and are fixed in the vendored taffy: an item with another `alignSelf` was shifted to the others' baseline, and a grid's baseline was its first item's bottom.

A trimmed text (`textBox`, #66) reports its baselines from the top of its trimmed box: the lines start `trim_top` above that box, and counting from the lines seated a cap-trimmed label in an `inline-grid`, or a flex or grid row, that much too high.

**A scroll container's baseline stays inside its border box.** A box with `overflow` other than `visible` or `clip` on either axis gives its parent a baseline clamped to `[0, BlockSize()]` (`LogicalBoxFragment::FirstBaseline` / `LastBaseline` when `IsScrollContainer()`), wherever a parent reads one off a child fragment: a block, a flex or grid container, a table cell, a line. A 10px block holding a 20px line has the baseline 10, and `margin-top: -30px` on the line (baseline -10) gives 0. Blink also forces the last baseline of an `inline-block`: a block child that scrolls vertically (`ForceInlineBaselineSynthesis`) gives the bottom of its margin box, whatever it holds (`BlockLayoutAlgorithm::PropagateBaselineFromChild`), and an `inline-block` that scrolls itself has no baseline (`BaselineMetrics`), which gpuix already had.

- taffy: `compute_child_layout` (`taffy_tree.rs`) clamps `first_baselines.y` of the output of every node whose `overflow` is not `visible` / `clip` on either axis to `0..size.height`, so block, flex, grid, table and leaf layouts all read the clamped value from a child. The clamp `flexbox.rs` had for a row's baseline-aligned items (`overflow.y` only) is that one now, and a flex column's baseline is clamped too.
- gpuix: an `inline-flex` or `inline-grid` that scrolls keeps its baseline in its border box, and so does a first item that scrolls (`text/atomic.rs`, `Kind::FirstItem { scrolls }`, `kept_in_box`, `in_scrolling_item`). A block child that scrolls vertically, of a parent that lays out blocks, and that ends the content of an `inline-block`, is its last baseline at the bottom of its margin box (`atomic::scroll_block`, `Collected::scroll_blocks`; zed `Window::layout_margin_bottom` reads the margin taffy resolved).

**A table row's descent below the baseline may be negative.** A `<td>` holding a 10px box with a 20px line has its baseline 10px below the bottom of its content. Blink's `RowBaselineTabulator::ProcessCell` (`table_layout_utils.cc`) seeds the descent with the first baseline-aligned cell and only a cell that spans rows seeds it with 0, so that row is 10 high; `measure_rows` (`compute/table/heights.rs`) floored the descent at 0 and made it 20. A cell with children and no baseline takes the bottom of its content edge for it (`FinalizeTableCellLayout`), so an empty `<span>` in a cell counts as a child ([text.md](text.md#inline-boxes)).

**A sized block reports the collapsed top margin of its first child when it is measured.** The shortcut of a block with both sizes known (and the one in `compute_inner` with the height known) returned before it looked at a child, so a flex row, a grid or a table cell measured `<div style="height:10px"><div style="margin-top:-30px">` at 10 and the final layout then put the box at -30; Chrome's is 0. The shortcut returns the margin set of the first in-flow child when the box's margins can collapse with its children's (same formatting context, not a scroll container, no padding or border above). `first_child_top_margin_without_layout` reads the styles up to the first in-flow child, which answers without laying anything out when that child cannot let a margin through (padding or border at the top, a scroll container, a flex, grid or table, no float or clearance), and the children after it are laid out only as long as their top margins collapse (`first_margin_only` in `perform_final_layout_on_in_flow_children`). A box whose first child is a plain block still measures that child.
**Content that ends above the content box is not negative room.** The free space of `align-content` is taken from the height of the in-flow content, which is at least 0: `intrinsic_outer_height` is clamped at 0 before the padding is taken off again, so a cell with 14px of padding and border around a child at -20 had 14px of free space and was pushed down by it.

## The 1/64 px unit

Chrome lays boxes out in `LayoutUnit`s of 1/64 px and snaps only when it paints. gpuix does the same: layout computes in 1/64 of a *device* pixel, painting snaps, and the reads that return a box return layout's own. Text measures in the same unit (see [text.md](text.md)).

### Lengths are cut as `LayoutUnit(float)` is (#65)

- Layout used to round every authored px length to a device pixel (`AbsoluteLength::to_taffy`), so `10.01px` was 10, a `0.4px` box was 0 and `33.3 + 33.3 + 33.4` painted 33, 33 and 33 with a gap. A length is now cut toward zero to 1/64 of a device pixel: `100.4px` is `100.390625`, and `-10.01px` is `-10` at scale 1 and `-10.0078125` at scale 2.
- A `calc()` is cut after it is resolved (`Calc::resolve` in vendored taffy, the one place it is), so `calc(2rem - 0.3px)` is `31.6875`.
- A percentage is cut toward zero to 1/64 device px where taffy turns it into a length (`resolve_percentage` in `util/resolve.rs`, called at every site that resolves one, the table module included), as Blink cuts `basis * pct`: `25%` of 101.296875 is 25.3125, not 25.324219.
- A flex item's share of the free space is rounded to 1/64 device px the way Blink's `ResolveFlexibleLengths` rounds it (`flexbox.rs`). The items are walked from the last, each takes the free space times its fraction of the weights still to come, rounded half away from zero, and the first item takes what is left. Three equal items shrinking are 1098, 1099 and 1099 at scale 1, not three equal thirds. A sum of weights under one no longer takes the gap twice.
- The fixed length of a grid track (and the argument of `fit-content()`) is cut to 1/64 where taffy reads it.
- The edges of a box snap at the end, half up, to the pixel it paints on, for the start and for start plus size. A box with a size never snaps to none (Blink's `SnapSizeToPixel`): 33.3, 33.3 and 33.4 paint 33, 34 and 33.
- A border width is Chrome's "snap as a border width", in layout, in paint and for collapsed borders (`layout/collapse.rs` `snap`): floored to whole device pixels, a width under one is one device pixel, none is none (`1.6px` is 1 at scale 1 and 3 device pixels at scale 2). A collapsed border keeps its exact half widths.

### Dividing free space

Free space is a `LayoutUnit` in Blink and is divided as an integer, toward zero. `util/resolve.rs` has `half_layout_unit` and `divide_layout_unit`. `common/alignment.rs` has `LayoutUnitDiffuser` (Bresenham: the remainder goes one 64th at a time over the buckets, and the call that gets it is chosen by `x >= y`), `initial_alignment_offset` and `alignment_spacing`.

- Flexbox diffuses the free space of `align-content: stretch` over the lines in layout order (the last line first in `wrap-reverse`), of `space-between` / `around` / `evenly` over the lines and over the items (visual order, so reversed for `*-reverse`), and of main-axis auto margins over the margins (start before end, items in visual order). Auto margins leave `justify-content` nothing to align.
- CSS Grid does not diffuse (`grid_track_sizing_algorithm.cc` divides and drops the remainder, with a TODO to change it), so `alignment_spacing` takes `diffuse_remainder`. `space-around`'s half share is cut twice, which equals `free / 2n`.
- Centring (`justify-content`, `align-items`, `align-self`, `align-content`, a table cell's `vertical-align: middle` and block `align-content`, `-webkit-center`, grid self alignment) is `half_layout_unit` of the free space, negative too.
- Auto margins: two cross-axis ones in flex are each half of the free space clamped to zero (so a flex item that overflows its line has no negative margin); in grid, half the free space (the margins are zero beside the centring Blink applies); in a block, the left is half and the right the rest (`ResolveAutoMargins`).
- An absolute child with no inset and a centring static position is placed by `centred_on_static_position` (flex and grid). The static point is half the content box cut to 1/64, and the child is centred in the span of the padding box that is as far from the point as the nearer edge (`ComputeUnclampedIMCBInOneAxis`, `ComputeInsets`).
- Grid `fr` tracks: `expand_flexible_tracks` takes the share `fr * 64 * flex + carried` as a float, cuts `share + FLT_EPSILON` to a whole unit and carries `share - cut` to the next flexible track. A track whose share is below its base size keeps the base and the carry (`ExpandFlexibleTracks`). `find_size_of_fr` already divided in the same float units.
- A `position: relative` block child resolves `top` / `bottom` percentages against the container's percentage resolution height (`block.rs`), `auto` when it is indefinite, then the other side negated, the top over the bottom and the left over the right (the right in rtl), cut to 1/64. Flex, grid and table items already followed those rules (flex `percentage_base`, the grid area, the table's `auto`). The same height fed `height: 50%` of a child and carried upstream's `.or(min_size.height)`, so a child of a `min-height: 100px` box with an auto height got 50px. It is `auto` as in Chrome now; a height a `min-height` clamps up is still definite.

### Reading boxes back (#45)

`getBoundingClientRect` and the reads that go with it used to return the box snapped to device pixels for painting. Chrome returns layout's own box, in 1/64 px: a `33.3333%` share of 100 px is 33.328125 wide, and a box after a text starts where the text ends, say at 69.3125.

These are the unsnapped border box cut down to a multiple of 1/64: `getBoundingClientRect`, `getElementBounds`, the `ResizeObserver` sizes, the `IntersectionObserver` rects, `onLayout`, the bounds of a `<span>` (its paragraph's rows shifted by the wrapper's laid-out origin) and the boxes `getElementsAt` tests. Painting, hitboxes, hit testing and the pointer's `clientX`, `offsetX` and `offsetY` keep the snapped box (`ElementBounds.painted_x/y` is the snapped origin).

These are integers, as in Chrome, rounded half up from what layout measured: `clientWidth`, `clientHeight` (the padding box less the scrollbar), `scrollWidth` and `scrollHeight` (the scrollable overflow, `layout_unsnapped_scrollable_overflow` in zed), and `clientLeft` and `clientTop` (the snapped border widths, rounded). `scrollTop` and `scrollLeft` are as they were (see [scroll.md](scroll.md) for the device-pixel rule). The values are checked against Chrome 155; gpuix has no `offsetLeft` and the like.

Details that cost time to find:

- The unit of the reads is the window's scale: `automation::layout_units` takes `LaidOut::scale`, and the `f32` noise is taken off on a 1/512 device pixel grid first.
- A collapsed table's `clientWidth` and `clientHeight` are its border box and its `clientLeft` and `clientTop` the outer half border rounded half up (`ElementBounds.collapsed_table`). Its cells' client size still leaves their own halves.
- An atomic inline keeps the fraction of its place in the line in every box it reports and is painted where that place rounds half up to, and so is what is inside it (`Window::with_unsnapped_element_origin`, which keeps the difference in `origin_phase_stack`; #80). The text side is in [text.md](text.md).
- `Window::layout_unsnapped_bounds` reads a box before it is snapped, and only answers in prepaint. The bounds are recorded in paint (never move that, see "Bounds are recorded in paint" below), so `capture_layout_box`, an `on_prepainted_layout` listener that also runs for a culled subtree, keeps the box for the `on_painted_layout` listener of the same element, which writes it in paint through the tape: still one write per element per frame. A replay or a relocated replay moves the value by a whole device-pixel offset, which stays exact because the value is a multiple of 1/64 once the `f32` noise is taken off.
- A span has bounds: its border box per line fragment (`text/inline_bounds.rs`, recorded at paint). `getBoundingClientRect` and the observers read the union, and a span that stops painting is gone.
- A text node has no box, so `Locator.bounds()` on a raw text node falls back to the box of the element that holds it (the whole paragraph, when several text nodes share one).
- **Bounds are recorded in paint.** The bounds of an element and of a span record during paint, and `bounds_frame_reset` clears the registry during paint too. Never move any of it to prepaint: `gpui::list()` prepaints a speculative row range, rolls the window back through `Window::transact` and prepaints a different one, so a box recorded in prepaint can belong to a row that never reached the screen. A layout-only pass (see [forced-reads.md](forced-reads.md#publication)) publishes the same values from prepaint instead. A `visibility: hidden` element paints nothing but still runs these listeners, so it keeps its box (`Window::visibility` tells a listener which it is, and `track_host_bounds` records no selection region for a hidden one). A missing box means `display: none`, a virtual list row outside its window, or a removed element.

Cost: an animated length now moves the boxes after it by fractions, as in Chrome, where it used to move them only when the rounded value changed. A spring's tail moves boxes until the spring rests (0.5 px of `restDelta` for a move over 5 px, as Motion), so `onLayout`, observer geometry and the frames that carry them last longer. On a page whose heights are springs retargeted from `onLayout`, that was about 40% more layout events, 35% more intersection geometry and about 9% more frames drawn while its cards play, with retention unchanged (no non-reusable reasons, replays as before). A root moved by a fraction is built, not relocated, since a relocated replay moves by whole device pixels.

### Virtual-list rows and box

A list used to measure its rows with `layout_as_root`, whose size is the snapped box (a row of `20.3px` was 20), and recorded no bounds: `List::paint` never ran the `on_painted` and `on_painted_layout` listeners, so `getBoundingClientRect` of a `<virtual-list>` was zeros and `onLayout`, `ResizeObserver` and `IntersectionObserver` (target, root, and the clip of its rows) read nothing for it.

- zed: `AnyElement::layout_as_root_unsnapped` (the size layout computed, through `Window::layout_unsnapped_size`, which keeps no bounds so it can be asked before a root is placed) is how `List` measures every row. Rows stack from `layout_unsnapped_bounds` of the list plus the padding `layout_insets` resolved (cut to 1/64, not the style's), at the unsnapped width.
- Each row is prepainted with `AnyElement::prepaint_at_fractional` (`Window::with_fractional_element_origin`): it is painted at the device pixel its origin rounds half up to, and `TaffyLayoutEngine::set_origin_seed` gives the root the fraction, so the edges of the row and of everything in it snap from that origin as the children of a block do. Two rows touch when painted where the unsnapped ones touch. `layout_unsnapped_bounds` reports from the seeded origin, and the enclosing atomic inline's phase is zeroed so it is not added twice.
- The scroll offset a row is placed by is the device pixel the total rounds half up to; the state keeps the fraction, so a small wheel delta still accumulates.
- `Interactivity::run_paint_listeners` is the one place the painted listeners run (div, culled div, list). A list publishes them in a layout-only pass (`publish_layout`) and notes its prepaint listeners as publications.
- gpuix: `build_virtual_list` records the box with `track_host_bounds`; there is no selection region and no scrolls (rows are not in its layout, its scroll metrics are `ListState::dom_scroll`).
- `ListState::bounds_for_item` (and so `item_is_above_viewport` and `item_is_below_viewport`) is where the row is placed: inside the border and the padding (`last_rows_origin`), as wide as the list is between its padding, and scrolled to a device pixel. A row that shows only in the top padding is neither above nor below the viewport.

## The layout engine persists across frames

gpui consumes its elements every frame: the element arena is cleared and a `Drawable` runs once. A frame that does not build a subtree therefore has to put back what the subtree prepainted and painted in the frame before, and that only works if its layout nodes are still there. So the layout engine must persist (this section), gpui needs an element that can be replayed (`gpui::retained`, in [retention.md](retention.md)), and gpuix has to decide which subtrees a frame may leave unbuilt. Each layer is useful alone. Don't clear the engine at the start of a frame: every retained root loses its nodes and its taffy cache.

zed `crates/gpui/src/taffy.rs` and the vendored taffy. The engine is not cleared between frames.

- **Keyed nodes.** A request is named by a scope (the hash of the `GlobalElementId` of the element asking, or of the nearest ancestor that has one) and its ordinal among the requests in that scope. The key only finds a candidate node. The request then compares its style, children and measure key with the node's and sets what differs, so taffy's per-node cache survives for every node a frame leaves alone. Requests without a key (`request_layout`, `request_measured_layout`) make a node that no later frame gets back; the engine counts them (`unstable_requests`).
- **Measured leaves.** A text, image or list measures through a closure that writes its result into a captured `TextLayout` (or the list's state). A keyed measured request (`request_keyed_measured_layout`) passes a *measure key*, which must hash every input the closure reads, and a state handle. With an equal key, equal style, rem size and scale factor, the node keeps the sizes taffy cached for it, the new closure replaces the old one, and the request gets the previous state back, because the closure that filled it will not run again. A key that misses an input the closure reads leaves a stale size in the node.
- **Placement versus probe (#48).** Taffy tells a measure function whether it is placing the leaf (`RunMode::PerformLayout`) or being probed (`ComputeSize`); gpui passes that on as `MeasureRun::Place` or `Probe` to the closures of `request_measured_layout` and `request_keyed_measured_layout` (the multi-line input's too, which lays its text out on either). A placement is a call or the final-layout entry of the node, never an entry of a size probe. The engine records the call that placed each keyed leaf and calls it again if a later probe overwrote the state, so the state is always the one of the placement, and a text keeps what it measured only for a placement. Without that, a container that asks a retained root for a size it is never laid out at (a flex row asking the min-content size of its item) ran the measure function of a replayed root, which is not prepainted, and left the text's handle holding the layout of the question and no bounds. Under `GPUIX_RETAIN_VERIFY=1` a page panicked reading the bounds of a text.
- **Keyed today:** `StyledText` (text, runs with their fonts and variation axes, font size, line height, white-space, overflow, line clamp, layout options such as the wrap style, `text-box-trim` and `text-box-edge`, inline boxes, the insets key, the atomic inlines' digest, font generation, and the font of the style when a trim cuts the box by its cap height or x-height), `img`, `list`, `uniform_list`. gpuix's `<input>` is keyed by its shaped text, runs, sizes, rows, font generation and entity (`TextEditorState::measure_key`), and a text with atomic inlines is keyed only while its boxes persist (see [text.md](text.md) for the text measure keys).
- **Rewritten styles.** gpui's layout rewrites some boxes after they are requested: width keywords (`min-content` and kin), natural widths, absolute boxes whose containing block is not their parent, forced widths, window roots stretched to the viewport. `NodeMeta::requested` keeps the style the element asked for, so a request compares with that and not with what taffy holds. These nodes are requested again and put back every frame, except that a keyword node whose content did not change is not measured again, so that what holds it keeps its `layout_generation`.
- **Collection.** Nodes are freed in `end_frame`, at the end of a presented draw, by reachability from the roots laid out in that pass (a mark in the taffy node, no map). A pass that ends without a frame (`end_pass`: a layout-only read, an abandoned container-query pass) collects only when the engine holds more than twice the nodes the last collection left plus 4096. `calc()` values are interned by value and swept when they outnumber what the last sweep left.
- **Engine of its own for atomic inlines.** A publication runs under the layout engine that was current when it was queued, and so does a deferred draw (`Window::defer_draw`). An atomic inline lays its boxes out in an engine of its own, swapped in only while it works, and a layout id from it means nothing in the window's engine: a box inside an `inline-block` read its insets from an unrelated node, or panicked with "invalid SlotMap key used", on a layout-only read.
- **Known gap.** A `display: none` flex child's `order` differs between a layout cache hit and a recompute. GPUI does not read it.

### taffy's measure cache (#36)

A node caches its size measurements in slots chosen from the known dimensions and the available space, but a lookup also compares the parent size. A stretched column child is measured once under the container's width and once with an unknown parent width; both measurements chose the same slot and evicted each other, so every level re-measured the level below it twice. Nested auto-width columns at depth 12 cost 24547 flexbox computations before the fix and 82 after; the `depth-col` benchmark (8 instances) went from 54.9 ms (6861 µs each) to 0.07 ms (6 µs each).

`third_party/taffy/src/tree/cache.rs` now keeps the measure entries fully associative with exact-key lookup and clock (second-chance) replacement. That is the eviction change of upstream [DioxusLabs/taffy#1010](https://github.com/DioxusLabs/taffy/pull/1010), and `Cache::get` takes `&mut self` for the second-chance bit.

The key is the fork's own, because a cache that survives from one frame to the next is asked more kinds of question than a per-frame one: it tells apart everything the answer of a node can depend on. Upstream's packs the requested axis into the sign bits of the parent size (a negative parent size, an inner size below its padding, was the same key as the positive one) and leaves out the sizing mode and whether the node's top and bottom margins may collapse with its parent's. A node moved to a parent that asks the other way then answered with the old parent's entries. Here a `modes` byte holds the sizing mode, the two collapsing flags, the axes asked and which dimensions are known.

A size measurement is cached with the margins that collapse through the node, which a block container reads (upstream cached the size alone, so a container's height depended on how many times it had asked). And a block container no longer adds a child's offset to the height its floats take when the child holds none, which made a scroll container as tall as the top of its last box when the box overflowed it, and as tall as the box when the box came from the cache. The engine fuzz found all of these.

### Vendored taffy patches

Each is marked `fdarian fork patch` in the source.

- The fully associative measure cache with its key and its margin-carrying size entries (above).
- `set_style` to an equal style is a no-op.
- `remove` and `clear` drop the node context (a leak before).
- `set_children` tolerates parent pointers that no longer match the child lists, in both directions, and adopting a child unlinks it from its old parent.
- `mark_dirty` walks to the root, because a node under `display: none` stores no cache and stopping at an empty cache left stale layouts above it. Relayout boundaries (below) are the one place the walk stops.
- A `dirty_generation` per node, and a `layout_generation` that also moves when the node is laid out with another size, padding, border, scrollbar or content size (a percentage padding changes the inside of a node whose box stays).
- `layout_generation` also moves for every ancestor when a box below the node is another one (`differs_box` in `set_unrounded_layout`). The painted-extent and scroll-reach memos are kept while the generation is the one they were stored with, and a box that moves while the node's own size, padding, border, scrollbars and content size stay would leave them stale: a box with no area is left out of a content size (`compute_content_size_contribution`), and the children of an escapable node are laid out by passes that do not write the node again.
- Each node keeps the `box_generation` its box last changed at (`box_changed_at`, set in `set_unrounded_layout`). gpui's `Window::box_stamp` is the greatest over a node and its ancestors in the window's engine: where the node is on the page, unmoved by a box elsewhere ([forced reads](forced-reads.md#consecutive-reads-share-one-pass)).
- A flex container's known dimensions are floored by its padding and border as block and grid already do: `compute_flexbox_layout` floored the size it worked out from the style but not one a parent passed as known, so a container with children and a height less than its padding came out that height to its parent, and a leaf was as tall as its padding. A relayout boundary that got or lost its children kept the height its parent had read, and the persistent engine then differed from a new one.
- `mark_reached` and `unreached_nodes` for collection.
- `RunMode` passed to measure functions.
- The block-container scroll height fix.

### Engine fuzz

`engine_fuzz_tests.rs` lays out random edit sequences in an engine kept across frames and in a fresh one and compares every node. Seeds 1 to 20000 pass; the suite runs 80. The range is chosen by an environment variable (see [testing.md](testing.md)).

## Relayout boundaries

`TaffyTree::mark_dirty` used to clear the cache of every ancestor to the root, so a leaf change inside a 100x100 scroller re-ran the algorithm of each ancestor over its children. Chrome stops the dirty chain at a relayout boundary (`ObjectIsRelayoutBoundary`, laid out again from `LayoutSubtreeRoot`).

- **Boundary** (vendored taffy, `is_relayout_boundary`; Blink's list for layout correctness, the self-painting-layer condition left out as a paint-system reason): placed by a parent and not hidden; a formatting context root (flex, grid, flow-root, a block that is absolute, a scroll container, has layout containment or has no children); not a flex, grid or table item, not a table, and not an absolute box that takes its place from the static position on an axis; and either size and layout containment, or a width and a height that are lengths, no `min` / `max` by content, and `overflow` other than `visible` on both axes. A change to the style of the node itself is never the end of the chain, since padding, margin and size are the parent's to resolve; the child list and the context are.
- **Walk.** `mark_dirty` stops at the first boundary and registers it as pending. `compute_layout` lays the root out as before, then each pending boundary under it, nearest first, whose layout is not current (`Cache::has_final_layout`; a size probe does not make it so), with the input it was last placed with (`SavedLayout`, kept by every `PerformLayout` call, dropped by a hidden layout). Boundaries not under the computed root stay pending. A boundary that answers otherwise than it did (size, baselines, margins, and the content size when it shows its overflow) falls back: the chain to the root is dirtied and the layout goes on from there.
- **The nodes above a boundary keep their caches**, but their `dirty_generation` and `layout_generation` are bumped, so the retained subtrees, request signatures, painted extent and scroll reach stamps and the intrinsic-width memo see the change. A style that `settle_containing_blocks`, the natural-width probe or `detach_for_relayout` writes goes through `set_style` and the child-list methods, which end the chain at the first boundary and leave its layout to the `compute_layout` that follows in the same pass.
- **Counters.** `TaffyTree::boundary_relayouts` and `boundary_fallbacks`, and gpui's `LayoutCounters::boundaries_laid_out` and `boundary_fallbacks`. They are not in `getLayoutCounters()`: the test renderer's `nodesLaidOut` shows the effect. `TaffyTree::set_relayout_boundaries(false)` turns them off (the fuzz compares both).
- **Guard.** A leaf change inside a 100x100 scroller of blocks lays out 4 nodes (6 with boundaries off), and an idle frame lays out nothing.

## Layout containment of `content-visibility`

Chrome gives `content-visibility: auto` and `hidden` layout containment whether or not the content is skipped; the values and the rest of the feature are in [observers-and-content-visibility.md](observers-and-content-visibility.md). The layout side:

- **Margins and fixed boxes.** `layout::style::apply` sets zed's `contain_layout` on every box with a `contentVisibility` other than `visible` (a non-atomic inline is part of a paragraph and builds no box, so it gets none). taffy lays a `Display::Block` with it out as a formatting context of its own, as one with size containment already was; its own margins still collapse with its siblings'. gpui's `NodeMeta::contains_layout` makes `containing_block` resolve a fixed node to its nearest layout-contained ancestor instead of the root, and such a box counts as positioned for absolute descendants. At prepaint `Window::with_frame` pushes a frame for it, so `Escape::Viewport` is placed and clipped by the contained box, and a deferred draw or patched unit keeps it. gpuix `layout/containing_block.rs` (`contains_fixed`, `reaching_ancestors`) and the hit walk of `retained_tree.rs` read the same box.
- **Percentage heights.** `LayoutInput::height_from_containment` is set by `contained_inputs` when `contain_block_size` gave the known height (an authored or parent-given one leaves it false). Block layout takes the percentage base of the children, and the sizes they resolve against, from the known height only without it. A flex container carries it as `AlgoConstants::percentage_base`, which every place that resolves an item's size, min and max, margin, padding, flex-basis or inset, or passes a parent size to an item, reads; the container's own size, free space, stretch, line sizes and absolute children still read the contained height. A grid resolves against its area, where Chrome gives the same 100. A flex column whose height was not given to it (`AlgoConstants::column_height_indefinite`) passes the flag to its items too, since the height it flexes them to is not definite in Blink either: the `flex: 1 1 0%` item of a card that is itself an item of an auto-height column has the content for its basis. The flag is part of the cache key.
- **The height of a flex column is the sum of its items' hypothetical main sizes**, as in Blink (`max_sum_hypothetical_main_size`, `flex_layout_algorithm.cc`). The content of an item enters only through its automatic minimum size, so `flex: 1 1 0; min-height: 0` in a column of automatic height is as high as its padding and border, not as its content (`longest_line_main_size` in taffy `flexbox.rs`). A percentage `flex-basis` of a column height that is not known (`flex: 1`, `50%` in an auto-height column) is the content, not the `height` of the item (`determine_flex_base_size`, Blink `ResolveBlockLengthInternal` `kMain`); a row does the same for a width that is not known (see [the row above](#a-flex-row-of-unknown-width-is-sized-by-its-items)).

## Breaking changes

Against upstream gpuix; an app author changes:

- `flex` has its CSS meaning (a number is `n 1 0%`); it was silently ignored. `flexFlow` and `place*` are new.
- `padding`, `margin`, `borderWidth` and `gap` take several values and `inset` exists; a multi-value string that was ignored now applies. `DimensionValue` serializes `auto` and a percentage as CSS (it was `null` and a bare fraction), and the shorthand fields of `StyleDesc` are `Sides<T>` or `Gap`, not one value, for anyone reading them in Rust.
- `margin*` and the inset props are `DimensionValue` (number, `%` or `"auto"`).
- `position` defaults to `static`. `top` / `left` without a `position` do nothing, and an absolute box resolves against its nearest positioned ancestor, not its parent.
- Positioned elements paint and hit-test above in-flow ones, and `zIndex` orders them across stacking contexts (a descendant can reach over its parent's later sibling). `getElementsAt` lists elements in paint order. `DialogPopup` defaults to `position: relative`, or its absolute backdrop would cover it.
- `<input>` bounds are the border box. A same-turn bounds or scroll read costs a synchronous layout pass.
- Anchored popups flip (and shift) instead of snapping over the trigger.
- An `<img>` with a `%` width or `maxWidth` gets its height from its intrinsic ratio.
- Empty and whitespace text no longer takes a gap slot.
- `alignItems` / `alignSelf: "baseline"` align by the first line of the text, where they aligned by the bottom of it. Grid baseline alignment changed with it.
- A query container (`containerType: "inline-size"` or `"size"`) is size contained: with no `width` in a flex row or an absolute box it is as wide as its padding and border, whatever it holds.
- A window that allows several draw passes (every DOM window) does not use GPUI's view cache.
- Table styles and props (`tableLayout`, `borderSpacing`, `colSpan`, ...) throw on an invalid value, as the other typed styles do.
- A box is read back in fractions of a pixel, as layout computed it, and not snapped to the device pixel it is painted at (#45). Code that read whole pixels gets fractions.

## Upstreaming

The zed side is the larger part: scroll routing with latching, CSS scrollable overflow, `Position::Sticky`, containing blocks, grid templates, floating-ui `Anchored`, paint ranks and `draw_if_dirty`. It changes GPUI's scroll behaviour for every user, so expect review on the `div.rs` scroll listener. The gpuix side is breaking (`position`, `onScroll`, the wheel sign).

The vendored taffy carries its own patches (above); the eviction change of the measure cache is upstream's [DioxusLabs/taffy#1010](https://github.com/DioxusLabs/taffy/pull/1010).

## Cost

- Tables and `:has()` cost only where used.
- A fitting atomic inline is two subtree layouts per frame.
- Container queries cost nothing in a steady frame; see above for a flip.
- A same-turn bounds or scroll read is a layout pass (see [forced-reads.md](forced-reads.md) for what it costs).
