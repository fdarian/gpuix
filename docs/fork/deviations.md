# Deviations

Every known difference between the fork and the reference it follows: Chrome and the DOM for events, layout, text, paint and scrolling, Electron for the window APIs, Motion for the motion APIs, Base UI for the component ports. This file is the single list. The topic docs in `docs/fork/` and `docs/reference.md` link here and do not repeat it; a behaviour that matches the reference is not listed.

A new deviation goes in the section of its topic, as a bullet with a bold lead phrase, then the fact and why. A Windows, Linux or wasm-only gap goes in "Other platforms" under its topic. The fork is macOS-only, so those are recorded, not open.

## Events and input

- **`preventDefault` on a `wheel` cancels that one input.** A browser that sees the first wheel of a gesture cancelled cancels the whole gesture; here the next input scrolls unless its own handler cancels it too, so a handler that wants a gesture cancelled calls `preventDefault()` on each input.
- **No drag image, and no drag to or from other apps.** `setDragImage` is a no-op, and a dragged element's `dataTransfer` stays in the window. GPUI is not the obstacle: it has an in-window drag ghost (`AnyDrag`, painted last at the pointer) and, on macOS and Wayland, an OS drag session that carries files. gpuix runs its own drag state machine (`events/element_drag.rs`) and uses neither, and `App::active_drag` is crate-private in zed. What a ghost would take: a public `App::start_drag` in zed (small), and in gpuix a ghost view that rebuilds the dragged subtree with no listeners at the pointer under its own element-id scope, a `setDragImage` napi call and the default semi-transparent copy. GPUI cannot snapshot an element to a bitmap (`render_to_image` is test-only), so the ghost is a live second build of the subtree per drag frame. Dragging out to other apps needs more: the OS payload is files only (`ExternalDragPayload::Files`), so text and URL payloads need a pasteboard writer in `gpui_macos`, `DoDragDrop` and `IDataObject` on Windows, and XDND on X11; a custom image on macOS needs an offscreen render to an `NSImage`. Dropping text or URLs in from other apps needs each platform's drag-enter handler to read more than file URLs.
- **Event paths and `:hover` follow the logical element tree** (an anchored popup is inside its trigger, as with a React portal), while GPUI's hit chain follows layout. A trigger therefore keeps `:hover` while the pointer is in its popup.
- **`contextmenu` fires on mousedown** (macOS timing) on every platform. Moving it to mouseup is a small gpuix change.
- **`clipPath` and `borderRadius` hit testing cover every host element whose hitbox comes from a styled box.** `<virtual-list>` inserts its own shaped hitbox, and its scrollbar sits inside the clip. A hitbox a custom element inserts itself with `Window::insert_hitbox` has no clip and square corners; `insert_hitbox_shaped` takes both.
- **`beforeinput`, `onInput`, `keypress` and `charCode` do not exist.** Text editing reports through `onChange` only, after the edit, so a handler cannot cancel one edit by type; `keydown`'s `preventDefault` cancels the key's action and its text.
- **`readOnly` controls** are submitted but not validated, and `select()` does not move focus. Password inputs get the password role and expose no value; number inputs get the spin-button role.
- **`:has()` is the six relational states, not a selector.** The states are `hasHover`, `hasActive`, `hasFocus`, `hasFocusVisible`, `hasDisabled` and `hasEnabled`. There is no `:has(.error)` and no `:has(> x)`, because gpuix has no selector engine. There is no `hasChecked` (nor `checked`): no element can be checked, since every `<input type>` is text-like and there is no checkbox, radio or `<option>`, so the state has no source until a checkbox control exists.
- **`:disabled` / `:enabled` cover form controls only.** There is no `<fieldset disabled>` or disabled `<form>` (neither exists), `:enabled`/`:disabled` for an `<option>` or `<optgroup>` do not exist, and `:checked`/`hasChecked`/`:indeterminate` are not available (no checkable element; they need a native checkbox control).

## Layout

- **Shorthand grammar.** A unitless number token inside a string reads as px in `margin` and `inset` (as their longhands do) and is rejected elsewhere. A `flexBasis` of `content` is rejected. The logical longhands (`marginBlockStart`, ...) do not exist, only the block and inline pairs, which assume a horizontal layout: the start of an inline pair is the left, and the right in an rtl element (`StyleDesc::mirrored_inline_pairs`, where `build_element_unpumped` and `InsetSpec::of_moving` read the style). A span in a paragraph takes the direction of the paragraph's container, not its own `direction`. `borderInline` sets both sides to one value, so it has nothing to swap. A numeric `border: 1` throws; write `"1px solid"`.
- **Lengths.** A focus-visible or focus-within `fontSize` changes only the element's own text, not its children's `em`, as colour does. Two nested `display: contents` ancestors with `em` in `fontSize` do not compound. A `calc()` that comes out negative clamps to 0 for `fontSize` and track sizes. `fit-content(calc(length + %))` as a grid track is rejected (taffy has no calc `fit-content`). A repeating gradient with a length-plus-percentage stop skips the zero-length averaging special case.
- **Clip and scroll follow the containing block (C2): residuals.** With a `filter`, the spread of the part that stays clipped can pass the clip of an escaped box. A `layout` (FLIP) glide is dropped for an absolute or fixed box.
- **An absolute child that escapes a box with no area is clipped away.** The containing block of the child is an outer `position: relative` box, so CSS lets it out of a zero-height (or zero-width) `overflow: hidden` box. It is painted under that box's empty content mask, which clips all of it. Culling is not the cause (an escaping box is never tested against the mask). Seen with a zero-height mask; other masks are not checked.
- **`zIndex` across stacking contexts (C3): deviations.** A virtual-list row is its own context, so a row's content never rises above the next row. A cached view prepainted inside a context is not reused the next frame (its recorded hitbox and tab-stop ranges would be stale). An element that is not a `Div`, `Img`, `Svg`, `List`, `UniformList`, `Canvas` or `Surface` is never lifted. The children of a custom element other than `<anchored>` are never flex or grid items (they draw themselves and have no laid-out children), so they take no `zIndex` without a `position`. `zIndex` cannot be transitioned or animated.
- **`anchor-size()`** resolves on the sizes, margins and insets of a direct child of `<anchored>`. It starts from the trigger's last painted size, so it is right in the first frame under a trigger that has already painted; otherwise the child is held at opacity 0 until the trigger is measured.
- **A `visibility: hidden` subtree is still painted**, with its primitives dropped, so a big hidden pane costs CPU; a "no descendant is visible" hint would skip it.
- **Tables** (`docs/reference.md` "Tables" lists them all). A `tableLayout: "fixed"` table whose `width` is a `%` of a parent with no width draws no collapsed borders (they are predicted before layout). The widths shared out are floats where Chrome counts in 1/64 px. Copied text keeps the tab after a cell that ends in a block, where Chrome drops it. A `table-*` on a custom element is a block. The spacing of table rows is whole pixels (an existing `border-spacing` rule: Chrome keeps it in a `short`, gpuix cuts it before the scale, so a fraction differs at 2x).
- **Direction** (`docs/reference.md` "Direction"): not done. The base direction of a paragraph is CoreText's (the first strong character), not the element's, so mixed text is ordered by it, and a reordered run has approximate bounds and hit tests (gpui's glyph indexes are taken as increasing along a line). `direction` is not animatable. The scrollbar of an rtl scroller is not compared with Chrome.
- **Container queries** (`docs/reference.md` "Container queries"). `scroll-state()` is unknown (false). `var()` is substituted only in the transform properties (see "Paint and transforms"); everywhere else custom properties are read only by `style()` queries, and `style(--x: inherit | unset | revert)` is unknown. There is no `@property`, and `""` declares nothing. `<anchored>`, `<code>`, `<markdown>` and `<diff>` take no `containerType`. Vertical writing modes are infeasible: the vendored taffy lays out horizontal-tb only (`third_party/taffy/src/style/alignment.rs` and the flexbox and grid code carry TODOs for the other modes) and gpui has no `writing-mode` or vertical text, so `cqi` is `cqw`, `cqb` is `cqh` and `inline-size` is `width`.
- **Intrinsic widths.** Text `min-content` wraps at the widest stretch between break opportunities and counts the trailing space, so it is one space wider than a browser's. `flexBasis` is measured like a width only along a row or row-reverse flex container's main axis and is `auto` in a column, block or grid; its `fit-content` is `max-content` (the container's size is not known there), so with `flexShrink: 0` it overflows where a browser clamps.
- **A grid `repeat(n, fr)` set.** Tracks that are not separated by an item are one set in Blink, sized as a whole and divided over its tracks; taffy sizes the tracks one by one, so the carried fraction of such a set can differ by a 64th (untested). `safe` and `unsafe` alignment (`safe center`, `unsafe center`) cannot be written in the API.
- **Scroll offsets in layout.** The scroll offset a box is placed at is the one it is painted at, a whole device pixel: the fraction of a scroll is dropped, so a box in a scroller scrolled by a fraction is where it is painted and not where a browser puts it.
- **A box that is not a scroller has no scroll handle:** `clientWidth` is its padding box, and `scrollWidth` is the same number, so what overflows it is not counted.
- **Relayout boundaries and floats.** Floats are left out of the boundary fuzz: a block laid out from its cache does not hand the floats that escape it to the block formatting context around it, boundary or not.
- **Scroll container baselines.** A scroll block in a block that is itself in a flex, grid or table container inside an `inline-block` is also taken as the last baseline (Blink forces it only through blocks all the way up), and a flex or grid container that scrolls inside an `inline-block` does not keep the baseline of its text in its box (the text is read off directly).
- **Fractional bounds (#45).** Bounds are fractional like Chrome's, with a few differences: the fraction of a scroll offset is dropped and a box that does not scroll reports its padding box for both `clientWidth` and `scrollWidth` (the two entries above), and the cases of a percentage, a flex share or a text that are still a 64th off are the 1/64 entries of this section.

## Text

- **White space: a hanging space stays in the text.** In `normal` and `pre-line` a hanging space at a soft wrap stays in the text, so selection, copy and search see it where CSS removes it.
- **Start and middle ellipsis are flat.** `ellipsis-start` and the middle cut still walk flat character advances, each measured at its run's size, and the ellipsis width has no kerning. (The end ellipsis and `lineClamp` cut where the text lays out, see [text.md](text.md).)
- **`<input>` and `<textarea>` have no tab stops.** They shape text without a style and keep breaking words.
- **`tabSize`, `wordBreak` and `overflowWrap` on a `<span>` do nothing**, because a paragraph is one string with one layout. See `docs/reference.md` "White space".
- **Wavy decoration.** Chrome's wavy line is its own curve (a wavelength of 1 + 2 * round(2 * thickness + 0.5)) that gpuix's sine does not match. It only starts over per text node too.
- **No `text-decoration-skip-ink`.** Chrome interrupts an underline where it crosses a glyph's ink; gpuix draws it whole.
- **Vertical-align rounding ties.** Decoration lines that a `vertical-align` shift puts on a rounding tie are a row from Chrome's.
- **`textUnderlineOffset` under `display: contents`.** Its `em` resolves against the child's font.
- **Atomic inlines.** An absolute descendant resolves against the atomic inline, which is also a stacking context. A percentage `height` inside it sees an `auto` height, as CSS does for a shrink-to-fit box. `textOverflow` and `lineClamp` ignore a paragraph with an atomic in it. A span holding only atomics reports its line box, a match cannot cross the box, and the decoration of a raised span that wraps is drawn at the row's baseline.
- **Inline boxes.**
  - A span that contains a block child is treated as a block.
  - An `auto` or `anchor-size()` margin along the line counts as 0, as `auto` does on an inline box in CSS, and a negative padding or border width counts as 0 (a `calc()` of a padding is clamped as a whole). A negative margin pulls the text, as in CSS.
  - The space of a span that holds no text left after white space processing, or none of whose glyphs are painted, is lost: it has no glyph to attach to. An empty span is not one of them: its placeholder is its glyph.
  - Inside a span with `verticalAlign: top` or `bottom` nothing can be aligned on its own: what it holds goes with it.
  - Only `backgroundColor`, borders, radii and `opacity` paint on an inline box: no gradients, no `boxShadow`, no `box-decoration-break: clone`.
  - A box's content area is that of the span's own font.
  - A span that starts on a `\n`, or is cut by `textOverflow` / `lineClamp`, loses its inline space.
  - A focused span does not dim (`keyboardFocusDim` is not read on it) and its accessibility node has no size.
  - A `groupHover` on a span follows a group declared by the container or above, not one declared by another span.
  - A hit is decided by the glyph cell under the pointer, so vertical padding that reaches into a neighbouring line is on the span only where that cell is the span's.
  - A hanging space at a soft wrap is part of the fragment's rect.
  - An empty `<span>` with inline padding, border or margin (a placeholder in its paragraph, [text.md](text.md#empty-inline-boxes)) is planned from the span's own style. A `hover` or other state style that gives an empty span padding it did not have, or a transition or animation that moves it from 0, does not make the placeholder (the span stays an empty line until a style change re-plans); the other direction keeps a zero-width placeholder, whose line is the strut's. Chrome counts the font and line height of every empty inline box in the line it is on, with padding or without; gpuix counts a box only when it has a placeholder. Find does not match a word across the box. White space before a placeholder is not trimmed by a line feed under `pre-line`, and `pre-wrap` collapses a trailing space before a box that ends the line.
- **`registerFont()` takes TrueType and OpenType only.** WOFF and WOFF2 are not supported; convert them first.
- **Font features need a font that has them.** As in a browser, so `zero` and `onum` paint like the default on the macOS system font.
- **`text-wrap: balance` and `pretty` approximate Chromium.** They are a scored breaker, not Chromium's. `pretty` re-breaks at most the last four lines, and only when the last line is a single short word. `balance` is limited to 6 lines per forced-break segment. Both are skipped for text with a tab, `break-spaces` or `lineClamp`.
- **Line breaking uses ICU4X, not ICU.** A quote next to a small kana or `ー`, and Lao and Khmer word boundaries, can differ from Chrome.
- **No `hyphens` or `line-break` styles.** The strictness is Chrome's `auto`.
- **The hyphen of a soft hyphen.** It is set in the font of the run before the break, where Blink uses the primary font of the box, so a span in another font differs. A range of the hyphen alone has no rect.
- **`LineWrapper::wrap_line` is untouched.** The editor's own wrapper does not break after hyphens.
- **Hanging of spaces is the paragraph's.** A `nowrap` block with a `wrap` span hangs them everywhere. A plain box is not listed to the line layout unless some box of the paragraph wraps.
- **No bidi in the line layout.** `direction` places an overflowing row at the start edge of the box (see the Direction entry under Layout for the paragraph's base direction), but the glyphs of a row stay in logical order, painted from the left, so a hanging space after an overflowing row in an `rtl` box is on the right where Chrome has it on the left.
- **A line shaped again at its end: what is not done** ([text.md](text.md#the-end-of-a-line-is-shaped-again)).
  - A break inside a ligature (Helvetica Neue `fi`): Chrome can break between the letters of a ligature and shape them apart. 45 layouts of the corpus.
  - The reshape before a space under a decoration or a background (`NeedsAccurateEndPosition`).
  - HarfBuzz's unsafe-to-break sets beyond the pairs a font kerns.
  - The start of a line in a font that kerns through a `kern` table: its reported width is about one kern share narrower than Chrome's (Helvetica `ART` 31.125, Chrome 31.72).
  - A box one or two letters wide in Inter or Helvetica can still break differently (of 8142 widths per scale, 23 at 1x and 29 at 2x still differ, 3 and 7 of them newly).
  - Two layouts of the Inter 550/18 and 700/25 texts differ for no cause found: c206 (Inter 16px 550/18 at 406.0078125, scale 2) is a tie of the f32 noise of a kern (the sum is 2 units of 1/65536 over the limit in Chrome and at or under it here), and c305 (28px 700/25 at 548.52, scale 2) is unexplained.
- **Advances of a fallback font.**
  - `system-ui` is up to 0.05 px per 28 letters off at 18px and above.
  - The kana of `system-ui` come from `.CJKSymbolsFallbackSC` and differ from Chrome's (45 of 81 corpus layouts).
  - `Apple Color Emoji` cannot be named as a family, and as the primary font of a box it uses the metrics scaled from the font units.
  - 5 emoji rows at scale 2 are one 1/128 px over the box.
- **CJK punctuation: `text-spacing-trim`** ([text.md](text.md#cjk-punctuation-text-spacing-trim)).
  - There is no `text-spacing-trim` property: `normal` always applies, and `font-feature-settings` that turn `halt`, `palt` or `hwid` on do not turn it off.
  - A `「` that starts a row is drawn with the glyph of the run's font, where Chrome shapes it alone and gets the font the system picks for it (PingFang behind Helvetica Neue), and the glyph after a trimmed closing bracket is not shaped again at a row start.
  - Hiragino Sans named as the family kerns `キス` -60 where Chrome has -50.
  - No vertical text.
- **Legacy kerning through `kerx`.** A font that kerns through a `kern` table is found by its missing GPOS table; an AAT font with `kerx` has none either, and HarfBuzz splits its pairs the same way (untested here).
- **Generic family keywords.** The CSS keywords `system-ui` and `sans-serif` are not font families here.
- **Text box trim.** A lone `cap` or `ex` edge is `cap text` or `ex text` as the spec says, where Chrome currently rejects it. The trim does not pass through anonymous table cells, the `text` edge uses the line strut's metrics, and `text-box-trim` uses the primary font's metrics, not those of the fonts a `normal` line falls back to.
- **Font smoothing.**
  - `none`, which Safari has, is an invalid value here, as are all but the three Chrome's macOS build draws.
  - `auto` is Chrome's to 0.07 % of the ink for black on white and white on black, and to 0.62 % (scale 1) and 0.32 % (scale 2) for #a1a1a1 on #0a0a0a. `antialiased` has the same grey-on-near-black residue (0.9 % and 0.4 %), which is in how gpui's shader blends against Skia's, not in the mask.
- **Font variations.**
  - An invalid `fontVariationSettings`, `fontFeatureSettings` or `fontVariantNumeric` is dropped when the style parses (a `motion` description or keyframe with one is still an error).
  - The automatic mappings of `opsz` (from the font size) and `wdth` (from `font-stretch`) are not done.
  - A keyframe track of three or more values whose tag sets differ flips as a whole, where Chrome decides each pair of keyframes on its own.

## Paint and transforms

- **Masks: what is not built.** `image-set()` is skipped and the legacy `-webkit-mask-composite` keywords do not exist; `no-clip` and `margin-box` invalidate a value, `fill-box` is `content-box` and `stroke-box` and `view-box` are `border-box`, `mask` is not animatable, and an image mask's tiles are culled to the content mask at group start.
- **`mask-border` differs from Chrome in five places.** Chrome has no unprefixed `mask-border-*`, so the oracle is `-webkit-mask-box-image`. A slice is cropped from the atlas, so a vector source scaled up is as soft as its raster; Chrome draws it sharp. Space gaps are whole device pixels where Chrome antialiases them. The Metal polychrome sprite shader clamps its lookup to the sprite's tile to keep a crop from blending in its neighbour; the HLSL and WGSL do not. The `mask` shorthand resets `maskBorder` and its longhands as CSS Masking says it does, while Chrome's `mask` leaves `-webkit-mask-box-image` alone, so that follows the specification and not the oracle.
- **`clip-path` has no `url()`, and `path()` is flattened.** `url()` and `filter: url(#id)` reference an SVG `<clipPath>` or `<filter>`, and gpuix has no SVG DOM, so they stay out of scope. `path()` becomes polygon contours, one per subpath, with curves flattened to 0.25px and a limit of 4096 vertices for the whole path (coarser, up to 4px, before it is invalid).
- **`clip-path`: more limits.** A value with a box that has no shape is ignored. `margin-box`, `stroke-box` and `view-box` are `border-box`, and `fill-box` is `content-box`. `inset()`, `rect()` and `xywh()` round their corners with circles, so the vertical radii after `/` in `round` are dropped. A string in `path()` has no escapes.
- **A dashed or dotted border on an elliptical corner** is laid out along the arc of the corner's mean radius.
- **Background layers.** `image-set()` is valid but not drawn: that layer is skipped and the others still paint. An interpolation space other than `srgb` and `oklab` skips the layer. `backgroundOrigin` and `backgroundClip` move the layers only; the background colour fills the border box (or the glyphs under `text`). `backgroundAttachment` has no meaning here and is ignored in the shorthand.
- **`url()` background images: limits.** At most 128 images are kept and at most 4096 tiles per layer; animated images draw frame 0; an inline span box paints `backgroundColor` only.
- **`outlineStyle: auto` paints as `solid`.**
- **Colours.** Relative colours (`from`) and `calc()` inside a colour are read in limited forms, and every colour is converted to hard-clipped sRGB before it is painted, so there is no wide-gamut output.
- **`UniversalStyle` is one layer.** It has no selectors, no specificity and no cascade between rules, so it cannot say "every `<text>`" or "every child of a card". An element that had no style when the layer first gave it a `transition` has nothing to fade from, so a colour the same change gives it appears at once.
- **A motion value's colours are not tied to an element.** They resolve as on a root with `colorScheme: "light dark"` and keep what they resolved to: they are not re-resolved on an appearance change. An ancestor's `hover` / `active` colour is not in a descendant's motion colour context.
- **Transforms: text in an animating transform is resampled.** A static transform rasterizes the glyph through the matrix, as Chrome does. Under a run of the transform (a CSS animation or transition, a Motion track, a motion value) the glyph is rasterized at a scale rounded up to the next power of root two and drawn through the matrix, then rasterized through it once the run ends, as Chrome composites an animating layer at a fixed raster scale; a rotation that animates is therefore resampled, and the scale Chrome picks and the moments it rasters again are not compared.
- **Transforms: loose clips.** A rotated or skewed child that is itself clipped, inside a rotated clipping ancestor, clips to the ancestor's bounding box with its radii dropped: when the relative matrix between two nested general transforms does more than scale and move, the local clip is replaced by its bounding box in window space. The pointer's path under such a nested clip is loose in the same way.
- **Transforms: tiles in a patch unit.** Mask and background tile culling still varies with the clip, so a tiled mask or background that a transform moves across a clip edge can still change the operation count.
- **Transforms: Motion.** A Motion key given as a string (`x: "var(--a)"`) and Motion's `transform` target do not substitute `var()`; only the CSS properties do. `animate()` of a motion component takes Motion's keys and its `transform` list. There is no `element.animate()`, and `animate(element, ...)` of Motion is not supported (the first argument is a motion value); `getAnimations()` seek, pause and play commands draw whole frames.
- **Transforms: the planes of a 3D context are not depth-sorted.** The planes of a `preserve-3d` context draw in paint order, as a flat tree does. Chrome sorts them by depth and splits planes that cross (a BSP tree), so two planes that intersect show one in front of the other here, and a plane that turns behind another can draw over it.
- **Transforms: `preserve-3d` scroll extents compose level by level.** A scroller counts a box inside a `preserve-3d` chain through each level's own flattened matrix and perspective, where Chrome accumulates the chain in 3D before flattening.
- **Transforms: the local clip of a parent in a `preserve-3d` chain.** A parent's local clip lies in the parent's plane, and a plane of the same 3D context is somewhere else in space, so the clip goes to the window as its bounding box with its radii dropped (the loose clip above, for any turn).
- **Transforms: near the eye.** A corner whose `W` is under 1e-3 (`MIN_W`) is cut there, so the bounding box and the outline of a box that nearly touches the viewer differ from Chrome's. A box wholly behind the eye is empty.
- **Transforms: antialiasing under perspective.** An edge is antialiased over the side of the square one pixel covers in local space (the geometric mean of the pixel's footprint, from the derivatives of the local position), where a pixel at a grazing angle is long and thin, so such an edge is slightly aliased.
- **Transforms: text under perspective is resampled.** A matrix with perspective has no one linear part, so a glyph takes the bucketed raster (the one an animating transform uses) and is drawn through the matrix, softer than Chrome's.
- **Transforms: curves under perspective.** A path's vertices are mapped projectively and its curves' control points are not exact under a perspective, as the rasterizer interpolates its antialiasing coordinates linearly on the screen.
- **Transforms: nothing else forces a flat context.** `isolation`, `mix-blend-mode` and `will-change` are in Chromium's list of grouping properties and do not exist in gpuix, so they cannot make the used `transform-style` `flat`.
- **Transforms: portals.** `<anchored position={{ x, y }}>` takes window coordinates: the layer is drawn in window space, so a transform around it neither moves nor turns the point.
- **Transforms: a `--p` written from JS is not a patched tick.** The write is a tree edit, so the frame is a paint-only frame that builds the elements which read the property (`Edited`), where a transition or an animation of the same transform patches every tick.
- **Transforms: a scroll range moved by a patch.** A patched tick moves the range of the scrollers around its roots, but a scroller whose scrollbar is hidden with `scrollbarWidth: none` still declines the patch when its range changes along an axis it scrolls, though it paints no thumb, and a scroller inside an atomic inline (`inline-block`) is not updated by a patch: its range stays the one of the last whole frame.
- **Transforms: scroll extents of a non-scroller.** `scrollWidth` of an element that is not a scroller ignores overflow, and an absolute child at the end of a padded scroller adds the padding (scenes `e12` and `e17` of the geometry oracle, `EXTENT_DEVIATIONS`). Both predate transforms.

## Scroll

- **A virtual list truncates a large single-frame scroll delta.** A delta above the 512 px overdraw is cut to it in a single frame. Unmounted placeholder rows count as 1 px without `estimatedItemHeight`.
- **A virtual list's classic scrollbar overlays its rows.** With macOS "Show scroll bars: Always" the bar does not take layout space, as a div's does.
- **The border ring of a rounded `<virtual-list>` is hit differently from Chrome's within about 0.5 px of the outer arc.** The rows, clipped and hit through the rounded padding box, match; the list's own box does not.
- **`scrollHeight` leaves out the bottom margin of the last child** of a scroller; Chrome counts it in the scrollable overflow.
- **Scroll anchoring: a nested scroller is one box.** A nested scroller is anchored as one box and is not looked into. There is no priority candidate for the focused editable or a find-in-page match, and `scroll-padding` does not shrink the area a box must be in. None of the three is exercised.
- **Scroll anchoring: Chrome's stale flag on a relative anchor.** Chrome compensates nothing in the layout after a second change of `top` of a relative anchor, as if the flag stayed set until the box is laid out. gpuix compensates (scene `anchorTopStale`, `it.fails`).
- **Scroll anchoring: events.** A frame reports the offset it paints when it differs from the last painted, so an offset written away and compensated back in one frame is no `scroll` event (Chrome fires two). The event of a write runs a frame after Chrome's, as for every write.
- **A `<virtual-list>` keeps its own row-index anchoring.** It does not use `overflowAnchor`.

## Motion

- **Springs differ from motion-dom in three places.** (1) motion-dom drops the inherited velocity for `duration` / `bounce` springs because it overshoots small moves; gpuix carries it, since carrying it is the point, and a critically damped spring cannot oscillate from it. The cost is that an underdamped duration spring interrupted at high speed can overshoot a short move. A duration spring that carries speed is done at the first multiple of 50 ms from its `duration` at which it is within its rest thresholds, where Motion's is done at `duration` whatever it reads. (2) Negative `bounce` (overdamped) and `visualDuration` are not built: the first needs `overdampedFreqScale`, neither was needed for the target components, and physics-form springs can already be overdamped. (3) Setting `stiffness` and `duration` together, or a spring option on a tween, is an error where motion-dom silently prefers one.
- **A culled native spring paints one frame at its end.** A dormant spring wakes at the instant it rests and completes in the same tick as its twin in view, but the tick that applies its end style draws a frame (at most one, pinned) of content Chrome would not paint for.
- **A motion's `currentColor` and inherited font ignore an ancestor's state style.** `parent_inherited` reads the declared styles of the ancestors, so a `hover` or `hasHover` style on an ancestor that changes `color` or the font is not in what a descendant's motion inherits.
- **A transition starts a frame after the write.** Chrome starts it when the style is recalculated, in the task of the write; a CSS transition here starts when a frame builds the element.
- **Variants and gestures of every `motion.*` (incl. `motion.span`).** No `staggerChildren` / `delayChildren` / `when`; no keyboard tap or auto `tabindex` for `whileTap`; SVG shapes take no gesture of their own; a leaving node answers to no gesture, where Framer lets active gestures go on with the properties `exit` does not name (`motion-variants.ts`).
- **`motion.span` keys.** A transform key, `layout`, `layoutId`, `layoutDependency`, `onLayoutAnimation*`, `whileDrag` and Framer's `drag*` are accepted and do nothing, as a transform does nothing to a non-atomic inline box in Chrome: no layout animation runs and none of its callbacks is called. A `Reorder.Item` rendered `as` a span renders and does not reorder. A span that is a flex or grid item, or has `display: block`, is laid out as an element and paints its colours the same way, but still takes only the span's keys. Letter and word spacing and `textShadow` are not drawn on an inline box, so there is nothing to animate.
- **`width: "auto"` as a motion target** works like `height: "auto"`: the natural width is measured one frame after the first paint, and the clock starts at the style change. Taffy's content width is not the width `auto` would give, so a node that can animate width carries `Style::measure_natural_width`: `compute_layout` lays the tree out once with those nodes' widths `auto`, records their border-box widths (`Window::layout_natural_width`), restores the styles and lays out again (taffy's cache redoes only the dirty chain). The flag is set only while a motion has a pending `width` goal containing `auto`, or a transition list covering `width` or `all`, or keyframes using `width`, with `interpolateSize: "allow-keywords"` for the last two; any such element pays the extra layout every frame. `animate` is not gated by `interpolateSize`, as for height. Inside the pass an inner flagged node is `auto` while an outer one is measured.
- **Layout size glides differ from Motion's projection in five places.** (1) `"preserve-aspect"` is not supported. (2) A `layoutId` newcomer is shown as the box the last holder was shown as from its first frame, but there is no crossfade (Motion fades the lead in over the first half and the follower out between 0.5 and 0.95 of the progress) and no mixing of the two border radii; the old holder stays as it is and the app hides it. (3) A retarget carries the speed of the glide it replaces on all four channels (translation of the centre and scale), where Motion restarts at velocity 0 (`mixTargetDelta` over a 0 to 1000 value); a spring is therefore per channel, and its rest thresholds are the ones of the other tracks, so a scale glide of 0.2 is at rest a little earlier than a move of 200 px. (4) Motion corrects the shadow of a box with one `box-shadow` and returns a list of several as it is; gpuix corrects each shadow. A `%` radius needs no correction in either; an elliptical px radius is corrected per axis in both. (5) A projected child is counter-transformed against the net projection of the enclosing `layout` box; when elements with their own transform sit between the two, the correction is conjugated by their matrix (`layout_projection::inside`), which Motion does not do (it does not read through them), and under a 3D enclosing transform it is the flattened plane. A glide is not a patch: a tick builds the page like every `layout` tick did (`LayoutAnimation` in `getPatchCounters().unpatchable`), but lays nothing out, since the transform changes no box. Text in a box that is scaled by a glide is stretched, as it is inside any scaled box in Motion.
- **`transition-behavior: allow-discrete`** works for `display`, `visibility`, the flex and alignment keywords (`flexDirection`, `flexWrap`, `alignItems`, ...), `position`, `overflowX`, `overflowY` (and `overflow` for both), `pointerEvents`, `tableLayout`, `borderCollapse`, `captionSide` and `emptyCells`, with the spec's `display` and `visibility` exceptions. `cursor` is not transitionable, and a transition into or out of `display: contents` is unreliable (the box generation reads the declared style). Like `display`, these are not targets of `motion` or keyframes (Chrome flips them at 50% there). `zIndex` transitions as an integer rounded half up, and `verticalAlign` blends a length or a percentage of the line height; a keyword against a length is discrete. An element held by an X-to-`none` display transition is listed in a per-frame thread-local read by `is_display_none`. There is no `@starting-style`: the first style an element is seen with never transitions (`motion`'s `initial` is the equivalent), so `none` to X shows X at once.
- **`auto` in a margin, an inset or `flexBasis` is discrete**, as in CSS where `auto` does not interpolate with a length: `motion`, keyframes and `@keyframes` flip at 50% of the eased progress, and a CSS transition runs it only under `allow-discrete` (`AnimValue::Keyword("auto")` paired by `Layout::DiscreteList`). Unset insets and `flexBasis` start at `auto`, unset margins at 0. `flex` is a target (`expand_shorthand` splits it into `flexGrow`, `flexShrink` and `flexBasis` with the static grammar of `css/flex.rs`) but a motion value cannot be bound to it. The logical shorthands (`paddingBlock`, ...) are not targets. One Chrome quirk is not copied: a CSS transition of a margin from a length to `auto` (under `allow-discrete`) holds the length until the end in Chrome (headless shell 1248), where Web Animations, the insets and the sizes flip at 50% as the spec says; gpuix flips at 50% for all of them.
- **`popLayout` needs a positioned parent** (`position: relative`): the leaving child becomes `position: absolute`, which resolves against its containing block. Framer's rule is the same.
- **Colour space.** CSS transitions and animations blend two legacy-syntax colours (hex, named, `rgb()`, `hsl()`) in sRGB and every other pair in Oklab, as browsers do; `currentColor`, an inherited colour and `color-mix()` count as modern syntax. `motion` springs and motion values stay in Oklab (per-channel springs with velocity carry-over).
- **`transitionProperty` needs kebab-case** (accepting camelCase is a few lines). A transition declared in the same `setStyle` as the value change runs: the retained tree keeps the style before the one that adds the declaration (`style_before_transition`). If two `setStyle` calls land before one render, the intermediate style is the start.
- **Cascade.** A running CSS transition beats a CSS animation on the same property. A declared change of a property that a running or filling CSS animation drives starts no transition (CSS Transitions §3). Deviation: an animation that has not produced a value yet already counts as covering the property, so a change then starts no transition either. A redefined `@keyframes` updates running animations on the next frame. An implicit 0% and 100% keyframe is the underlying value (re-read each frame); where the underlying value cannot be read (inherited `fontSize`) the nearest keyframe holds. On an SVG shape it is the attribute, else the inherited value, else CSS's initial value (`0` for `strokeDashoffset` and `r`, `1` for `fillOpacity`, black for `stopColor`, `none` for `strokeDasharray` and `d`, `auto` for `width` and `rx`). Keyframe properties are limited to the animatable set.
- **`%` in motion.** The percentage part of a length is a share of the parent's content box (the border box for a corner radius), so it follows the parent's size exactly. Margins and insets resolve against the parent's content box, width for left, right and every margin side, height for top and bottom. CSS uses the nearest positioned ancestor's padding box for insets and absolute margins (needs a public `containing_block` and its padding-box size from zed). A `%` height under a parent with no definite height is `auto` (`motion/containing.rs`; grid items never count as definite, relative `top`/`bottom` and `minHeight`/`maxHeight` `%` in an auto parent are not zeroed). Padding resolves against the parent's width on every side, as in CSS, and `flexBasis` against the main size of its flex container.
- **Auto-size animations start at the style change.** An animation that waits for a measurement (`auto`, an unset size) takes its numbers from it but its clock from the frame of the change (`Pending::started`), as an `interpolate-size` transition does in a browser. A measurement that arrives frames after the commit therefore starts the animation that far in.
- **Relative units in motion.** A length in `em`, `rem` or a viewport unit is px by the time an element's track holds it, resolved in the element's `LengthContext`. A motion value is not tied to an element: it resolves the viewport units against the window at write time and keeps `em` and `rem` (`AnimValue::Relative`), which `MotionValueStore::apply` resolves against each element it is bound to, so one value is two sizes on two fonts. A CSS animation that moves an element's `fontSize` does not move the `em` of a bound motion value (motion values apply before CSS animations). A percentage in a motion value is a share of whatever element it is bound to. The percentage part of a spring rests at a hundredth of the tight px thresholds, so `restDelta` and `restSpeed` are in percentage points there. Multi-value motion values whose counts differ fill out by the shorthand's side rule (`"8px"` to `"8px 16px"`) instead of jumping; counts no shorthand could pair flip at the halfway point.
- **`fontVariationSettings` in motion.** Two settings that name the same axes blend per axis, as Chrome's `CSSFontVariationSettingsInterpolationType` does. Any other pair, `normal` against a list included, is discrete and flips at 50%; a CSS transition runs that only under `allow-discrete`, where `animate`, keyframes and `@keyframes` flip with no opt-in. A span animates it, the paragraph being laid out each frame.
- **Unset starts.** An unset `color` starts from the inherited colour (a parent's colour change does not start a transition on the child, where a browser would). `aspectRatio` and `lineHeight: normal` take the target at once, as CSS does for non-interpolable keywords. An unset `fontSize` and `fontWeight` start from the inherited computed values. An unset border or outline width starts at the `border` shorthand's width or `medium` (3px), whatever the style, as Chrome's animations do (checked against `fixtures/motion-values-oracle.html`: Blink zeroes a `none` border where it is used, so `getComputedStyle` reads 0 but a style that appears starts no transition). Chrome also floors a fractional border width to a whole device pixel, so an animated width steps where gpuix lays out the blended value. `letterSpacing` is not in `StyleDesc`.
- **Reduced motion** follows framer's `positionalKeys`: `width`, `height`, `top`, `right`, `bottom` and `left`, Motion's transform keys (`x`, `y`, `scale`, `rotate`, `skew`, the origins; the CSS `transform` properties are not reduced), and `layout`, `layoutId` and `Reorder` glides, jump; everything else animates. Deviation: a bare `animate(motionValue)` bound to one of those six keys is reduced too, which framer does not do. SVG geometry attributes are not reduced.
- **`matchMedia`.** `hover` is fixed to `hover` and `pointer` to `fine`, because GPUI exposes no input-device signal. Size queries re-evaluate when the window is resized (`mediaChange` from `observe_viewport`); there is no DOM `resize` event. A bare `matchMedia()` binds to the most recently mounted root.
- **`layoutId`.** An old holder that is still mounted is not hidden, the hand-off window is one render, and layout events arrive one frame late. `layout={false}` also disables `layoutId` (whether Framer does the same is unverified). `layout="size"` on a `layoutId` box animates the size only, as Motion does (the box was moved by the id alone before).
- **A glide starts at a commit, for any box when the tree changed.** Motion measures only the boxes that re-rendered (or share a `LayoutGroup`); a box whose component did not re-render still glides in gpuix when the tree changed anywhere and layout moved it. The measure is the first drawn frame after the commit, with the ticks of a running animation kept out by a layout pass before that frame (`docs/fork/motion.md`, "The commit apart from the frame's ticks"), which costs one extra layout pass on a frame that follows a commit while something animates and a `layout` box exists. A scroll alone (a commit that re-renders a box and scrolls its scroller, the box unmoved in its content) glides nothing; Motion glides the box by the scroll if it re-rendered. There is no `layoutScroll`: every scroller is measured in the viewport, as Motion does a scroller without it (with `layoutScroll`, Motion measures in the scroller's content, and a scroll written in the commit then moves the start with the content, `scrollDownLayoutScroll` in `motion-layout-scroll-oracle.json`). Motion's document scroll is measured in page coordinates; gpuix has no document scroll.
- **Motion values.** A function-form transform and `useVelocity` are computed in JS and run one frame behind. A spring follower replays missed frames in 16 ms steps, capped at 1000, before each read or write. Hook-created motion values are released but not destroyed on cleanup.
- **Motion value playback controls.** `play()` after `cancel()` runs the animation again, as in Motion; only `stop()` is final. A paused animation holds its value's node until it is stopped. `finished` and `then` stay pending after `stop()`, `cancel()` or a replacement and never reject; the `(from, to, {host})` overload of `animate` settles its temporary value on an internal signal. Motion rebases `startTime` when the first tick comes more than 40 ms late; gpuix does not. `startTime` is ms on the renderer's clock, where Motion's is on `performance.now()`: only differences are comparable. gpuix has no scroll timelines (`scroll()`, `useScroll`, `ScrollTimeline`, `animation-timeline`), so `attachTimeline` serves a timeline an app writes.
- **SVG keyframes and transitions.** The SVG attributes that are not CSS properties (`pathLength`, `x1`, `stdDeviation`, `dx`, `refX`, ...) are neither keyframed nor transitioned. A paint of `none` against a colour swaps halfway, as in Chrome; `none` or `auto` against a value is discrete for that interval. A `%` `width` or `height` means nothing on a shape, and paths with different commands flip halfway. The transitions of two properties that one change starts are made in the order of their CSS names, so a pair that ends at the same instant tells its events with `height` before `width`, where Chrome tells `width` first.
- **Web Animations: what is not built.** There is no `document.timeline` (`document` spans every window); `animation.timeline` is the renderer's, whose `currentTime` is ms on the renderer's clock, so `startTime` and the times of events are comparable with Chrome's only as differences. `animation-composition` (and `effect.composite`) is not supported, so the two oracle cases that set it are not replayed, and neither are the three that need `::before` or `::after`, since gpuix has no pseudo-elements. `replaceState`, `persist()`, `commitStyles()`, `onremove`, `setKeyframes()` and a settable `effect` do not exist, and `Animation`, `KeyframeEffect` and `DocumentTimeline` cannot be constructed by an app. `currentTime` reads the time of the last frame, not the instant of the call. The cancel event of an animation whose element is removed comes from a task of its own (`setTimeout(0)`), where the DOM's comes at its next frame.
- **`getKeyframes()` and `getTiming()` against Chrome.** Every kind of value gpuix animates is read as Chrome writes it (898 oracle cases), except: `0%` reads `0px`; the z of a `transform-origin` is dropped; a percentage `text-decoration-thickness` is folded to px; `lighter` and `bolder`, `min-content`, `thin`, `normal` and the `border` and `outline` shorthands are refused in keyframes (the test lists them all in `REFUSED`); a two-value `border-color` in a style and an `em` SVG length are not read; Chrome writes `currentcolor` as black in a transition and gpuix does not; 40 colour cases from converted spaces (`lab()`, `lch()`, `color-mix()`, wide gamuts) are within 2e-4 of Chrome's digits, not equal. gpuix starts transitions of `text-underline-offset` and `text-decoration-thickness` from `auto` and of an `aspect-ratio` with `auto` where Chrome starts none, and does not start a `translate` between one and two values or a `translateZ` transition, which Chrome does.
- **`filter` animation: the corners.** (1) Chrome 156 mixes a legacy `rgb()` drop-shadow colour with an `oklch()`, `lab()` or `color()` one as if the modern colour were black; gpuix blends the pair in Oklab, as it does for `box-shadow`. (2) An `oklch()` colour is clipped to sRGB when parsed (motion's `Color` does that for every property). (3) A `currentColor` in a `drop-shadow()` resolves when the animation is planned, so a later change of `color` mid-animation is not followed. (4) A motion key track of three or more filter lists that do not line up (`[a, b]`, `[a]`, `[a, c]`) steps as a whole; CSS keyframes decide each interval, as Chrome does. (5) A motion value cannot be bound to `filter` (`parse_value` reads no filter string). (6) A JS style change of `filter` alone is a layout change (a stacking context), where an animation of it is paint only. `url()` filters do not animate.
- **A list of variant names plays with one transition.** `animate={["a", "b"]}` merges the targets and the last name that has a `transition` wins for every key. Motion animates each name with its own transition. Closing it needs per-key transitions on the wire, which `Transitions` takes as written (no `times`/`ease` fitting, no nested `default`).
- **`initial`'s `transition` is dropped, and it is not the way back.** Motion plays the way out of a `while*` for a key that `animate` does not define with `initial.transition`, else the component's; gpuix uses the resting description's transition (`animate`'s own, else the component's). No `inherit: true` on a transition, and no `transitionEnd`.
- **Animations of Motion in `getAnimations()`.** They are listed where Chrome lists the ones Motion 14.1.0 hands to the browser (`opacity`, `filter`, `backgroundColor`, browser-syntax colours); every other key is JS in Motion and in gpuix and not listed, and standalone motion values are never listed. Differences from the animations Motion makes (`motion-waapi-oracle`, cases in `NOT_EXPRESSIBLE` and `VALUES_DIFFER`): Motion's JS easings (`circOut`, `backOut`, `anticipate`, functions) and `steps(4)` as Motion reads it are not gpuix eases; the `transform` and `clipPath` keys, `transformTemplate`, `onUpdate`, inertia, `autoplay: false`, a negative delay, a spring over more than two keyframes or with `damping: 0`, and spring fields on a tween do not exist or are refused; `color-mix()` is the colour it computes to, not the function; an SVG `fill` starts from the shape's fill, where Motion starts from black; `borderColor` is four animations here. One `ease` over N keyframes is rendered per segment. A spring tells `onMotionComplete` up to about 50 ms after Motion does when Motion hands it to the browser: the animation lasts as long as the easing it writes, which Motion measures on a scale of 100, where the value rests by the thresholds of its own move. A spring that interrupts another carries the velocity of `opacity` only. A `pause()` holds the time of the last frame, where Chrome holds the next one. The `stop()` of Motion commits a value sampled from a JS replica of the animation, which a `motion` component has no counterpart of, and the animation is listed from the first drawn frame, so a control used before that has nothing to act on. A `duration` of 0 is not replayed: Motion lists it for one frame, and not reliably.
- **Revived animations.** A command plays again an animation the style or Motion cancelled, as in Chrome, with these limits: a script animation of a `motion` component is revived only while its track is unchanged; the run of an element that is removed or `display: none` stays gone (Chrome runs it, unrendered); a disowned transition is not ticked while it is dormant in skipped content, so it catches up when the content shows.

## Observers and content-visibility

- **`display: contents` virtual-list row (C7).** It lays out as an anonymous block inside its one list item, not spliced into the list's items (the list's item, focus-handle and index bookkeeping is per row), and the list measures the row as that block, its children stacked (the DOM has no such list). Its listeners fire (the event path holds it), `getBoundingClientRect` is a zero rect, an `IntersectionObserver` reports not intersecting, it is not focusable and takes no Tab stop (`needs_focus`), and the anonymous block carries its `role` and `aria-*` (oracle `display-contents-oracle.html`, which also records the Tab order and the accessibility tree).
- **`display: contents` element spliced into a parent.** It keeps no accessibility node (a node needs a gpui element, and taffy has no `contents`), so its `role` and `aria-*` are ignored there and `aria-hidden` on it hides nothing, whereas Chrome keeps both.
- **`ResizeObserver` on a `display: contents` element.** It reports nothing for the 0 by 0; Chrome delivers one 0 by 0 entry at `observe()`, as for `display: none` (which `docs/reference.md` documents).
- **Observers merge reports per frame, not per spec step.** The spec repeats the resize observation loop at deeper depths until no observation is shallower than the last; gpuix does not. An `IntersectionObserver` reports one entry per target per frame, where the spec queues one per threshold crossing between deliveries.
- **A `ResizeObserver` on a scroller with a classic gutter reports another content box than Chrome.** Observing the scroller itself, the entry's content box is 185 wide where Chrome's is 170 (a 200 px scroller with a 15 px gutter); the entries of its children and the `rootBounds` of an `IntersectionObserver` rooted at it match.
- **Changes below a skipped element rebuild the elements above it.** The `subtree_revision` of the ancestors moves though nothing below is built.
- **`motion` states and SVG shapes of a skipped subtree are not paused.** Only CSS animations and transitions go dormant.
- **Focus handles of a skipped subtree are not removed.**
- **Containment: the test window's scale.** None other known, but 24 cases of `content-visibility.test.tsx` fail against Chrome for the test window's scale, with or without containment.
- **Tab into a skipped element scrolls to the nearest edge.** Chrome centres a focus target that is out of view; gpuix scrolls it to the nearest edge, as it does for a built target (Tab, `focus()`), so the first Tab into the entry is scrolled by about half a window less than Chrome's.
- **Accessibility nodes of skipped content have no bounds and no actions.** No Click, no Focus: a screen reader finds them, reads them and cannot press them until the element is built. Chrome activates the element for any of them.
- **A skipped element with no role is a `Group`.** In Chrome it is `generic`. An `aria-hidden` or `inert` element leaves its whole subtree out, where a built one keeps its node, hidden; the same for a name that comes from one.
- **Custom elements below a skipped one are described by their props only.** `role`, `aria-*`, the default role of `<img>`, `<input>` and `<textarea>`, an input's `value` and `placeholder`; the state an editor keeps for itself (typed text, a number field's range) is not known until it is built. `<virtual-list>` rows and `<anchored>` content below a skipped element have no node of their own.
- **Find in skipped content: native text is not counted.** Matches in `<code>`, `<markdown>` and `<diff>` text inside skipped content are not counted (that text exists only while the element renders).
- **Find: scrolling to the active match is the app's.** `createTextSearchController` and `useTextSearch` do not scroll. A skipped element has the box `contain-intrinsic-size` gives it, so scrolling to the element works before it is built; Chrome scrolls to the match itself.
- **Find: `ranges` of a spec.** They index the text of the collected groups, which have none of the text of `hidden` content.
- **Find: the reveal lasts as long as the match is active.** Chrome unlocks for two lifecycles and then lets the viewport decide, but it has scrolled to the match by then.
- **An animation that finishes while its content skips has its `currentTime` clamped.** Chrome keeps counting past the end, so a `getAnimations()` read of a finished-while-skipped run differs from gpuix's.
- **`getComputedStyle` in skipped content.** Chrome's read (`q3_inside_read`, `readStyle`) has no gpuix counterpart and is not played.
- **Motion completion callbacks of skipped content.** They are JS in Chrome and fire on time; gpuix keeps #90's `At(end)` wake.
- **A far `auto` host under a rotated ancestor stays skipped.** With `rotate(30deg)` on an ancestor Chrome treats the host as relevant (`transform-skipped-read-oracle`, `a.rotate30.auto`); gpuix keeps it skipped, as it keeps every box that far out; the boxes a read answers are Chrome's either way (`STAYS_SKIPPED` in `transform-skipped-read.test.tsx`).

## Forced reads

- **A bounds or scroll read does not make the accessibility tree or the input handler current.** A read is a layout-only pass, and the pass skips the accessibility tree and the input handler (IME caret bounds), which keep describing the previous frame until the next draw. This holds for a read inside an input handler as well as outside one. Making them current would mean swapping frames, which a read never does: a swap inside dispatch breaks the dispatch tree and the held mouse listeners ([forced reads](forced-reads.md#inside-input-dispatch)).
- **A forced element that runs a CSS animation loses the layout records kept for its host.** The pass samples it at the instant of the read, so `Retain::skip_content` drops its records and those above it up to the host, and the next forced read builds the host again.

## Window

### Drag regions (`appRegion`), from Electron

- **Paint order, not Blink's pre-order.** zed registers a box when it paints, so "last wins" is paint order. Where gpuix paints out of tree order (positioned boxes with a `zIndex`, deferred `<anchored>` layers), a region follows the paint.
- **A `<virtual-list>`'s own box registers no region.** Its rows do, by inheritance, so the region is the rows' boxes, not the list's.
- **An inline `<span>` flattened into a paragraph has no host box, so the paragraph registers its regions** (`text/inline_region.rs`): one rectangle per line fragment of the span's border box, as `PassThrough` hitboxes registered in the paragraph's paint after the container's own region, so a span wins over its container and a nested span over its parent. A span registers only where its effective value (inherited, `display: contents` included) differs from the enclosing box's; `pointerEvents` and `inert` do not take part, hover is folded in as for the cursor, and a span's margin is not in its region. A span that is a flex or grid item still registers as a host box.
- **A double click is decided on the second mouse-down**, where Electron and AppKit decide on the second click.
- **`appRegion` is not a DOM or CSS property.** It is Electron's `-webkit-app-region`, and the standards-track `window-drag` has a different value set; the exception to the DOM/CSS principle is taken because a web port needs it and nothing in the DOM does the job.

### Window placement and displays, from Electron

- **The test renderer ignores `x` / `y`.** Its window stays offscreen (origin -10000), so the options are forced to `None`.
- **A point on no display opens on the nearest display.** The display whose rect is nearest is used.
- **Ids are `CGDirectDisplayID`s** (32-bit), not Electron's. An id that does not fit 32 bits throws.
- **A mirrored display is not listed**, since it has no frame of its own.

## `<webview>` and window composition

The page is a native `WKWebView` between GPUI layers ([webview.md](webview.md)), so what GPUI does to its own primitives does not reach it. Compared with an `<iframe>` in Chrome and with Electron's `<webview>`:

- **Rounded ancestor clips, transforms, filters, masks, `clip-path` and blend modes do not apply to the page.** The native view is cut by the content mask as a rectangle (so an `overflow` ancestor works, its rounded corners do not), and a transform only moves the box it puts it in. GPUI cannot draw a native view through its offscreen passes, and a rounded or transformed mask would need the view's layer to be masked per frame by a path GPUI does not hand over.
- **A page inside an effect group draws above the whole group.** The placeholder takes the order of the outermost open group, so the group's content is below the page and none of the group's content is above it. Only the opacity of opacity-only groups applies (multiplied with the element's own); a `filter`, `mask` or `clip-path` on a group does not reach the page.
- **`backdropFilter` and blend modes of content painted after a page see only the layer they are drawn in.** Everything above a page is drawn in a transparent overlay layer of its own, so a backdrop blur over a page blurs nothing and a blend mode blends with transparency, not with the page. Content painted before the page is in the window's layer and works as usual.
- **Only a uniform `border-radius` cuts the page.** Four equal circles map to the container layer's `cornerRadius`; unequal corners, elliptical radii and `border-radius` on an ancestor leave the page square.
- **Pointer events over the page also reach DOM listeners on and around the `<webview>`.** GPUI sees every press, move and release first (hover, `:active`, outside-click dismissal, focus), and then the page does; an `<iframe>` keeps them from its parent. A handler that stops propagation withholds a press from the page.
- **`pointer-events: none` on a `<webview>` does nothing.** The page still gets the events, the element's handlers still run, and GPUI content under the page does not get them. The hitbox that the placeholder is tied to is always a normal one.
- **A page with nothing tabbable takes one Tab stop.** WebKit focuses the page itself and the next Tab leaves it; Shift+Tab the same. Chromium skips an iframe with nothing to focus. The element gets `focus` and then `blur` for that stop.
- **Keys typed into the page do not reach the parent, and GPUI's modifier state catches up late.** While the first responder is in the page, GPUI's key dispatch does not run (as in an iframe): no `keydown` on the `<webview>` or `window`, and GPUI's Tab default does not run (the page's own does). `flagsChanged:` is not seen either, so the modifiers GPUI knows are corrected by the next event.
- **`did-fail-load` carries `NSURLError` codes**, not Chromium net errors: `-1009` where Electron says `-106`, `-999` where it says `-3`. A failure of WebKit's own domain (a restricted port, 103) keeps its code. `did-stop-loading` also follows a failed load.
- **An app with a `<webview>` is not idle.** WebKit answers the UI process with a run-loop wake that gpuix's run-loop watch does not see, so a timer wakes JS: every 16 ms for 1.5 s after anything asked a page for work, every 250 ms otherwise. About 4 wakes a second at rest, about 60 in the 1.5 s after an action. See [frames-and-wakes.md](frames-and-wakes.md#waking-js-for-a-webview).
- **The page can be a frame ahead of the GPUI content around it.** Views and drawables are committed together, but not always in the same frame: after a scroll, the page shows the new offset while the GPUI marker beside it shows the one before. Measured with the e2e lockstep group on a release build (240 captures per run, eight busy processes for the loaded half, nine runs): 18 mismatches of 2160 (0.8%; per run 2, 0, 4, 1, 6, 1, 0, 0, 4), and 0 of 2160 on a quiet machine. Every mismatch was the GPUI side late (the page at the requested offset, the GPUI marker at the previous one); the page was never late. The next frame is right. The e2e allows 3% and prints the number. Without the transaction (drawables presented on their own schedule) 20 to 40% of captures, loaded or not; before the flush after every composed frame, 12 to 20% under that load. Variants measured in the same way and not better than the committed code: every composed frame presented with the transaction (9, 9, 0 of 240 loaded), `waitUntilCompleted` before the present instead of `waitUntilScheduled` (2, 4, 23), both (14, 9, 6), an explicit `CATransaction` begin and commit instead of the flush (nine runs, 11 of 2160, 0.5%: not distinguishable from 0.8%), and drawing the GPUI layers before the views move (10 of 1440 over six runs). The cause is not proven. Not tried: applying the views' frames in the drawable's presented handler (the page would then be the late side, a frame behind instead of ahead). See [webview.md](webview.md#geometry-the-container-and-the-content-view).
- **The cursor over the page is not verified in-process.** WebKit sets it for the real pointer only, and a test cannot move that without a global event. The e2e reports it as not checkable; the window view's cursor rects leaving out the native frames are checked.
- **One window-sized transparent layer per visible page.** Layering by paint order costs a `CAMetalLayer` and a renderer above every page that shows; ten pages in view are ten overlays.

## `<nativeview>`

A native view from another library between the GPUI layers ([nativeview.md](nativeview.md)). It shares the composition of `<webview>`, so the [`<webview>` list](#webview-and-window-composition) above applies to it where it is about what GPUI cannot do to a native view (transforms beyond the box they put it in, filters, masks, blend modes, effect groups, `backdropFilter` over it, one overlay layer per view). What is its own:

- **Rounded ancestor clips do not round the view.** An ancestor's `overflow` cuts it as a rectangle; the element's own `overflow: hidden` rounds it to the inner `border-radius` (four equal circles; otherwise square), and that mask also cuts what the view draws outside its box. A radius and an outer shadow cannot be combined.
- **A view whose box is wholly outside the clip is hidden**, so the outer shadow of a box scrolled out of sight does not show at the clip's edge, as it would for a shadow painted by the box itself. Overflow shows while the box touches the clip.
- **A view that overflows (the default `overflow: visible`) takes the layer order of everything it can draw over**, not of its box: everything painted after it within the clip is above it, even where it does not overlap its box. Correct, and costs a layer per view whatever the overlap; `overflow: hidden` keeps the layers to the box.
- **With `nativeEvents`, GPUI sees a press first** and the library view gets it after, unless a handler stops `pointerdown`, as for a `<webview>` (an `<iframe>` keeps events from its parent). The wheel over the view is the view's. Without it the surface takes no pointer events at all.
- **`onAttach` is asynchronous.** It arrives through the event queue, after the first frame that has the surface; `onDetach` is synchronous. An element unmounted before the attach was delivered gets neither.
- **`onDetach` cannot call gpuix.** It runs inside the call that destroys the element or closes the window, so a renderer call from it fails with the nested-call error.
- **The element is not focusable.** The library takes the keyboard by making its view first responder; a press on anything that is not a native container returns it to the window view. Tab does not leave a library view that holds the keyboard.
- **The view fills the padding box**, not the content box: the children's `padding` is inside the view.
- **Nested native views are not supported**; each `<nativeview>` is its own container in the window (what would change is in [nativeview.md](nativeview.md#several-native-views-and-nesting)).
- **Other platforms**: an empty box that warns once, like `<webview>`.

## Base UI

- **`initialFocus` defaults to the popup, not the first tabbable element.** Base UI picks the first tabbable element. GPUI's tab order exists only after the popup has painted, so the popup is focused and the first Tab walks that order.

## Other platforms

The fork is macOS-only, so these are recorded, not open. Each entry says what the other platforms do or lack and, where it is known, what closing the gap would take.

### Events and input

- **Windows and Linux dispatch asynchronously.** `preventDefault` cannot cancel a native default there (a press's focus, a wheel scroll, editor actions), a label always activates its control, form `invalid`/`submit` events arrive after `requestSubmit()` returns, the focus events of a press, `autoFocus` and a frame are queued too, and the first move of a `Reorder` drag can be lost (it captures the pointer from a queued `pointerdown`, so a move that arrives before the handler runs is not captured). Not infeasible, a consequence of the threading: on macOS GPUI runs on the JS thread (`MacPlatform::new_embedded`), so an input callback is already inside a napi call and `sync_dispatch::emit` can call the handler directly. `gpui_windows` and `gpui_linux` have no embedded loop, so gpuix runs `Platform::run` on its own thread, and a blocking round trip can deadlock: several JS-to-UI calls (clipboard, scroll metrics) block the JS thread on a reply, so a UI thread waiting on a JS handler and a JS thread waiting on the UI thread stall together. Two ways out. A request/reply bridge in gpuix: the UI thread waits on a channel for the handler's `{defaultPrevented, propagationStopped}` while servicing the commands that handler issues, with a timeout and the queued path as the fallback; a busy JS thread then stalls input. Or embedded run loops for Windows (a `PeekMessage` pump) and Linux (a calloop dispatch with a zero timeout) in zed, after which the macOS design applies unchanged and the second thread and its command enum go. Either must be built and tested on a Windows or Linux host. The OS drop operation of dragged-in files is macOS only.
- **`cursor: none` and pointer lock are macOS only.** Only `gpui_macos` implements pointer lock (`CGAssociateMouseAndMouseCursorPosition`); the platform trait's default refuses it. `cursor: none` has no Windows implementation that was tested (`CursorStyle::None` maps to no cursor there) and Linux shows the default cursor. Lock needs `ClipCursor`, a hidden cursor and raw-input deltas on Windows, `zwp_pointer_constraints_v1` with `zwp_relative_pointer_v1` on Wayland, and XInput2 raw motion with a grab on X11; Wayland `cursor: none` is `wl_pointer.set_cursor(null)`. Elsewhere `movementX/Y` of a move are 0.
- **Input methods other than macOS's.** Windows (TSF or IMM32) and Linux (ibus, text-input-v3) report `isComposing` false and fire no `Process` keydown or composition events, and their composition keys go to the input method before GPUI sees them. On macOS a value an app sets while a composition is open ends it without a `compositionend`.
- **`code`, `key`, `keyCode` and `which` off macOS** come from GPUI's key name assuming a US layout, because the other platforms leave `NativeKey` empty. They have the physical key at event creation (the Windows scan code, the xkb keycode) and each needs a table like `events/key_codes.rs`.
- **File picker `accept`** works on macOS and goes through the portal filters on Linux, which are implemented and untested. Windows ignores it: `file_open_dialog` never calls `SetFileTypes` for an open dialog. It needs a `COMDLG_FILTERSPEC` list built from `PathPromptOptions.filters`.
- **`EyeDropper`** exists on macOS only. Its abort has no cancel call (`NSColorSampler` has no dismiss API), so the magnifier stays up until the user clicks or presses Escape; nothing to build there. Windows has no system picker (it would be a custom overlay reading the screen), and Linux could use the portal's `Screenshot.PickColor`.

### Text

- **Per-run `fontSize` goes through CoreText only.** The macOS shaper builds a font per run; the other shapers still shape every run at the line size.
- **Line box metrics are macOS-only.** `gpui_wgpu` and `gpui_windows` accept the window scale and ignore it, and their shapers still report unrounded ascent and descent. `widens_ascent` is set by `gpui_macos` from the face's family name.
- **Font smoothing.** Only the macOS rasteriser reads `Antialiased`; the Windows and wgpu text systems ignore it, as they ignore the luminance bucket.
- **Font variations** are macOS only.

### Paint and transforms

- **Effects exist on macOS (Metal) only.** On wgpu and DirectX the groups draw flat and only opacity applies (`Platform::supports_effect_groups()` is false there). It is a port, not a limit: the group pass (texture pool, resample, colour matrix, blur, drop shadow, mask, clip-path and composite) is about 660 lines of Rust and 235 of Metal in `gpui_apple`. wgpu needs the same passes in WGSL (WebGL2 takes its own shader variant), DirectX 11 in HLSL, roughly a thousand lines of Rust and a few hundred of shader per backend, written on that platform.
- **The Quad shaders are unverified off macOS, and that is more than effects.** The fork rewrote them on every backend for rounded content masks, per-side border colours and styles, elliptical corners, gradients and background tiles: about +300 lines of WGSL (plus 76 for WebGL and 19 for the subpixel shader) and +300 of HLSL. The HLSL is compiled by `gpui_windows/build.rs` (fxc) only on a Windows host and has never been built; the WGSL was validated with naga and never rendered. Gradients, per-side borders and their styles, elliptical corners and rounded `overflow` clipping are as unproven on Windows and Linux as effects are. Checking them needs a Windows host (fxc build, then GPUI's render tests) and a wgpu run.
- **The transform shaders read the 6-float matrix.** The wgpu (WGSL) and DirectX (HLSL) shaders take the affine matrix and not the homography, so perspective is drawn on macOS (Metal) only.

### Motion

- **`measureMotionAnimation` is not registered in the browser (wasm) entry**, so `duration` and `iterationDuration` of an `animate()` control throw there before the value is bound to a renderer.
- **Reduced motion: the OS setting is read on macOS only.** Windows has `SPI_GETCLIENTAREAANIMATION` and `SPI_GETHIGHCONTRAST` with `WM_SETTINGCHANGE`, and Linux the portal or gsettings `enable-animations`, a small read each.

### Window

- **Linux has no drag threshold:** the window menu or the move starts on the press, with no wait for movement.
- **No `system-context-menu` event.** Electron lets a page cancel the system menu on Windows and Linux; here the OS owns it on Windows, and on Linux a right press opens the window menu with no hook.
- **The `screen` displays are macOS only.** `screen.getAllDisplays()` and `getPrimaryDisplay()` throw "only implemented on macOS" elsewhere (and in the browser build). Windows and Linux place the window at (x, y) in whatever space their platform uses.

### `<webview>`

- **Windows, Linux and wasm have no `<webview>`.** The element is an empty box that logs a warning once, its methods throw (`executeJavaScript` rejects), and no page is made: `PlatformWindow::create_native_surface` refuses where the platform cannot compose, and `draw_composed` defaults to a plain `draw`. Closing the gap takes a native engine view and the layer cut on each platform (`composition.rs` in gpui is platform independent; `gpui_macos`'s `window/composition.rs` and `gpui_apple`'s overlay renderer are the macOS half).
