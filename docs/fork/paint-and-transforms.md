# Paint and transforms

How a box is painted (clipping, borders, backgrounds, effect groups, opacity, colours, `<svg>` and `<img>`, masks, `clip-path`, outline, the universal style) and how CSS transforms, in two and three dimensions, are drawn, hit, measured and animated (#92). Paint is "Area D" in older notes. The `StyleDesc` fields live in `packages/native`, CSS strings are parsed in `packages/native/src/css/`, and the painters are in the zed submodule (`gpui`, `gpui_apple`).

## Clipping, borders and corners

- **`overflow` clips to the padding box** with rounded inner radii (zed rounded content masks), also when the border is transparent.
- **Borders.** Per-side colours, widths and line styles (`solid`, `dashed`, `dotted`, `double`, `groove`, `ridge`, `inset`, `outset`), the `border*` shorthands, and per-corner radii on every painted part. A side that no declaration gives a line style is `none`, as in CSS: a `none` or `hidden` side has width 0, so a width alone draws nothing, and a visible style with no width is `medium` (3px). `borderColor` is the shorthand of four side colours, which `motion` and CSS transitions animate separately.
- **Radii are elliptical**: `a / b`, a two-value corner longhand, a percentage per axis. This holds for quads, shadows, content masks, effect-group clips and hit testing. A corner's inner edge is the outer ellipse less the adjacent border widths per axis, as in CSS. A radius string is a CSS length like any other (`px`, the absolute units, `%`, `em`, `rem`, the viewport units and `calc()`), and `motion` animates both radii of a corner. An invalid or negative radius throws when the style is committed, as an invalid width does, where `boxShadow` and `clipPath` ignore an invalid string.
- **Nested `overflow` clips are exact on macOS where they can be.** An inexact pair (a child's corner inside the parent's cut-away corner, or mixed elliptical radii at a shared corner) paints through an identity effect group under the parent's mask, one offscreen pass; hit testing keeps each clip separately. Still approximate: platforms without effect groups, a box inside the clip that escapes it, and a positioned box the clip contains (painted by its stacking context with the prepaint clip).
- **A one-axis clip is a plain rectangle**, as in Chromium (csswg-drafts#7434). `overflow: clip` beside `visible` cuts only the clipping axis (square, unbounded on the other); `hidden`, `scroll` or `auto` beside `visible` compute it to `auto` (CSS Overflow 3).
- **Hit testing follows the shape.** `clipPath` clips hit testing and `borderRadius` cuts the hit area of the box itself; both are described in [events-and-input.md](events-and-input.md).

## Backgrounds and shadows

- Linear, radial and conic gradients (plus the repeating forms) with any number of stops, colour hints and `in oklab`; multiple layers; `backgroundImage`, `Size`, `Position`, `Repeat`, `Origin`, `Clip` and the `background` shorthand; `backgroundClip: "text"`.
- `boxShadow` is a CSS string with multiple layers and `inset`. It is parsed when a style is deserialized; caching it measured no gain.
- **`url()` in `background` / `backgroundImage`** paints, mixed with gradients (position, size, repeat, origin, clip, `backgroundClip: text`). It loads as an `<img>` `src` does and paints nothing until loaded, or if the load fails (logged once). `blob:` URLs are fetched in JS and handed over with `setStyleImage` / `failStyleImage`. A hover image starts loading when the hover first applies.
- **A state style's shorthand resets the longhands it covers** (`background`, `overscrollBehavior`, `gridArea` / `gridColumn` / `gridRow`, `border*`, `borderColor`, `mask`, `outline`, `textBox`, and the layout box shorthands), so a hover `background` replaces every layer longhand, as in CSS. `overlay_fields!` in `events/state_styles.rs` is the list of every `StyleDesc` field that takes part in state styles.

## Effect groups

Effect groups (zed `effects.rs`, `gpui_apple`) are `filter`, `backdropFilter`, `maskImage`, `clipPath` and `opacity` that composites the element as a group. A subtree that paints one primitive keeps the cheap per-primitive path.

- **`clipPath`** takes `inset()`, `rect()`, `xywh()`, `circle()`, `ellipse()`, `polygon()` and `path()`. A `mask` or `clip-path` with an unsupported value is invalid, as in CSS, instead of falling back.
- **Masks** are a list of `BackgroundLayer`s, each with a `mask_mode` and a `mask_composite`; zed draws each layer into its own texture and runs a combine pass only when some layer is not alpha + add. A layer is a gradient or an image (a path, `file://`, `data:`, `http(s):`, `blob:`, loaded like `url()` backgrounds). `maskMode` (`alpha`, `luminance`, `match-source`) and `maskComposite` (`add`, `subtract`, `intersect`, `exclude`) are longhands or part of the `mask` shorthand. An unloaded or failed image is a transparent layer, so the element is hidden whole, as in CSS.
- **`mask-border` is the top mask layer, added.** `maskBorder` and its six longhands draw a nine-slice of a gradient or `url()` image (`Style.mask_border`, zed `mask_border.rs`) as one more layer composited with `add`: Chrome's `-webkit-mask-box-image` unions with the `mask-image` layers, it does not intersect. The oracle is that prefixed property, because Chrome has no unprefixed `mask-border-*`; the names and initial values follow the spec where the two differ (`slice` starts at `0` and the shorthand does not imply `fill`; `mode` starts at `alpha`, which is also all Chrome reads). A gradient source is laid out for each slice's scaled size, not warped with it, so a radial one keeps its circle and an angled one its angle. The `mask` shorthand resets `maskBorder` and its longhands, as CSS Masking says it does.
- **The Metal polychrome sprite shader clamps its lookup to the sprite's tile** so a crop does not blend in its neighbour. Keep this when touching the sprite shader: `mask-border` slices depend on it.

## Opacity

- **`opacity` composites the element as a group.** A subtree that paints one primitive keeps the per-primitive path.
- **`opacity: 0` paints nothing.** The contents are painted with the scene hidden, so no primitive is inserted or recorded and a replay inserts none. Painting them into a group thrown away at its end rasterised and looked up every glyph (about 7.5 µs a text on a built frame, 2 to 4 µs when replayed). Hitboxes, listeners, cursor styles, tab stops, accessibility nodes, canvases, the text registry, selection and find run as before, so the element keeps its box and is hit, as in Chrome. The fade composes with `visibility` (a visible element inside an `opacity: 0` one stays hidden, and the one after it shows again), and prepaint sees it, so a subtree recorded faded out is not replayed once it shows.
- **An opacity run is an effect group for the whole run.** In Web Animations an element with a current animation of a property acts as `will-change` of it, and Chrome keeps its compositor layer. So while an animation or transition of `opacity` is current the element paints its group at whatever value it samples, 0 included, and its operations keep their shape from one tick to the next.
  - gpuix (`animate_style`): `StyleDesc::animating_opacity` is set while a CSS animation that is current (active, or before its active phase going forward, not one that only fills), a running CSS transition, a `motion` track or a moving motion value targets `opacity` (`opacity_runs`). `has_effect_group` reads it, so `lift_z`, `creates_context` and `Resolved` all see an effect group at any sampled value.
  - zed: `Style::has_active_opacity_animation` makes `group_effect` return a group at 1 and keeps the element's scene at 0. A static opacity is as it was: 1 has no group, 0 paints nothing.
  - What an opacity run does to patched ticks is in [patch-frames.md](patch-frames.md).
- **The `opacity` of an inline box** is a compositing group (`OpacityGroup`, painted by `text/paint.rs` through `TextLayout::paint_group`) that paints after the text around it. Selection and find washes stay under it, and an atomic inline in it is not faded.

## Colours

- `currentColor`, `light-dark()` (through an inherited `colorScheme`), `color-mix()`, `color()` in all CSS colour spaces, and named colours. The default text colour follows the scheme.
- **A hovered `color` reaches descendants' `currentColor`.**
- **A style value is parsed with a `ColorContext`.** `light-dark()`, `currentColor` and `color-mix()` cannot be resolved without one, so `apply_styles` takes `&ColorContext`, a state refinement uses `for_state`, and children get `descend`. `parse_color_rgba` has no context and none of those functions: do not call it on a style value.
- **Motion colours resolve through `ColorContext`.** Targets and keyframes (motion, CSS transitions, CSS animation keyframes, `<svg>` `fill` / `stroke`) take `currentColor`, `light-dark()`, `color-mix()` and `color()`, resolved in the element's own context (`currentColor` for `color` itself is the parent's). A new `color`, `colorScheme` or window appearance resolves them again and the track runs to the new colour. A static `<svg>` `fill` / `stroke` that uses those functions is written as `rgba()` in the svg's context. An animated `<svg>` shape changes hue through `SvgPaint::image`, which keeps one image and drops the previous one from the atlas, so an `<svg>` holds one atlas entry, not one per frame.

## `<svg>` and `<img>`

- **SVG rasterizes with resvg at device scale in its own colours**, and `currentColor` resolves to the element's `color`. Shapes with no fill paint black, and the content clips to the border radius.
- **The ink of an `<svg>` is its box.** It draws one image fitted to its box, `overflow: visible` included, so `build_element` takes `Subtree::of_element(empty, style)` for it in place of `block` (the box plus what its own style adds; a positioned `<svg>` still blocks) and the element calls `cullable`. In a culled subtree its canvas makes no image and starts no job (`SvgPaint::note_culled`; `retain_state` is 1 after such a paint, so an `<svg>` never shown is not an unsettled raster).
- **It rasterises off the frame by size.** A document up to 4 KB drawn up to 128x128 device px rasterises in paint (`svg_paint.rs`: `INLINE_BYTES`, `INLINE_PIXELS`). Anything bigger rasterises on the background executor, one job at a time per `<svg>`, drawing the previous raster stretched until the new one lands. A running resvg job cannot be cancelled, so a changed key waits for it, and a big `<svg>` that has not rasterised yet draws nothing on its first frames.
- **A running document is rasterised in the paint, whatever its size** (`CustomElement::shapes_run`, `Key::in_paint`), so `draws_changes_at_once` holds and its ticks are patched. A static large `<svg>` keeps the job.
- **Shape children** serialise the shapes, what they refer to by id (gradients, `clipPath`, `mask`, `use`, `symbol`, `pattern`, `marker`, `filter` with its `fe*` primitives), `image` and `text` / `tspan` / `textPath`; the vocabulary is `custom_elements/svg_names.rs`. `<text>` inside an `<svg>` is told from the host `text` by position. `<image>` takes `data:` URLs, `file://` URLs and paths, not `blob:` or `http(s):`, because the svg rasterises without waiting for a load.
- **The shapes sleep with the `<svg>`.** A shape is never built, so a running shape named the shape in `Sources::motion`, which `holds` could never find culled. `running_motion` names the `<svg>` (`svg_tree::host_of`), and the clocks of its shapes enter and leave dormancy with it (`with_shapes`), so `animationiteration`, `animationend` and `getAnimations()` of a shape come at the ticks of a shown one.
- **Motion on shapes.** `<svg>` takes DOM-style shape children (`<path>` and friends); `pathLength`, `strokeDasharray` and `strokeDashoffset` draw, and `d` morphs. An `<svg>` with shape children ignores `source` / `src`, and its `width` / `height` props size the svg box.
- **`<img>`** gets `onLoad` (with `naturalWidth` / `naturalHeight`), `onError`, and `file://` and `blob:` URLs.

## Outline

`outline` (`width || style || colour`, any order) and `outlineStyle` are CSS's: the style is `none` unless one is given, the width `medium` and the colour `currentColor`, so a ring needs a style. The style reaches the painted outline (`gpui::Outline.style`, a zed commit), so `dashed`, `dotted` and `double` draw. `outlineOffset` is not part of the shorthand, and a state's `outline` resets the base's width, style and colour.

## Universal style

`setUniversalStyle(style | null)` (and `<UniversalStyle>` in the React and Solid adapters) is a fork addition equivalent to `* { ... }`: one style applied under every element, at the lowest precedence per property, to elements mounted later as well. It is not inherited, text nodes are not matched, and it is not a stylesheet (no selectors). Edge: when the layer is the first to add `transition` to an element that has no style of its own, a colour set in that same change applies at once instead of transitioning.

## Rounding of painted geometry

The rounding of painted geometry (box edges, underline origins, glyph subpixel quantisation, emoji and svg sprites) is translation-covariant: a shift by whole device pixels moves the result by that shift, with the bytes of positive results unchanged. That is exact only at a scale factor that is a power of two (1, 2, 4), where a position shifted by whole device pixels is exactly the shifted position, so at any other scale factor a retained recording does not relocate (see [retention.md](retention.md)).

## Cost

- A `Quad` is 452 bytes where upstream's is 160 (gradient data in `Background`, per-side border colours, styles and inner colours, and the vertical corner radii), and path vertices grew from 34 to 56 words. The impact is upload bandwidth only: 292 bytes more per quad, so 5,000 quads add about 1.5 MB a frame, with no shader cliff. Tile culling and a cap on tiles per layer bound image layers.
- Gradient (so background and mask images), filter and clip-path strings go through a bounded per-thread parse cache keyed by the text and, when the text reads `currentColor`, `light-dark()` or `color-mix()`, by the colour context, and when it reads `em`, `rem` or a viewport unit, by the length context (`css/cache.rs`). A 500-element grid of three-layer gradients builds its frame in 3.9 ms instead of 6.7 ms.

## CSS transforms (#92)

GPUI drew only translations (`Window::with_element_offset`) and gave only SVG and glyph sprites a matrix, so gpuix had no `transform`, `scale` or `rotate`, and a motion component could not slide, scale or turn without animating `top`, `height` and insets (a layout on every tick) or a JS tween that wrote a style per frame. Transforms move and turn boxes in paint, hit testing and geometry reads without a layout pass.

Scope: macOS and Metal only (no wgpu, HLSL or WGSL). A pure translation draws a box where layout snaps it, moved by exactly the translation, as Chrome does ([A translation is not rounded](#a-translation-is-not-rounded)). Motion's transform keys and CSS transitions and animations of `transform` ship with it, and their ticks patch. The 3D functions, `perspective`, `transform-style` and `backface-visibility` run through the same path ([Three dimensions](#three-dimensions)). What Chrome does that this does not (a depth sort of planes, `element.animate()`) is in the [deviations](deviations.md#paint-and-transforms).

### What is supported

| Surface | What it takes |
|---|---|
| `transform` | `none`, or a list of `translate()`, `translateX()`, `translateY()`, `translate3d()`, `translateZ()`, `scale()`, `scaleX()`, `scaleY()`, `scale3d()`, `scaleZ()`, `rotate()`, `rotateZ()`, `rotateX()`, `rotateY()`, `rotate3d()`, `skew()`, `skewX()`, `skewY()`, `perspective()`, `matrix()` and `matrix3d()`. Lengths are px, `%` (of the element's own border box), em, rem, vw, vh and `calc()` of them; angles are `deg`, `rad`, `grad`, `turn` and a bare `0`, or a `calc()` of them (sums of angles, products and quotients by numbers). `var()` is accepted in all of these ([below](#custom-properties-and-calc)). `perspective()` takes `none` or a length from 0 up, a z has no percentage, and an invalid value is ignored as a whole, as in CSS. |
| `translate`, `rotate`, `scale` | The individual properties. `translate` takes a length along z as a third value; `rotate` is a string angle, a number of degrees or an axis (`x`, `y`, `z` or three numbers) and an angle; `scale` is one to three numbers or percentages, or a number. |
| `transformOrigin` | One or two of `left`, `center`, `right`, `top`, `bottom`, lengths and percentages and a length along z; `50% 50%` by default. |
| `perspective`, `perspectiveOrigin` | `none` or a length from 0 up (a number is px), and the point of the border box the viewer looks at (`50% 50%`). Not inherited. |
| `transformStyle`, `backfaceVisibility` | `flat` / `preserve-3d` and `visible` / `hidden`. Neither is animatable. |
| Motion keys | `x`, `y`, `z`, `translateX`, `translateY`, `translateZ`, `scale`, `scaleX`, `scaleY`, `scaleZ`, `rotate`, `rotateX`, `rotateY`, `rotateZ`, `skew`, `skewX`, `skewY`, `transformPerspective`, `originX`, `originY`, `originZ` as `style`, `animate`, `initial`, `exit`, `variants`, keyframe lists, springs, gestures and motion values. `x`, `y`, `z` take a number (px) or a CSS length; `rotate`, `rotateX`, `rotateY`, `skew` take degrees or a CSS angle (a motion value too: `"0.25turn"`); `originX` / `originY` a fraction of the border box or a CSS length; `originZ` and `transformPerspective` px. |
| Motion `transform` | A CSS transform list or `none` as a target (`animate`, `initial`, `exit`, `variants`, keyframes, gestures) or in a motion value bound to `transform`. Its own key: when it is set it is the list and Motion's keys beside it are ignored. |

### Composition

CSS Transforms 2: around the origin, `translate`, then `rotate`, then `scale`, then the list (matrices multiplied in that order, each applied to what the ones after it placed). The list is, in this order, Motion's `transform` target (`StyleDesc::motion_transform`, wire `motionTransform`) when one is set, Motion's keys when any is present, or `transform`. A Motion list replaces `transform`, as `buildTransform` writes into it, and a Motion `transform` replaces the keys, as `buildHTMLStyles` builds nothing from them when `latestValues.transform` is set (`none` counts as set). Motion's order is `perspective(transformPerspective) translateX(x) translateY(y) translateZ(z) translateX translateY translateZ scale(scale) scaleX scaleY scaleZ rotate(rotate) rotateX rotateY rotateZ skew skewX skewY` (motion-dom 14.1.0), and a key at its default is left out of the string as `buildTransform` leaves it. `originX` / `originY` / `originZ` override `transformOrigin` per axis. `perspective` is not a Motion key: on a motion component it is the CSS property of the element, which `animate` and the transitions tween (`AnimProp::Perspective`, with `perspectiveOrigin`).

- A transform other than `none`, a `perspective` other than `none` or a declared `transform-style: preserve-3d` makes the element a stacking context (painted in the `z-index: 0` layer) and the containing block of its absolute and fixed descendants (Chromium's `CalculateIsStackingContextWithoutContainment` and `ComputeIsFixedContainer`: the declared `preserve-3d` counts even where a grouping property makes the used value `flat`; `backface-visibility` makes neither). An identity value (`translateZ(0)`, `scale(1)`) does both too; `none` or an invalid value does neither. Motion keys that are all at their defaults (`x: 0`, `scale: 1`) are `none`, as Motion writes `transform: none` for them: no context and no containing block until a key leaves its default. A list set through Motion's `transform` is a context even when it moves nothing, as `translateX(0)` is.
- It changes no layout: margins collapse through a transformed box as without it.
- A non-atomic inline box takes no transform, as in CSS; the keys on a `<span>` are accepted and ignored.
- State styles (`hover`, `focus`, ...) register all the keys.

**Wire names.** The JS motion components rename a static `scale` and `rotate` in `style` to `motionScale` and `motionRotate` (`motionComponentStyle`), so Motion's `scale: 1.2` does not meet the CSS property of the same name. A motion value keeps its key, and the native motion contexts (`animate`, `initial`, `exit`, variants, keyframe arrays, motion-value bindings) read `scale` and `rotate` as Motion's, and `transform` as Motion's `transform` (`AnimProp::MotionTransform`, wire `motionTransform`), which is not the static `style.transform`: that one is replaced by Motion's keys and by Motion's `transform`. On a plain element `scale` and `rotate` are CSS. CSS keyframes (`defineKeyframes`) and transitions take the CSS properties (`transform`, `translate`, `rotate`, `scale`, `transformOrigin`); Motion's keys are not CSS properties, and `transition: all` leaves them alone.

### A translation is not rounded

Chrome adds the translation of `transform`, `translate` and Motion's `x` to the snapped paint offset of the element: the box is where layout rounds its own position to (parent and `left` together, to a device pixel), moved by exactly the translation, and a fractional translation antialiases the edges. `will-change: transform` and `translateZ(0)` are drawn the same. Text is on a subpixel position, as it is for a fractional `left`. `transform-snap-oracle` (528 boxes at two scales, a background, a border or both, parents at 0 to 1.7 px, a `left` of 0 or 0.3, translations of -0.6 to 559.6; #109) pins the rule, and `transform-snap.test.tsx` holds gpuix to it within a tenth of a device pixel. A box moved by `left` has the edges of its whole position rounded, so the two differ by up to a pixel: a thumb at `left: 0; x: 559.6` in a parent at 11.3 has its edge at 570.6, and `left: 559.6` at 571.

gpuix added the translation rounded to a whole device pixel to the snapped bounds, so the thumb was drawn from 571 and a box moved by `x` was up to half a device pixel off, and stepped by whole pixels while it animated. Now a translation by a whole number of device pixels (to 0.01) is the translation path above, byte for byte as before, and one by a fraction is a general transform (`TransformKind::General`): the primitives carry the translation as their matrix, the quad shader antialiases its edges, text is rasterized through it on a subpixel position and a content mask pushed inside is a local clip. While a translation animates, its text moves by whole device pixels (a glyph on a new subpixel position at every tick is a raster at every tick, `patched-clipped-text.test.tsx` counts them), as the box beside it moves by the exact translation, and the text takes the exact position when the animation ends. The cost is that a subtree under a fractional translation is not relocated when a scroll moves it, but built, as under any general transform.

### GPUI

- **`Window::with_transform(matrix, f)`** composes onto the ambient transform (logical px, local space to window space), and every painter and prepaint inside it reads it. Each push is classified: identity, translation only, or general. It takes a 4x4 and the `preserve_3d` flag of the parent ([Three dimensions](#three-dimensions)), and a matrix with perspective is a general one.
  - *Translation only* (the composed transform is a pure move by whole device pixels, to 0.01): every `paint_*` adds the translation, in whole device pixels, to the logical bounds before snapping, and the primitive keeps an identity matrix. Content masks pushed inside are mapped into window space. The output is byte-identical to the same content placed there, so text stays sharp (`transform-paint.test.tsx`, "draws a translated line of text exactly as the same text placed by an offset"). A translation by a fraction of a device pixel is a general transform ([below](#a-translation-is-not-rounded)).
  - *General*: quads, shadows, underlines, sprites and paths carry the matrix in device px (the scale factor folded in); their bounds, radii and borders stay in local device px. Paths bake the matrix into their vertices. Glyph sprites are the exception, see "Text" below.
- **Clip model.** A primitive's `content_mask` stays in window space (hardware `clip_distance` on the transformed vertex, rounded coverage at the window fragment position), as for untransformed content. `with_content_mask` under a general transform goes into a separate `local_clip` in the primitive's local space, which the fragment evaluates with the local position. Entering a general transform inside another one with a local clip maps that clip exactly into the new space when the relative matrix only scales and moves; otherwise the clip is replaced by its bounding box in window space, intersected into `content_mask`, with its corner radii dropped. That is the one loose place (see the [deviations](deviations.md#paint-and-transforms)). The window mask is never intersected with the bounding box of a local clip, so hitbox and primitive masks stay the same from one tick to the next.
- **Shaders** (`shaders.metal`: quads, shadows, underlines, monochrome and polychrome sprites). Under a non-identity matrix the vertex stage grows the local quad by one device px (in local units, `1 / scale_factor`) and maps it through the matrix; the fragment computes the box SDF, rounded corners, borders, dashes and the local clip in local coordinates and antialiases over `0.5 / scale_factor` local px. A transformed quad never takes the pixel-aligned fast path, so straight edges are antialiased. An untransformed primitive runs the same code with an identity matrix. Under perspective the vertex stage outputs a homogeneous position and the pixel scale comes from derivatives ([Three dimensions](#three-dimensions)).
- **Surfaces and groups.** Effect groups (opacity, filter, mask, `clipPath`) cover the bounding box of their transformed content; `clipPath` polygons are mapped through the matrix (a rounded rectangle or an ellipse under a rotation becomes a polygon); mask layers rotate exactly.
  - *Surfaces.* A `PaintSurface` carries the `transformation` and `local_clip` of a quad, and its shader uses the same `transformed_vertex` (the texture coordinate comes from the unit position, clamped), so a surface under a rotation is the image rotated and its coverage is the rect times the local clip times the window mask. Pinned equal to a rotated image of the same pixels by a `gpui_apple` pixel test.
  - *`backdrop-filter`.* The group's reference box stays the border box in the element's own space (`GroupEffect::reference_transformation`), and the composite evaluates its rounded rectangle in local space (inverse matrix, local rect and radii in `CompositeParams`), so the backdrop is cut to the rotated, rounded outline of the box and not to the bounding box of it.
  - *Blur follows the matrix, for `filter` and `backdrop-filter` alike*, because Chrome filters in the element's own space and transforms the result: `ResolvedFilter::Blur { x, y }` is scaled per axis when the matrix keeps the axes apart (a scale, or a quarter turn of one) and by the square root of the area scale otherwise (a rotation, a skew), which is what the Chrome oracle fits; a `drop-shadow()` moves by the matrix and blurs by that square root. A separable blur along the window's axes cannot follow a turn, which is why the general case is a single sigma.
- **Text.** A glyph is rasterized through the 2x2 part of the ambient matrix, so rotated, skewed and scaled text is as sharp as Chrome's: `RenderGlyphParams` carries it quantized to 1/4096 (`GlyphTransform`; identity for untransformed and translation-only text, which stays byte-identical). The macOS rasterizer takes the raster bounds through it and concats it into the CoreGraphics CTM around the glyph's origin. The tile is then drawn upright in window space at the origin the matrix maps the glyph to: with the subpixel variants of the axis the baseline lies on when the matrix keeps it on one (scales, flips, quarter turns), at a rounded origin otherwise, as Skia does. The local clip is still evaluated in local space: a sprite carries the window-to-local matrix (`clip_transformation`) its fragment finds the clip through. Chrome keeps CoreGraphics smoothing under every transform, so `-webkit-font-smoothing` means what it means untransformed, and `scale(2)` text equals the text at twice the size to the pixel (oracle). A glyph too big to rasterize through its matrix (1024 device px) takes the animating path below. An emoji of Apple Color Emoji is drawn at the device size (`draws_at_device_size`, [text.md](text.md#advances-of-a-fallback-font)), which is not in proportion to the size (a 16 px disc is 10, 20, 32 and 64 px wide at scale 0.5, 1, 2 and 4), so a bucketed raster does not ask for the window's scale times the bucket (the emoji of a larger size): `Window::paint_emoji` asks for the window's scale with the bucket as a uniform `GlyphTransform`, and the sprite drawn back at 1/bucket is the upright emoji, whatever the bucket. Under a 2D matrix the emoji comes out where and as large as the upright one transformed (the ink box within 0.5 px, the centroid within 0.35 px at rotations of 30, 90, 180 and -45 degrees and scales of 1.5, 0.5 and 2 x 0.75, at both window scales); rotated emoji are as sharp as the resampled upright tile, and enlarged ones sharper (1.4 to 2.5 times the edge steepness), but a shrunk one (0.5) is more aliased than the resampled tile, as CoreGraphics draws a bitmap font through a minifying matrix.
  - *Animating* (`ElementTransform::animating`, ORed down the ambient stack by `Window::with_transform_animating`): the glyph is rasterized at `animating_raster_scale` of the matrix, its scale rounded up to the next power of root two within [1/4, 8], and drawn through the matrix. Chrome rasterizes an animating layer at a fixed scale and rasterizes it again when the animation ends; here the raster is made again when the bucket changes (a few times per animation, not per tick) and once the run ends, when the text takes the static path. gpuix sets the flag from `StyleDesc::transform_in_motion`: any run of the transform on the element or an ancestor (CSS animation or transition, Motion track, motion value). It is not `animating_transform`, which stacking reads and which counts CSS runs only (see "`animating_transform`" below).
- **`Style::transform`** (`Option<ElementTransform>`, `None` = unset, `none` = `Some` with no functions so a state style can clear the base) is resolved by `Div`, `List` and the elements on `Interactivity` from the unsnapped border box layout computed, not from its pixel snap, in prepaint and in paint, and wraps the element's hitbox, background, border, shadow and children in `with_transform`. `Style::contain_positioned` makes a box the containing block of fixed and absolute descendants without the rest of layout containment (what a transform needs). gpuix decides stacking contexts itself; GPUI infers none. The layout engine keeps each node's transform (stored at `request_layout`, compared in the node's meta so a change bumps the extent epoch) for scrollable overflow.
- **Hit testing and events.** A `Hitbox` keeps the space it was inserted in (`to_local`, the window-to-local matrix of the ambient transform, rounded to device px for a translation; none for a matrix that flattens the plane, which hits nothing) and the local clip. `contains_point`, `Frame::hit_test`, `dom_hit_test` and the clip-path test of `ClipIndex` test each hitbox in its own space; `Hitbox::to_local`, `window_bounds` and `contains_window_point` are public, and `Window::hit_chain_entries` gives the space of each link. A mouse listener keeps the space it was registered in and is given the event with its position mapped (`MouseEvent::with_position_mapped`: move, down, up, wheel, pinch, drop), so `clientX` is in the window and `offsetX` in the target. `Div` and `InteractiveText` compare the pointer with their hitbox through the space. `Window::mouse_position` stays in the window.
- **Deferred draws are still the element in place.** `Window::defer_draw` captures the ambient transform stack (and the local clip, when a content mask is given), and the deferred passes restore it as `paint_lifted` does, so the draw is prepainted and painted inside the transforms it was deferred in, under its content mask in both passes, and its hitboxes and listeners get the hit space of the transform. A draw deferred inside a transform that flattens the plane paints nothing. The layout glide's lifted drag (`layout_flip`) is deferred this way and so keeps turning with the transforms of its parents. Content that lives elsewhere in the tree opts out: `Deferred::in_window_space` draws the child in window space, and `Anchored::reference_in_deferral_site` places a child of such a draw against the bounding box in the window of its layout parent (or of the corner it sits at), the box floating-ui reads with `getBoundingClientRect`. `Anchored` fits, flips and snaps against the window in the space it is placed in: in a transformed space that is the bounding box of the viewport taken back through the matrix.
- **Skew.** `SkewX` and `SkewY` are their own `TransformFunction`s that pair only with their own kind; the 2D matrix decomposition used by `Interpolated` orthogonalizes the second column (Gram-Schmidt), so a shear blends as a shear.

### gpuix

- **Parsing and apply** (`css/transform.rs`, `Parts`): the seven CSS properties of the transform (`transform-style` and `backface-visibility` are read beside them) and Motion's keys are parsed once per distinct value (`Cache`), resolve em / rem / vw / vh with the element's `LengthContext`, and become one `ElementTransform`, which `apply_styles` puts on the GPUI style. `Parts::is_active` says whether the element has a transform in CSS's sense; `layout/stacking.rs` (`creates_context`, `lift_z` at 0, like an effect group) and `layout/containing_block.rs` (`contain_layout`, `containing_block::contains_fixed` for the retained walks) read it, so `RetainedTree::elements_at` models the same contexts.
- **Motion.** `AnimProp`s for every Motion key (numeric, length and angle kinds), `AnimProp::MotionTransform` for Motion's `transform` and `AnimValue::Transform` for `transform`, `translate`, `rotate` and `scale`; CSS transitions, `@keyframes`-style animations, `motion` tweens, springs and keyframes, motion values and Web Animations accept them. Motion's keys are positional for reduced motion (they jump, as Motion's transform animations are disabled), CSS transforms are not.
  - *Angles.* A motion value holds an angle (`"45deg"`, `"0.25turn"`, `"1rad"`, `"100grad"`, `AnimValue::Angle`) for `rotate`, `rotateZ`, `skew`, `skewX` and `skewY`, in degrees (`"0.5turn"` reads back `"180deg"`); bound to another key an angle is skipped. A number and an angle mix in degrees (`0` to `"1turn"` is `"180deg"` halfway, where Motion mixes them to `NaN`).
  - *The `transform` target.* A Motion `transform` is its own `AnimProp` (`"transform"` on the motion contexts, `motionTransform` on the wire, `StyleDesc::motion_transform`), blended with the CSS transform blend (function by function, then as matrices; Motion animates it with WAAPI, which does the same). Motion reads a `transform` it has not animated from the element's: the list its keys or the style's `transform` made. A motion value holding a transform string (`"translateX(10px) rotate(45deg)"`, `"none"`) bound to `transform` drives it; two lists blend as a CSS transition does.
- **Paint-only.** A change of a transform value is paint-only (`differs_only_in_paint`) as long as "has a transform" does not flip; a flip changes the containing block, so it is layout. Every transform `AnimProp` is in `paints_only`, so the ticks patch. A text that reads a `var()` is never assumed to keep "has a transform", so a change of that text is layout; the same text with another `--x` is paint (below).

### Three dimensions

A card flip, a tilted panel or a carousel that recedes are transforms with a third axis, and they are drawn, hit and measured by the same path as the 2D ones: Chrome's model (CSS Transforms 2) on the existing matrix stack, with Chromium's source as the reference where the specification leaves a choice. The Chrome oracle puts every box within 0.06 px.

- **A primitive carries a projective 3x3.** `TransformationMatrix` is the z = 0 plane of a 4x4 (rows and columns 0, 1 and 3 of it), so everything that already took a matrix (quads, shadows, underlines, sprites, surfaces, paths, clips, hitboxes) takes a homography. A matrix whose bottom row is `0 0 1` is affine and draws as before, byte for byte. Under a homography the vertex stage outputs the homogeneous position with `W` as the clip `w`, so the hardware divides, interpolates the local position in perspective and clips what is at or behind `W = 0` (z is 0); the clip distances are the distance times `W`, which is linear in clip space. The fragment antialiases over the side of the square a pixel covers in local space, found from the derivatives of the local position (`fragment_pixel_scale`), where an affine matrix uses its flat scale; the quad is grown by a pad larger than that, since it varies along an edge. The backdrop reference and the surface shader divide the same way.
- **Behind the eye.** A point whose `W` is under `MIN_W` (1e-3) is at the horizon or behind it and is not on the plane. `TransformationMatrix::project` returns none for it, the bounds of a box are those of its outline cut at `MIN_W` (`clipped_outline`, Sutherland-Hodgman against one plane; a box all behind the eye is empty and paints nothing), paths and `clip-path` polygons are cut in their own space before their points are mapped, and a hit test maps the pointer through the 3x3 inverse with the divide and misses where `W` is under `MIN_W`. A path's vertices are mapped projectively, so its edges are exact and the control points of its curves are not.
- **An element is an `ElementSpace`.** Beyond its `transform` (now a 4x4 `Matrix3d`, with `TransformFunction` variants `Translate3d`, `Scale3d`, `Rotate3d(axis, angle)`, `Perspective` and `Matrix3d`, and `ElementTransform::origin_z`), an element has a `perspective` and `perspective_origin` for its children, `preserve_3d` and `backface_hidden`. `Window::with_element_space` pushes all of it onto the ambient transform, and `layout_own_space` / `layout_to_window` give a layout node's space for geometry reads. The ambient is a 4x4 and the 3x3 it flattens to.
  - *In a flat parent* the element's 4x4 is flattened onto the parent's plane: the matrix its primitives are drawn through is the parent's, times the z = 0 plane of the element's 4x4 with the parent's perspective in front of it (`perspective` is not inherited: it goes in front of each child's transform and reaches no grandchild).
  - *In a `preserve-3d` parent* the element is a plane of the same 3D rendering context: the 4x4s of the chain multiply out and are flattened once, at the primitive. The context starts at the first element of the chain whose parent is flat. Its planes are drawn in paint order, not sorted by depth, and not cut where they cross ([deviations](deviations.md#paint-and-transforms)); a clip of a plane's parent is in the parent's plane, which is somewhere else in space, so it goes to the window as its bounding box.
  - *Which value is used.* A grouping property makes the used `transform-style` of an element `flat` whatever it declares: `opacity` below 1 (or an animation of it), `filter`, `backdrop-filter`, `clip-path`, a mask, and `overflow` other than `visible` on either axis (`layout/stacking.rs`, `groups_descendants`, Chromium's `HasGroupingPropertyForUsedTransformStyle3D`). `isolation`, `mix-blend-mode` and `will-change` are in Chromium's list too and gpuix has none of them. `contain: paint` is not in the list. The declared value is still the stacking context and the containing block.
- **`backface-visibility: hidden`** paints nothing of the element and what is in it, and hits nothing, while the 4x4 it has accumulated in its 3D context shows its back. The test is Chromium's `IsBackFaceVisible`, which cc's `EffectTree::UpdateBackfaceVisibility` asks of the transform to the screen: the sign of the (2,2) entry of the inverse, which is the determinant of the flattened 3x3 over the determinant of the matrix, with the tolerance of a float (`Matrix3d::shows_backface`). A back that faces away is an empty window mask, which hides both the paint and the hit. A flat card flattens its faces onto itself before it turns, so each face is the root of its own context and the front is seen mirrored at 180 degrees; a `preserve-3d` card shows the face that turns toward the viewer.
  - `Window::layout_faces_away` answers the same question for a retained tree, whose hit test walks outside the paint. gpuix publishes it with the box (`ElementBounds::faces_away`) and a patch publishes it with the matrix.
- **Extents and culling go through the flattened 3x3.** A scroller's extent counts a box where its flattened matrix puts it, seen through its parent's perspective (`transformed_overflow`), and composes a `preserve-3d` chain level by level ([deviations](deviations.md#paint-and-transforms)).
- **Text under a homography** has no one 2x2 to rasterize through, so a glyph takes the bucketed raster that an animating transform uses and is drawn through the matrix: a perspective card is resampled and a little softer than Chrome's.
- **Used value, paint and layout.** The depth properties are not inherited, and a state style is folded into the style, so a base `perspective: 600` is cleared by a state's `perspective: none` (`forms_context_if_declared` says it for stacking). A change of the perspective or its origin moves only what the children paint (paint-only); the change that makes or ends a stacking context and a containing block (a `perspective` appearing, `preserve-3d` toggled) is layout, as for a transform.
- **Measuring.** `getBoundingClientRect` is the box of the four projected corners, cut at `MIN_W`; `offsetX` / `offsetY` are in the plane of the box through the 3x3 inverse; `getElementsAt` and `elementFromPoint` agree with the pointer, back faces included.

### Custom properties and calc()

`transform`, `translate`, `rotate`, `scale`, `transformOrigin`, `perspective` and `perspectiveOrigin` take `var(--x)` and `var(--x, fallback)`, and angles take `calc()`. No other property substitutes `var()`: custom properties are read by these seven and by `style()` container queries ([layout.md](layout.md)).

- **Substitution is on the text, before the parsers** (`transform::resolve_vars`, called in `build_element_unpumped` with the custom properties the element computes to, its own included), so the parse cache stays keyed by text and every reader of the transform (`Parts::of`, `is_active`, `is_active_if_declared`, stacking, the containing block) sees the same substituted style. The focus-visible and focus-within overlays are substituted too; the pointer states are folded into the style before it.
- **A `var()` that cannot be resolved makes the declaration invalid at computed-value time**, as in CSS, which is the property's initial value: `none` (`50% 50%` for the origin). That is not "ignored as a whole": a base `transform` does not survive it. A missing name with no fallback, a malformed call and a name that is guaranteed-invalid are unresolvable; the fallback may hold `var()` itself.
- **A custom property whose value holds `var()` is computed where it is declared** (`CustomProperties::descend`): against the other declarations of that element, in any order, and what it inherits. A descendant that overrides a name it refers to does not change it. A missing name or a cycle, with or without fallbacks, makes it guaranteed-invalid, which removes the property whatever it inherited; a reader of an invalid property takes its own fallback.
- **`calc()` in angles** (`css/angle.rs`, `parse_degrees`): sums of angles and products and quotients by numbers (`calc(45deg + 0.125turn)`, `calc(1turn / 4)`, `calc((1 - 0.5) * 180deg)`). A bare number (`calc(90)`) or a length is not an angle. `translate` takes the general `calc()` of lengths and percentages (a product with a `%` is a fraction of the box).
- **Transitions and animations see the computed value.** A transition compares the style with the element's custom properties substituted, so a `--p` change under `transition: transform` runs from the value computed before the change (and retargets from where it is), and a `--p` that stays the same starts none. A keyframe's `var()` resolves against the element each frame, and an unresolvable one is the initial value, so an animation follows a `--p` that changes while it runs.
- **A `--x` change alone is a paint-only batch** (`StyleDesc::differs_only_in_paint_or_custom_properties`) while no `@container` rule is in the tree, because `style()` queries are the only other reader and they lay out. A transform that turns on or off with it (`transform: var(--t)`) moves a containing block, which the next frame lays out and a bounds read before it does not see.
- **Only the subtrees that read it build again.** A custom property read by a build (a transform with `var()`, a `style()` query on the parent) is part of the key of the subtree that read it only (`Record::reads_custom`, like `reads_colors`), so a `--p` set above a page of 200 rows builds the elements that read it and not the rows. Per `--p` update that was 1803 elements built and is 3.
- **A `--p` written from JS is a tree edit,** so the frame is a paint-only frame, built for the elements that read it, and not a patched tick (`Edited`, [patch-frames.md](patch-frames.md)).

### Geometry

Chrome's rules, with the layout box and the painted box kept apart.

- `getBoundingClientRect` (and `getElementBounds`, `probeElementBounds`, `getBuiltElementBounds`, the automation tree) is the smallest box that holds the four corners of the border box after the transforms around the element and its own, under a perspective included (a corner behind the eye is cut at the horizon, [Three dimensions](#three-dimensions)). `offsetWidth`, `clientWidth`, `scrollWidth` and the other sizes, `ResizeObserver` and layout reads stay the layout box. `ElementBounds` keeps the layout box and `to_window`, the exact matrix, taken in prepaint from `Window::transform` and `Window::layout_own_transform`.
- A transform moves a box without a layout pass. The layout stamp of a forced read counts layout boxes, which a transform does not change, and `getBoundingClientRect` adds the transforms around the box on top of it. A paint-only write to a transform makes the next read capture the boxes again, so it answers with the transform written ([forced-reads.md](forced-reads.md#a-read-after-a-write-to-a-transform)).
- `offsetX` and `offsetY` of a pointer event are in the target's own space (from its padding edge), through the inverse; inline spans map through their paragraph's container. `getElementsAt` tests each clip and box through its inverse, so it agrees with the pointer.
- **`scrollIntoView` through nested scrollers** carries the box that holds the target in the window and maps it into each scroller's space, as Chrome does (oracle: 8 nested-scroller scenes, 128 cases): a scroller aligns the bounding box of the box's corners in its own space, then hands the next scroller the box that holds where its scroll left it, as a window box. A turn between two scrollers enlarges the box each time, as in Chrome; carrying a quad through the chain does not match (the first step already differs). A flattened scroller does not scroll. Key scrolling under the pointer, `IntersectionObserver` and `content-visibility` proximity use the window-space box. An `IntersectionObserver` target with a transform is intersected as its bounding box and its border and scrollbar room count as 0.
- **Autoscroll and focus follow the drawn box.** A selection drag's autoscroll compares the pointer with the list's edge zone in the list's space (`to_local_point`), and a virtual list compares a row with its viewport there (`box_in`). The input's drag autoscroll already works in local space (`window.on_mouse_event` maps the position). Tab into skipped content reads the box it is drawn at in the window and scrolls through the same chain (`scroll_element_into_view_at`), to the nearest edge.
- **A scroller scrolls as far as the transformed boxes inside it reach** (forwards and down only), through `transformed_overflow` in the taffy engine, in both the snapped and the unsnapped extents. The engine keeps each node's transform from `request_layout`. A patched tick of an animated transform moves the range too: the patch measures the scrollers around the roots it repaints again after the roots lay out (frame `ScrollerRecord`s, `Window::move_scroll_ranges`), gives their handles the new range, and gpuix republishes `scrollWidth` and `scrollHeight` from the capture (`republish_scroll_content`). The extent memo of a tick is forgotten for the node and what it is in, not for the whole engine. The patch is declined (`PatchDecline::ScrollExtent`) only where the frame would show the difference: the offset has to clamp, or the range changes along an axis the user scrolls and so moves a scrollbar's thumb. Anything else is a patched tick whose result is what the whole frame would give.
- **Text selection goes through the transform.** A text's registry entry and its selection-start regions record the matrix the text is painted through (and move with a replayed subtree like the bounds). A press, a drag, a double and a triple click map the window pointer into each text's space (`registry_point`) before comparing it with the layout bounds and computing the offset; the nearest-text fallback measures in the text's space scaled by the square root of `|det|`; `userSelect: none` regions are mapped too, and a flattened text is not hit. The autoscroll step still passes the window position, and `update_drag_at` maps per text.

### Animations

- **Pairing, as Chrome does it.** Lists that pair up function by function blend each pair (translate lengths blend their px and their fraction apart; `rotate`, `scale`, `skew` blend their numbers), the shorter list padded with identity functions. From the first pair that does not match (different kinds, `matrix()`, or a flip against a rotation), the rest of both lists is emitted as an `Interpolated { from, to, progress }` function, which GPUI resolves with the box size and blends through the CSS Transforms 1 2D matrix decomposition (translate, rotate, scale, skew); the matching head is blended on its own. `none` blends as the identity of the other list. The individual `translate`, `rotate` and `scale` blend as their own values, and `transform-origin` as two lengths. The pairing is `motion/transform_value.rs`; the keyframes of a run are positions among their distinct lists (`Layout::Transform`).
- **3D pairing, as Chrome does it** (`TransformOperations::Blend` and the operations' own `Blend`). Two functions blend one by one when they share Blink's primitive type: `translate()`, `translateX()`, `translateY()`, `translateZ()` and `translate3d()` are one primitive, the `scale` forms another, and every rotation (`rotate()`, `rotateX()`, `rotateY()`, `rotateZ()`, `rotate3d()`) a third; `perspective()`, `matrix()` and `matrix3d()` pair only with their own kind, and a `matrix()` is not a `matrix3d()`.
  - *Rotations* blend as Blink's `Rotation::Slerp`: turns about one axis (the axes within 1e-4 of the squared cosine, or one turn is zero or has no axis) blend their angles, so a turn can pass half a circle and takes the long way round; turns about other axes blend as quaternions by the shorter way.
  - *`perspective()`* blends as the reciprocals of its distances (`none` is a reciprocal of 0, a distance under 1 px counts as 1 px), and a reciprocal that comes out 0 or less is `none` again.
  - *The matrices left over* are decomposed in 3D when either list holds a 3D function (CSS Transforms 2 / Chromium's `Matrix44::Decompose`: translation, scale, skew, perspective and a quaternion; the quaternion is read by the stable case of the rotation matrix, since the specification's has a degenerate case near a half circle), blended (slerp for the rotation) and recomposed (`Transform::Blend`). Two matrices of the plane keep the 2D decomposition of CSS Transforms 1.
  - *Singular rests.* A leftover that cannot be decomposed (one that flattens space) is no blend: Chrome steps the whole list at the halfway point, unless a fraction of the box is in what is left over, where the blend waits for the box and steps only that part. This holds for 2D lists too.
  - *The other properties.* `translate` and `scale` blend with their z, `rotate` with an axis (as the rotation functions do), `transform-origin` as two lengths and a depth, `perspective` as a length (`none` against a length flips at the middle, and a spring that overshoots below 0 writes 0) and `perspective-origin` as two lengths. In Motion's contexts they are `AnimProp::TransformOrigin` (a list of three), `Perspective` and `PerspectiveOrigin`, and the depth keys are `Z`, `TranslateZ`, `ScaleZ`, `RotateX`, `RotateY`, `TransformPerspective` and `OriginZ`.
- **Internal formatter.** An animation hands its style to the renderer as text, so the tail of a blend between lists that do not pair is written as `-gpuix-interpolated(<progress>, <from list>, <to list>)` (`css/transform.rs`). It is not author CSS.
- **Patched ticks.** A tick of a transition, a CSS animation, a tween, a spring or a motion value of any of these is a patch with no decline of either kind (`getPatchCounters`), including a word that rolls up into an `overflow: hidden` slot (`y` from a percentage), unless the tick moves the range of a scroller around it where the frame would show it (`ScrollExtent`, see Geometry). A Motion run that leaves its defaults (`x` from 0) is a stacking context from the first frame it is off them, and one that returns to them stops being one: those two frames are layout frames, as the flip of any transform is. Seeking, pausing and playing through `getAnimations()` draw whole frames (`Repaint::Layout`, as for any property). The same holds for a tick of a 3D list, the depth of the origin, a Motion `rotateY` and the `perspective` or `perspective-origin` of a parent: the element that runs is built alone and gpui paints its operations again.

### Retention and patched ticks

How transforms meet replay and patched ticks. The mechanisms are in [retention.md](retention.md) and [patch-frames.md](patch-frames.md).

- **Draw order and culling.** `insert_primitive_local`, the bounds tree and `primitive_bounds` use the transformed bounding box intersected with the content mask. `lies_outside_the_mask` and `prepaint_unlifted_child` cull a child by its transformed bounding box, and a culled element keeps its transform (`Window::layout_own_transform`) so the boxes of its descendants stay right. Every `translate` of a primitive (retained relocation) moves `transformation.translation` too.
- **Replay and patch carry the transform.** A patch's `Surroundings` and a retained `ReplayKey` carry the ambient transform and local clip (as they carry `element_opacity`). A recording is not replayed under a different ambient transform, and is not moved by a scroll or a layout when the ambient is more than a translation: it is built, so a page that scrolls inside a rotated card does not get the relocation speedup. A patch compares hitboxes ignoring `to_local`, `content_mask`, the local clip and the exact clips, and after a successful patch copies those, and the spaces of the listeners, from the scratch frame into the rendered one (`Hitbox::relocated` moves the space, not the bounds, inside a transform that is more than a translation). So a tick that only changes a transform is a patch with no declines (`patch_tests.rs`: a card that turns, a root and a card that turn, a card that slides, a listener given the position in the card as it is now, a subtree replayed inside another transform built again).
- **Operations do not depend on the clip.** `patch_unit` declines a unit whose operation count changed (`Operations`). A box or a line that a transform slides out of or into a clipping parent changed it when the scene dropped a clipped primitive before recording it, `paint_layer` pushed no layer for clipped-away bounds and text left out the glyphs a font away from the mask. Now a primitive, quad or layer clipped away is still recorded, and a patchable root keeps an operation for every glyph. A glyph the content mask clips away is a *pending glyph* (zed `PendingGlyph`): the sprite's origin, size, colour and params without an atlas tile, which painting it would have rasterized. `same_kind` equates it with a sprite, so the operations do not depend on the mask, it is never routed, and a paint or replay that finds it inside the mask gives it a tile. Its bounds include the pixel the rasterizer adds to a tile at a subpixel position, so its sprite is clipped away too. A long text sliding behind a clip rasterizes only what shows (120 glyphs in a 40px slot: 120 rasterized, then 7); `getFrameWorkCounters().rasterizedGlyphs` counts the rasterizations the atlas missed. Don't drop clipped primitives before recording again: a sliding word in an `overflow: hidden` slot declines every tick.
- **Every other local box tested against the mask is moved by the transform too (#116).** Background-image tiles, mask-image tiles and mask-border pieces were cut against the window mask in the local space (a 1000 px background under `translateX(-300px)` in an 800 px window lost the right 300 px; the pieces of a mask border were left out or kept wrongly), and the input's caret-visible test, which decides whether the caret blinks, did the same (a caret that a transform put in view did not blink, one it put out of view woke the window every 500 ms). They use `Window::reaches_content_mask`, and a rect passed in (`Style::visible_in_local_space`) is the mask taken back into the local space. Tests: `background-image-in-transform.test.tsx`, `input-caret-transform.test.tsx`, gpui `style_transform_tests`. Known and not fixed: the key of a gpui `.cached()` view has no ambient transform (gpuix has none), and an escaping absolute box under a rotated frame keeps the local clip of an `overflow: hidden` between.
- **A glyph is tested against the mask where the transform puts it.** The content mask is in window space and a glyph is painted in the local space, so the test that leaves out the glyphs a font away from the mask (`Window::reaches_content_mask`, used by the line painter for glyphs and soft-hyphen hyphens) moves the glyph's box by the ambient transform first (the translation, or the bounding box through the matrix) and under a general transform also tests it against the local clip. Tested in local space against a mask that had moved with the box, every glyph of a card with `overflow: hidden`, `overflow-x`, or a clipping child, moved by about 80 px or more (the font's reach past the clip), was dropped while the card and its background drew (#110; `clip-path` is not a mask and was never affected). `clip-in-transform.test.tsx` compares the ink of such a card with headless Chrome's through translations in both axes, a scale, a rotation and combinations, and counts the glyphs painted to show that what a clip really hides is still not painted wherever the card is.
- **`animating_transform`.** While a CSS animation or transition of a transform property (one that moves, scales or turns the element; the origins only place a transform and do not count) is current, `StyleDesc::animating_transform` keeps the stacking context and the containing block at every value it samples, `none` and the identity included, as `animating_opacity` keeps the effect group: Chrome keeps the context through a CSS run even at `none` (oracle `transform-run-context`). A Motion track or a motion value does not set it: Motion writes `transform` each frame, and `none` when its keys are at their defaults, so the context follows the value (the flip at a run's ends is a layout frame). `OpacityRun` is `LiftRun` (`Record::lift_run`, `Kept::LiftRun`, named `lift-run`) and is recorded for every run, Motion's included: a record made on the other side of a run's start or end of either animation is not skipped. The text raster has a flag of its own, `transform_in_motion`, that counts every run (see "Text").
- **Tapes.** A patched tick of a moving transform changes the boxes the elements publish. The tape of a patch is compared with the recording apart from the transforms around each box (`same_writes_apart_from_transforms`, `describe_apart_from_transform`), and after a successful patch those boxes are published from the capture (`each_bounds`, `publish_captured_bounds`). The registry entries and start regions of selectable text carry their matrices, which are compared apart from the transforms the same way and published by the patch (`Tape::each`). Whether the back of a box faces away is part of what a patch publishes with it and is not a difference the tape compares, so a Motion-turned card hides the face that turns away on patched ticks. Anything else that differs is still a mismatch.

### Measured

On the downstream app's pages (headless, 10 s idle, 75 Hz), patched and whole frames a second moved from 0 / 33.8 to 32.9 / 18.3 (changelog), 0 / 39.0 to 35.5 / 19.3 (fluid hover), 0 / 69.1 to 64.2 / 5.4 (carousel dots) and 66.3 / 4.0 to 67.7 / 2.5 (thinking indicator). What is still a whole frame there is not transform work: the hover commit (`PendingView`), the fluid highlight's `top` / `left` / `width` / `height` (`Edited`, `LayoutAnimation`) and the carousel track's width spring. With the thinking indicator's word slot `overflow: visible` instead of `hidden`, `Operations` declines fell from 11 to 3 in 10 s: they were the word's text moving in and out of the clip, which the clip-independent operation list closes (`motion-transform.test.tsx`, "a word that rolls up into an overflow hidden slot").

The downstream app's workarounds that can now move to `y`, `scale` and `rotate` have not been rewritten: the queued-stack and callout cards as insets, the chevron's JS tween, the dash-sliding spinner, the arrow glyph, the dialog scale and the changelog dot. The sidebar's `marginLeft` for sub-rows stays, because the rects measured there include the offset on purpose.

## Breaking changes

- `<svg>` no longer gets the `#e2e2e2` tint, and shapes with no fill paint black. Icons that used `#000` and relied on `color` to tint them need `currentColor`. Its content clips to its border radius.
- `overflow` clips to the padding box even when the border is transparent.
- Hover and active states that set `color` now reach `currentColor` in descendants.
- GPUI `Style.border_color` became `border_colors` and `Style.clip_path` became `ClipPathValue`.
- An appearance change always rebuilds the view.
- An undeclared border style is `none`, as in CSS: a `borderWidth` or `borderColor` alone draws nothing. Add `borderStyle: "solid"` (or a style in the `border` shorthand).
- An outline paints only with a style (`outline` or `outlineStyle`): `outlineWidth` and `outlineColor` alone draw nothing, as in CSS. A focus ring written `focusVisible: { outlineWidth: 2, outlineColor: "..." }` needs `outlineStyle: "solid"` or `outline: "2px solid ..."`.
- An `opacity: 0` element paints no primitive. It keeps its box and its hit area and runs its listeners, text registry, selection and find. While an animation or transition of its `opacity` is current it paints its group at 0 so that its operations keep their shape.
- An `<svg>` with shape children ignores `source` / `src`, and its `width` / `height` props size the svg box.
- A Motion key at its default is no transform. `x: 0` or `scale: 1` alone no longer makes the element a stacking context or the containing block of its `absolute` and `fixed` children, as in Motion, which writes `transform: none`. Motion's `none` also replaces a static `style.transform`.
- A deferred `<anchored>` (the default) is placed against the trigger's transformed bounding box in the window and drawn in window space, not against the untransformed box. In GPUI a `defer_draw` keeps the ambient transform stack and its content mask in prepaint, where it used to draw with an empty stack: a deferred draw inside a transform is turned and scaled with it unless it opts out (`Deferred::in_window_space`).
- `filter: blur()`, `drop-shadow()` and `backdrop-filter` under a scale, rotation or skew blur by the matrix (a `blur(4px)` under `scale(2)` is a `blur(8px)`), where they used the deviation of the style. `ResolvedFilter::Blur` is `{ x, y }`; `ResolvedFilter::blur(sigma)` builds the symmetric one.
- A `var()` in a transform property is substituted and an unresolvable one is `none`; a string with `var()` was invalid and ignored before. A custom property with `var()` in its value is computed where it is declared, not where it is read.
- Text under a general transform is rasterized through the matrix (`RenderGlyphParams` has a `GlyphTransform`), so its pixels change from the resampled ones.
- `rotateX()`, `rotateY()`, `rotate3d()`, `perspective()` and `matrix3d()` were invalid and made the whole `transform` ignored; they apply now. `translate3d()`, `translateZ()`, `scale3d()` and `scaleZ()` drew in 2D and now move or scale in depth, which shows under a `perspective` or a `preserve-3d` chain. Motion's `z`, `translateZ`, `rotateX`, `rotateY`, `transformPerspective` were accepted and ignored and now apply (`scaleZ` and `originZ` are new keys; the `perspective` key of a motion component is the CSS property of the element).
- A `perspective` and a declared `transform-style: preserve-3d` make a stacking context and the containing block of absolute and fixed descendants, as a transform does; an element with only one of them was neither.
- `TransformationMatrix` is a projective 3x3 (`rows`), the ambient transform is a 4x4, and `with_transform` takes a 4x4 and the parent's `preserve_3d`; `apply` and `to_local` return an `Option`. `ElementTransform` has `origin_z` and the 3D `TransformFunction`s.
- A pair of lists whose leftover matrices cannot be decomposed, 2D ones included, steps the whole list at the halfway point, as Chrome does; it blended through the 2D decomposition before.

## Upstreaming

The zed commits touch the scene, the Metal pipeline and the `Quad` layout, so they are the hardest to send: they change every GPUI renderer. Moving gradients into their own primitive would win back the `Quad` size and is the change to make first. The gpuix side is breaking mainly for `<svg>` colour and inline text.
